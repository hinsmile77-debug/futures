## 1. 규칙 자체의 이해 — 두 규칙은 서로 다른 물건이다

| | 롱 (GB 단순돌파 · 90분) | 숏 (압축돌파 · 하락추세 · 60분) |
|---|---|---|
| 트리거 | GB 0.5 상향돌파, **추가조건 없음** | 압축(GB·GS≤0.5 & \|GB−GS\|≤0.5) 후 10봉 내 GS 0.5 상향돌파 & GB≤0.10 & MA20<MA60 |
| 청산 | 90분 / 15:05 | GS≥1.2 / 60분 / 15:05 |
| 횟수 | 비중복(보유 중 재신호 무시) | **당일 최초 1회** |
| 노출 | 61.9% | 8.5% |
| β | +0.463 (t=10.87) — 시장 지배 | **−0.037 (t=−2.81)** — 시장과 반대 |
| 성격 | "쌀 때 사서 90분 들고 있기" | 독립 수익원 후보 |

**두 규칙은 상태(state)도 서로 안 겹친다.** 롱은 직전봉 GB 하나만 있으면 되고,
숏은 「압축 발생 봉 번호 + 당일 진입 플래그 + MA20/MA60」을 들고 있어야 한다.
⇒ **하나의 클래스로 합치면 안 된다.** 도전자 2개로 분리 등록한다(문서 §운용권고 2와 일치).

### 필요한 입력 4종 — 전부 종가 하나에서 나온다

```
GB(20) = (close − 20봉 최저종가) / close × 200
GS(20) = (20봉 최고종가 − close) / close × 200
MA20, MA60 = 종가 단순이동평균
```

미시구조·옵션·매크로 피처를 **하나도 쓰지 않는다.** 그래서 미륵이 피처 파이프라인
(STEP 4)과 완전히 독립이며, 피처 결측·게이트·CB 상태와 무관하게 계산된다.
이것이 "별도 운영"이 실제로 성립하는 근거다.

## 2. 🔴 착수 전 정정해야 할 문서 오류 4건

### 2-1. 원화 환산이 **5배 과대**다 — 미니선물 승수를 쓰지 않았다

문서는 `1pt = 250,000원`으로 환산했다(롱 432.5pt → 108,124,994원).
그러나 이 PC의 **운영 종목은 A0569000 = KOSPI200 미니선물**이고 승수는 **50,000원**이다.

```
config/constants.py:86   MINI_FUTURES_PT_VALUE = 50_000
config/settings.py:5998  현재 운영 종목: A0569000 (미니선물) — 승수 50,000 · 틱 0.02pt
```

같은 폴더의 `analysis/gp_lib.py:PT_VALUE = 50_000` 은 맞게 잡혀 있다 —
**검증 스크립트는 맞고 요약 문서만 틀렸다.**

| | 문서 | 실제(미니, 1계약) |
|---|---|---|
| 롱 211일 | 108,124,994원 | **21,625,000원** |
| 숏 211일 | 18,762,534원 | **3,755,000원** |

### 2-2. 비용 가정 0.15pt는 **채널을 안 나눈 값**이다 — 나누면 숏의 결론이 PC마다 갈린다

> 🔴 **[2026-09-10 사용자 지시] 왕복비용은 CYBOS·CREON으로 분리한다.**

대신증권은 **로그인 매체별로** 요율을 고시한다(495차). 두 운영 PC가 서로 다른 채널이다:

| 채널 | PC | 편도 요율 | 왕복 수수료 | +슬리피지 1틱/편도 | **왕복 총비용** | 1계약 원화 |
|---|---|---|---|---|---|---|
| **CYBOS** | MW0601 | 0.0098104% | 0.206018pt | 0.04pt | **0.246018pt** | **12,301원** |
| **CREON** | MW0602 | 0.0019% | 0.039900pt | 0.04pt | **0.079900pt** | **3,995원** |

(참조가 1,050 · 미니선물 50,000원/pt) — **3.08배 차이**다.
문서 가정 0.15pt는 **CYBOS 기준으로는 싸고, CREON 기준으로는 비싸다.**

거래수를 곱해 소급 t를 채널별로 재산출하면:

| 규칙 | 문서(0.15pt) | **CYBOS** | **CREON** |
|---|---|---|---|
| 롱 (587거래) | 2.91 | **2.53** | **3.19** |
| **숏 (149거래)** | **2.02** | **1.64** | **2.30** |

⚠ 🔴 **숏은 CYBOS에서 단일검정 문턱 1.96을 못 넘고, CREON에서는 넘는다.**
**같은 규칙의 유의성이 PC마다 다르다.** 채널을 합쳐 하나의 숫자로 말하는 순간
어느 쪽이든 틀린 말이 된다. ⇒ 판정은 **감지된 채널의 요율**로 하고, 리포트는
**두 채널 값을 병기**한다(사전등록 `gp_rule_cost.report_both`).

문서가 이미 지적한 Bonferroni 미달(필요 3.38 vs 2.02)과 **별개의 추가 감점**이다.
⇒ 숏을 "유의한 독립 수익원"으로 인용하지 말 것. 섀도 관찰 대상으로는 유효하다.

⚠ 위 재산출은 **소급**이며 가설의 출처다 — 판정 근거가 아니다(SOP §11 K-1).

### 2-3. 검증 데이터 원천 표기가 틀렸다 — `session_bars`가 아니라 `raw_candles`다

문서 머리말: *"미륵이 `session_bars` 1분봉 · 211거래일"*

실측(2026-09-10):

| 테이블 | 행수 | 범위 | 거래일 |
|---|---|---|---|
| `session_bars` | 1,208 | 2026-09-07 ~ 09-09 | **3** |
| `raw_candles` | 96,903 | 2025-08-19 ~ 2026-09-09 | **259** |

`session_bars`는 533차 풀타임 수집으로 **2026-09-07에 시작**됐다(550차 리포트가
"풀타임 수집 첫 3거래일"이라 적고 있다). 211일이 나올 수가 없다.
추출 스크립트 `analysis/gp_extract.py:64` 도 `FROM raw_candles` 다.
⇒ **재현 시 `raw_candles`를 볼 것.** 이 오기를 그대로 두면 다음 세션이 3일짜리
테이블에서 211일을 찾다가 헛돈다.

### 2-4. GP 기간 파라미터가 명세와 다르다 — 20 vs 25

`GOLDEN_POWER_구현명세.md`는 **n=25**를 HTS 실측 47지점과 오차 ≤0.01로 검증했고
`golden_power.py`의 기본값도 25다. 그러나 이 규칙은 **n=20**(`gp_bull_20`)을 쓴다.
산식은 같고 파라미터만 다르므로 계산은 문제없으나, **n=20은 HTS 대조를 거치지 않았다.**
09:20 진입 시작 시각이 「09:00 + 20봉 워밍업」과 정확히 일치하므로 의도된 값으로 보인다.
⇒ 구현 시 `period=20`을 **명시적으로 넘긴다**(기본값 25에 기대면 조용히 다른 규칙이 된다).

| 확인 항목 | 결과 |
|---|---|
| 매분 도달하는가 | ✅ `run_minute_pipeline` 내부 조기 return은 **데이터 가드 4개뿐**(중복봉·타입오류·비정상가격·고저역전). CB 발동·게이트 차단·FLAT 여부와 **무관하게** 훅에 도달한다 |

## 4. 🔴 선결 결함 — GP가 그대로 상속한다

### 4-1. 열린 가상거래가 **영구 미청산**으로 남는다 (계측 4원칙 ②)

`challenger_trades` 28건 전수 확인:

```
B_OFI_REVERSAL  2026-05-14 12:53  exit_ts=NULL  ← 미청산
B_OFI_REVERSAL  2026-05-18 14:20  exit_ts=NULL  ← 미청산
B_OFI_REVERSAL  2026-05-20 11:32  exit_ts=NULL  ← 미청산
                                  → 28건 중 3건 = 10.7%
```

원인 두 가지가 겹친다.

1. **엔진의 15:10 안전망이 도달 불가다.** `_is_force_exit_time(ts)`는 봉 ts로
   판정하는데 파이프라인이 15:10 이후 봉을 안 준다(§3-2). 마지막 처리 봉은 15:08이다.
2. **`_open_trades`가 인메모리다.** 프로세스가 재시작하면 열린 가상거래를 잃고
   DB 행은 `exit_ts=NULL`로 굳는다 — **552-10(`_broker_dep_base_today`)·
   552-11(`entry_source` 오귀속)과 같은 「재시작이 지운 상태」 계열**이다.

그리고 `_compute_and_save_daily()`는 `get_today_closed_trades()`만 세므로
**미청산 거래가 집계에서 조용히 사라진다.** 손실이었는지 이익이었는지 모르는 채로
성과가 좋아지는 방향이다 — 계측 4원칙 ②(미측정 ≠ 0) 위반.

⇒ GP 롱은 **노출 61.9%**로 장중 대부분 포지션을 들고 있다. 이 결함을 안 고치면
GP 손익 기록은 처음부터 못 믿는다. **최우선 선결 항목이다.**

### 4-2. 가상손익 수수료가 **키움 잔재 요율**이다 (493차와 같은 사건)

```
challenger/challenger_engine.py:_calc_pnl   commission = (…) * 0.000015 * 2
challenger/variants/base_challenger.py      COMMISSION_RATE = 0.000015
```

`1.5e-05`는 493차가 규명한 **키움 잔재 요율**이며 CYBOS 실제(9.8104e-05)의 **1/6.54**다.
브로커 채널 감지는 이미 `config/constants.py:BROKER_CHANNEL_SPECS`로 파생돼 있는데
challenger만 하드코딩을 들고 있다. 그대로 두면 GP 가상손익이 §2-2의 낙관 편향을
**코드 차원에서 재생산**한다.

### 4-3. 슬리피지 축이 없다

`_calc_pnl`은 수수료만 뺀다. 미니선물 1틱 = 0.02pt이고 GP는 종가 진입 가정이므로
최소 1틱 왕복(0.04pt)은 계상해야 한다. **계측 4원칙 ⑤** — 파생값(net)을 대사하려면
구성요소(gross·수수료·슬리피지)를 각각 걸어야 한다.

### 4-4. 도전자별 강제청산 시각을 못 준다

`FORCE_EXIT_TIME`이 엔진 모듈 상수다. GP는 **15:05**, 기존 도전자는 15:10.
도전자별 오버라이드가 필요하다(기본값 15:10 유지 — 기존 동작 불변).

### 4-5. 진입 게이트가 `grade in ("A","B")`로 고정돼 있다

```
challenger/challenger_engine.py:_run_shadow_inner
    if (open_trade is None and signal.direction != 0
            and signal.grade in ("A","B") and not is_force):
```

GP에는 등급 개념이 없다. GP 도전자가 트리거 시 `grade="A"`를 반환하면 통과하지만,
그건 **등급을 위장하는 것**이다(계측 4원칙 ④ 폴백 가시화 위반).
`signal_meta`에 `rule="GP_LONG_GB90"` / `grade_na=True`를 남겨 위장이 아님을 표시한다.

## 5. 수익 판넬 「GP」 구분 신설 — 가능하되 급소가 하나 있다

### 5-1. 현행 구조

```
dashboard/main_dashboard.py:6889
    _ORIGIN_KEYS  = ("auto", "manual", "unknown")
    _ORIGIN_LABEL = {"auto":"자동", "manual":"수동·외부", "unknown":"미측정"}
```

출처 축은 **포지션 단위**로 판정되고(`_assign_origins`), 방향 축(순/역)과 직교하며,
체크박스 상태가 `ui_prefs`에 저장된다. 「GP」를 네 번째 키로 넣는 것 자체는
**라벨·툴팁·체크박스만 추가하면 되는 기계적 작업**이다.

### 5-2. 🔴 급소 — 브로커 net 대사 경로를 오염시킨다

`_effective_day_krw()`가 이 패널의 **단일 관문**이고, 그 안에 `_day_is_whole()`이 있다:

```python
def _day_is_whole(self, date_str, day_rows):
    total = self._day_total_legs.get(date_str)
    return total is None or len(day_rows) >= total
```

브로커 net(익일가예탁현금 − 예탁현금)은 **그 날 전체의 합**이라 거래별로 못 쪼갠다.
GP 가상거래를 `self._rows`에 그냥 섞으면 두 방향으로 다 깨진다:

| GP 체크박스 | 벌어지는 일 |
|---|---|
| **해제** | `_day_total_legs`가 GP를 포함해 부풀어 → 모든 날이 `_day_is_whole=False` → **브로커 실측 net을 통째로 못 쓰게 된다.** 전환기준 ① 판정 원천이 죽는다 |
| **체크** | 브로커 net(실거래 전용)이 **가상거래를 포함한 집합의 손익**으로 표시된다 — 정확히 493차가 경고한 "조용히 그럴듯한 값" |

### 5-3. 처방 — 「분리 합성」

GP는 실거래와 **중복되지 않는 별도 계정**이므로 덧셈으로 합성할 수 있다.

1. `_day_total_legs` 집계에서 **GP 행을 제외**한다 (실거래 완전성 판정은 실거래만 본다).
2. `_effective_day_krw()`를 두 갈래로 나눈다:
   ```
   day_krw = (실거래분: 브로커 net 또는 엔진 net)  +  (GP분: Σ pnl_pt × 50,000)
   ```
3. GP 체크 시 **패널 상단에 배너**를 띄운다 — 반사실(`_is_cf`) 탭이 이미 쓰는
   방식 그대로다. 문구: 「🟣 가상 포함 — GP 섀도 손익이 합산돼 있다. 실적이 아니며
   **전환기준 ① 판정에 쓰지 말 것**」.
4. GP 체크박스 **기본값 OFF**. 켜지 않으면 현행 동작과 **바이트 단위로 동일**하다.
5. KRW 셀에 접미 마커(기존 `≈` 관례와 같은 자리)로 GP 포함 여부를 표시한다.

⚠ **전환기준 ①의 판정 함수는 영향받지 않는다** —
`utils/db_utils.py:fetch_daily_net_for_verdict()`는 패널과 별개 경로로
`daily_broker_pnl`을 읽는다. 오염 위험은 **사람이 패널을 보고 판단할 때**뿐이며,
그래서 배너가 선택이 아니라 필수다.

### 5-4. 데이터 공급 경로

`refresh_pnl_history(rows)`가 실측·반사실 두 패널에 **같은 rows**를 넘긴다.
GP 행은 `trades`에 없으므로 별도 공급이 필요하다:

```
utils/db_utils.py:  fetch_gp_shadow_positions(limit_days)  ← challenger.db 조회
main.py:_refresh_pnl_history()  →  refresh_pnl_history(rows, gp_rows=…)
```

⚠ **`trades` 테이블에 GP를 절대 넣지 말 것.** 브로커 대사·전환기준·수수료 재환산·
승패 사후검증이 전부 그 테이블을 실거래로 전제한다.

## 7. 착수 전 결정이 필요한 사항

1. **§2-1~2-4 문서 정정을 먼저 반영할지** — 원화 5배·비용·데이터 원천·기간 파라미터.
   정정 없이 구현하면 GP 패널 수치가 문서와 안 맞아 그때 다시 규명하게 된다.
2. **숏 규칙을 이번에 같이 넣을지** — 비용 정정 후 t=1.62~1.78로 단일검정 문턱
   미달이다(§2-2). 「관찰만 한다」면 넣는 게 맞고, 「유의한 규칙을 검증한다」면
   전제가 이미 깨져 있다. 관찰 목적으로 넣는 것을 권한다 — β=−0.037이라
   롱과 성격이 정반대이고, 넣지 않으면 그 사실 자체를 관측할 방법이 없다.
3. **관찰 기간 60거래일 중 규칙 파라미터를 건드리지 않는다는 확약** — 문서
   §운용권고 1이 요구하는 조건이며, 중간 조정하면 사전등록이 무효가 된다(458차 D6).
