# 1. 설명 — [2] Meta-Gate와 스코어러는 무엇인가

## 1-1. 채널 [2]가 묻는 것

`entry_quality_prob` — 메타라벨링 스코어러가 매 신호에 매기는 **"이 진입이 좋은 진입일 확률"** —
이 실제로 좋은 진입과 나쁜 진입을 가르는가.

그 확률로 신호를 3분위로 나누고 각 분위의 **실현 순EV**(방향조건부 미래이동 − 왕복비용)를 잰다.

**합격선** (`config/settings.py:VALIDATION_CAMPAIGN["meta_gate"]`, 사전등록):

```python
"top_ev_min_pt":     0.0,   # 상위 33% 순EV > 0
"sep_cost_mult":     2.0,   # (상위 − 하위) > 왕복비용 × 2  = +0.1409pt
"min_per_tercile":   30,    # 분위별 최소 표본
```

**왜 중요했나** — 2026-07-04 감사 §5가 **"활성화 순서 2순위: Meta-gate 사이징"** 으로 올린
승격 후보였다. 이 확률이 좋은 진입을 가른다면 그걸로 계약수를 조절하자는 것이었다.

## 1-2. 스코어러의 정체

**한 줄 정의**

> **"이 신호로 진입하면 방향이 맞고 실이익이 나는가"를 직접 학습한 GBM 이진 분류기.**
> 그 확률이 `entry_quality_prob`이다.

앙상블이 *"가격이 어디로 갈까"* 를 예측한다면, 스코어러는 그 위에 한 겹 얹혀
*"그 예측을 믿고 진입해도 되는가"* 를 묻는다. 금융ML의 **메타라벨링(meta-labeling)** 구조다 —
1차 모델은 방향, 2차 모델은 실행 여부.

**구성** (`learning/meta_label_classifier.py`)

| 항목 | 값 |
|---|---|
| 학습 데이터 | `meta_labels` 테이블 (STEP 1 예측검증이 매분 축적, 6개 호라이즌 합산 **101,354행**) |
| 레이블 | `skip` = 0 / `take`·`reduce` = 1 |
| 알고리즘 | `HistGradientBoostingClassifier` (max_iter 200 · depth 4 · lr 0.05 · leaf 30) |
| 전처리 | `StandardScaler` |
| 불균형 처리 | `compute_sample_weight("balanced")` — pos_rate 0.18~0.27 |
| 검증 | `TimeSeriesSplit` 3폴드 → AUC |
| 최소 표본 | 호라이즌당 **2,000행** 미달 시 학습 스킵 |
| 산출물 | `model/horizons/meta_gate/{hz}_entry_quality{,_scaler,_features}.pkl` (gitignore, PC별) |
| 재학습 | **매주 금요일 EOD 캠페인 체인** (`scripts/campaign_steps.py` → `train_meta_label_classifier.py`) |

> 재학습이 스케줄에 붙은 것은 **357차**다. 그전에는 어떤 스케줄에도 연결돼 있지 않아
> [2] 채널이 갱신 불가였다 — 그 자체가 한 번 고쳐진 결함이다.

## 1-3. 레이블 정의와 임계의 근거

`learning/meta_labeling.py:derive_meta_label()`:

```
realized_move = (future_close − target_close) × predicted      # 방향 조건부 실현이동

predicted == FLAT                          → skip   (0.0)
방향 틀림  or  realized_move ≤ 0            → skip   (0.0)
realized_move ≥ max(threshold_move×2, 0.05)
   or  confidence ≥ 0.70                   → take   (1.0)
그 외 (맞았으나 follow-through 약함)        → reduce (0.5)
```

### 임계(`threshold_ratio`)는 어디서 오나

호출부는 [`learning/prediction_buffer.py:422`](../../learning/prediction_buffer.py) 한 곳뿐이다:

```python
if _sigma_saved > 0 and SIGMA_K > 0:
    threshold = _sigma_saved / 100.0 * SIGMA_K * math.sqrt(h_min)
else:
    threshold = HORIZON_THRESHOLDS.get(horizon, 0.0003)

actual = build_single_target(target_close, current_price, threshold)   # ← 같은 값
meta   = derive_meta_label(..., threshold_ratio=float(threshold))      # ← 같은 값
```

🔴 **핵심 — 메타라벨 전용 상수가 아니다.** 바로 위에서 `actual`(UP/DOWN/FLAT)을 만드는 데 쓴
**그 밴드를 그대로 재사용**한다.

| 항목 | 내용 |
|---|---|
| 정의 | `σ_at_t / 100 × SIGMA_K × √(호라이즌 분)` — 예측 시점 rolling σ(`predictions.sigma_at_t`) |
| `SIGMA_K` | **0.41** — 근거는 *"FLAT 34% 달성 계수"*. `scripts/optimize_sigma_k.py`가 FLAT 비중이 3클래스 균등(≈33%)에 오도록 역산 |
| `√h_min` | 확산 스케일링 (랜덤워크에서 σ ∝ √시간) |
| 폴백 | σ 미저장 시 정적 `HORIZON_THRESHOLDS` (1m 0.075% … 30m 0.476%) |

⇒ **`realized_move ≥ threshold_move × 2.0`의 뜻**:

> *"UP/DOWN으로 분류되기 위한 최소 이동폭의 **2배** 이상 실제로 갔는가."*

배수 2.0은 임의의 튜닝값이 아니라 **"간신히 방향이 맞은 것"과 "제대로 따라간 것"을 가르는 배수**다.
하한 `0.05`(pt)는 σ가 극단적으로 낮은 날 임계가 0에 수렴해 아무 움직임이나 take가 되는 것을 막는
절대 바닥이다.

> ℹ **학습과 채점이 일부러 다른 임계를 쓴다.** `USE_FIXED_LABEL_THRESHOLD = True`라
> `batch_retrainer`의 **학습 레이블은 고정 `HORIZON_THRESHOLDS`**를 쓰고, 위 채점 경로만
> rolling σ다. 코드 주석이 의도를 밝힌다 — *"실전 rolling sigma와 학습 임계값을 분리 →
> 레이블 드리프트 제거"*(개선 4). **결함이 아니라 설계다.**

### `confidence`는 앙상블 confidence가 **아니다**

호출부가 `predictions` 테이블에서 읽는다:

```python
row = pred_conn.execute("SELECT id, direction, confidence, ... FROM predictions "
                        "WHERE ts=? AND horizon=? AND actual IS NULL")
...
confidence = float(row["confidence"] or 0.0)
```

`predictions`는 **STEP 5 멀티 호라이즌 예측**이 호라이즌마다 한 행씩 쌓는 테이블이다.
즉 이 `confidence`는 **그 호라이즌 모델 자신의 confidence**이고,
앙상블 투표 결과인 `ensemble_decisions.confidence`와는 **다른 테이블·다른 스케일**이다.

실측 분포 (`meta_labels`, 방향성 예측만):

| hz | n | min | max | avg | ≥0.70 |
|---|---|---|---|---|---|
| 1m | 18,535 | 0.3333 | 1.0000 | 0.4465 | 1,284 |
| 3m | 11,372 | 0.3333 | 1.0000 | 0.4697 | 1,087 |
| 5m | 8,938 | 0.3333 | 1.0000 | 0.5093 | 1,161 |
| 10m | 7,341 | 0.3333 | 1.0000 | 0.5227 | 1,055 |
| 15m | 6,363 | 0.3333 | 1.0000 | 0.5561 | 1,104 |

최솟값 0.3333은 3클래스 argmax의 구조적 바닥(1/3)이다.

🔴 **두 conf를 섞어 읽지 말 것.** CLAUDE.md 476차가 *"방향성 confidence는 2026-06-01 이후
0.60에 한 번도 닿지 않았다"* 고 못 박은 것은 **앙상블** 쪽이며, 이 임계와 무관하다.
이쪽은 0.70을 정기적으로 넘는다.

## 1-4. 피처의 "그 시점" — 예측 시점 T, 검증 시점 아님

```
T      STEP 4  피처 생성            → features (현행 141키)
       STEP 5  멀티 호라이즌 예측    → 그 features를 모델에 먹인다
       STEP 9  predictions INSERT   → ts=T, features=_feat_clean, sigma_at_t=σ_20
          ↓  (h분 경과)
T+h    STEP 1  verify_and_update(current_ts = T+h)
               target_ts = (T+h) − h = T                  ← 여기
               SELECT ... FROM predictions WHERE ts = target_ts
               meta_labels INSERT (ts=T, features=compact(그 행의 features))
```

검증 루프는 **현재 시각에서 h분을 되감아** 그때 남긴 `predictions` 행을 꺼낸다
(`horizon_targets = {h: current_dt − timedelta(minutes=m)}`).
`feat_dict`는 그 행의 `features` 컬럼 — **h분 전에 이미 저장돼 있던 값**이고 재계산하지 않는다.
`meta_labels.ts`도 `target_ts`(=T)이므로 테이블의 타임스탬프는 **예측 시점**을 가리킨다.

✅ **룩어헤드가 구조적으로 차단된다.** 피처는 T의 스냅샷, 레이블만 T+h 종가로 계산.
스코어러가 학습하는 관계는 정확히 *"T에 보이는 것으로 T→T+h 결과를 맞힐 수 있는가"* 이고,
이는 `MetaGate.evaluate()`가 매분 넘기는 것과 **같은 정보 집합**이다. **학습/서빙 정보 시점 일치.**

**어떤 피처인가** — `main.py:9767`이 넘기는 `features_clean`:

```python
_feat_clean = {k: round(float(v), 4) for k, v in features.items()
               if v is not None and v == v}      # v==v → NaN 제외
```

- STEP 4가 그 분에 만든 **피처 딕셔너리 전량** (호라이즌별로 고르지 않는다)
- **6개 호라이즌 행이 같은 features JSON을 공유**한다
- `compact_feature_json()`이 한 번 더 훑어 float 변환 실패 키를 버리고 6자리 반올림

⇒ 앙상블 모델의 배포 피처셋(`feature_names_hz`, 호라이즌당 10~17개)과는 **다른 집합**이다.
그쪽은 선별된 부분집합, 이쪽은 그날 만들어진 전량.

> 🔴 **463차 교락이 아팠던 이유가 여기 있다.** 6개 호라이즌의 입력이 동일하니
> 3m 진입에 1m 모델을 써도 **아무 오류 없이 그럴듯한 확률이 나온다.** 조용히 틀렸다.

## 1-6. ⚠ 오독 방지 — 무엇이 탈락한 것인가

**① "채널 [2] 탈락"은 "MetaGate 폐기"가 아니다.**
MetaGate는 라이브에서 그대로 돈다 — `MetaConfidenceLearner` 기반 `blended_conf` →
take/reduce/skip, 등급별 임계, 431차 무정보 폴백 중립화. 전부 무변경.
탈락한 것은 **`entry_quality_prob`을 사이징 승격 근거로 쓰는 것** 하나다.

**② 스코어러를 끄자는 뜻도 아니다.**
`strategy/entry/meta_gate.py:105`가 못 박고 있다:

```python
# [260704 감사 P1] meta_labels 기반 진입품질(수익확률) 섀도우 스코어 — 로깅 전용,
# action/size_multiplier 결정에는 관여하지 않는다.
entry_quality_prob = self._eq_scorer.score(horizon, features)
```

**처음부터 로깅 전용**이라 이번 탈락의 **라이브 영향은 0**이고, 스코어링·기록·주간 재학습은 계속된다.
488차의 `opt_chain_pcr` 두 축 분리와 같은 구도다 — *"승격 자격 없음"* 과 *"수집을 끄자"* 는
다른 이야기이고, 끊으면 재설계 때 쓸 표본이 함께 끊긴다.

## H1 🔴 스코어러 AUC가 0.49~0.55다 — [2] 탈락의 상류 원인

**실측** (`logs/retrain_eod_20260821.log`, 2026-08-21 재학습, TimeSeriesSplit 3폴드):

| hz | AUC | n | pos_rate |
|---|---|---|---|
| 1m | 0.5458 | 23,984 | 0.270 |
| 3m | 0.5092 | 16,770 | 0.250 |
| **5m** | **0.4971** | 14,055 | 0.230 |
| 10m | 0.5255 | 12,801 | 0.208 |
| 15m | 0.5477 | 11,818 | 0.184 |
| **30m** | **0.4890** | 21,926 | 0.204 |

🔴 **사실상 동전 던지기다.** 최고가 15m 0.5477이고, **5m·30m은 0.5 미만(역방향)**.

**왜 중요한가** — 이 AUC는 스코어러가 **자기 자신의 레이블**(take/reduce vs skip)을 맞히는
능력이다. 그것조차 무정보면 그 확률로 **손익을 분리하기를 기대할 근거가 없다.**
즉 [2] 채널의 FAIL은 분위 판정 단계의 문제가 아니라 **상류에서 이미 결정돼 있었다.**

⚠ **AUC와 [2] 분리도는 다른 축이다** — 전자는 라벨 예측, 후자는 손익 분리. AUC가 높다고
[2]가 통과한다는 보장은 없다. 다만 **AUC ≈ 0.5면 [2]가 통과할 리 없다**는 방향은 성립한다.

🔴 **그리고 이 수치는 매주 금요일 EOD 로그에 찍혀 왔는데 아무도 읽지 않았다.**
캠페인 리포트에도, 수집기 §12에도 없다. 292·303·371·468차가 반복한
*"안전장치가 한쪽 값에 붙박여 죽어 있는데 매번 사람이 뒤늦게 발견"* 과 같은 계열이다.

## H5 🟡 `confidence ≥ 0.70` OR 분기의 실효는 2.9%

`take` 16,316건을 두 분기로 분해:

| hz | take | realized_move로 | conf≥0.70 (교집합 포함) | **conf 때문에만 take** |
|---|---|---|---|---|
| 1m | 4,380 | 4,291 | 560 | **89** |
| 3m | 2,998 | 2,931 | 463 | **67** |
| 5m | 2,327 | 2,255 | 503 | **72** |
| 10m | 1,940 | 1,858 | 437 | **82** |
| 15m | 1,623 | 1,538 | 413 | **85** |
| 30m | 3,048 | 2,962 | 476 | **86** |
| **합** | **16,316** | **15,835** | 2,876 | **481 (2.9%)** |

⇒ **OR 분기가 실제로 라벨을 뒤집는 경우는 2.9%뿐이다.** 97.1%는 이동폭 조건만으로 이미 take.

⚠ **순환 주의**: `conf≥0.70`인 방향성 예측 6,825건 중 take가 2,876건(42%)인데,
그중 481건은 **이 규칙이 스스로 만든 것**이다. 자기가 take로 만들어 놓고
"conf가 높으면 take가 많다"고 읽으면 안 된다.
순환을 제거하면 35.1%(2,395/6,825) vs 기저 25.0% — 라벨 공간에서 약간의 lift가 보이나
**손익 축은 [39]가 일자단위로 이미 기각**했다(모델축 +0.16%p, n=25,240, 일자 p=0.1628).
**신호단위 lift를 근거로 삼지 말 것**(313차).

**할 일**
- 재설계 시 이 OR 분기를 **유지할지 결정**한다. 2.9%를 위해 레이블에 두 번째 축(confidence)을
  섞는 것이 값을 하는지, 아니면 **이동폭 단일 기준**으로 단순화할지.
- ⚠ 제거하면 레이블 정의가 바뀌므로 **§9-4 검증 시계 리셋 대상**이다. 과거 판정과 비교 불가.
