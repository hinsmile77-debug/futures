**순서 근거**: D2가 D1의 전제다 — 복구 재실행이 시간 청산의 부분 땜질 역할을 하고

## D2 — 시간 청산 피드 독립화

### 설계 확정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 발화 지점 | `_scheduler_tick` (30s QTimer) 내 신설 `_ts_scheduler_force_exit_net()` 호출 | 피드와 무관하게 도는 유일한 주기 실행점. `_fetch_investor_data`도 같은 타이머 계열에서 TR을 쏘므로 COM 호출 안전성 선례 있음 (메인 스레드, 콜백 밖) |
| 발화 시각 | **15:11:00부터** (FORCE_EXIT 15:10 + 60초 유예) | 정규 경로(STEP 8)가 15:10 분봉 마감에서 먼저 처리할 기회를 준다. 피드 정상이면 이 안전망은 영원히 no-op |
| 상한 | `is_market_open()` — 일반일 15:35 / 만기일 15:20 | 장 마감 후 주문 불가. 만기일 조기마감 자동 반영 |
| 발화 조건 | `position != FLAT` **or** `_integrity_broker_qty > 0` | 후자는 15:18 FINAL_CLOSE의 유령 잔량 케이스와 동일 조건 (`main.py:12758` `_broker_cached`) |
| 차단 조건 | `_has_pending_order()` — 대기 중이면 스킵(다음 30s 틱에 재확인) | 정규 경로가 이미 주문을 낸 상태에서 이중 발사 방지. Chejan은 시세 구독과 별개 연결이라 스톨 중에도 체결 통보는 온다 |
| 청산 수단 | 기존 `_ts_broker_direct_force_exit(self, price, reason)` **재사용** | 브로커 잔고 직접 조회 후 시장가 — 내부 상태 불신 전제라 스톨 상황에 정확히 맞음. 신규 주문 코드 0줄 |
| 가격 | `_last_pipeline_price` → `position.entry_price` 폴백 | 시장가 주문이라 가격은 로그·pending 등록용 힌트일 뿐 |
| 재시도 | 30s 틱 자연 재시도. 시도 횟수 카운터 + 첫 발화 시 notify 1회, 이후 5회마다 로그 | EmergencyExit(3회×10s)와 달리 블로킹 없이 타이머 리듬 그대로 |

### 명시적 비목표
- STEP 8의 15:10/15:18 로직 변경 없음 (정규 경로가 항상 우선)
- CB/EKS 상태 무관 — 시간 청산은 절대원칙이라 게이트를 타지 않는다

## D1 — 복구를 유지보수 패스로 교체

### 설계 확정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 컨텍스트 캐시 | 파이프라인 완주 지점(`main.py:9161` 옆)에서 `self._maint_ctx = (features, decision, ts)` | STEP 8이 features에서 실제로 쓰는 것은 `atr` 하나(`:12509`), decision은 신호소멸 섀도 3키뿐 — 1~4분 묵은 캐시로 충분. 캐시 없으면(기동 직후 스톨) 빈 dict — `atr` 기본 0.5로 동작 |
| 유지보수 함수 | 모듈 레벨 `_ts_run_maintenance_pass(self, row)` — 기존 `_ts_*` 패턴 | 스텁 self로 단위 테스트 가능 (test_phantom_hardstop 선례) |
| 하는 일 | `position != FLAT or pending or broker_qty>0`일 때만 `self._check_exit_triggers(price, 캐시 features, 캐시 decision, bar)` 1회 | STEP 8은 pending 가드 + 동일입력 멱등이라 반복 호출 안전 |
| 가격 | `_last_pipeline_price` 우선(봉만 죽고 틱이 살아 있으면 DB 종가보다 신선), 폴백 row close | |
| bar 재구성 | Phase 1 `_bar_from_raw_candle_row(row)` 재사용 | 봉중 스톱 판정에 high/low/ts 필요 |
| **안 하는 일** | STEP 1~7·9 전부, DB 쓰기 전부, `notify_pipeline_ran()`, `_last_real_pipeline_dt` 갱신 | 시계 보존 → ExchangeCB 감지 ~90s 단축 (§1-2 구멍 봉합) |
| 시나리오 B 계측 | `row ts > 캐시 ts`면 "원 실행 미완주(scenario B)" 로그 1줄 | 제안서 §7 미결 — 무료로 얻는 발생 빈도 계측 |
| `_try_pipeline_recovery` 골격 | 가드·row 조회·스킵 분기·600s ExchangeCB·age 체크 전부 유지. 유지보수 호출은 **스킵 분기보다 앞** — 같은 ts라도 매 호출 수행(멱등이라 무해, 스톨 중 안전 점검이 살아 있음을 로그로 증명) | 228차·381차가 다듬은 에스컬레이션 구조를 건드리지 않는다 |

### 파급 효과 (의도된 변화)
- `bar_recovered=1` 신규 발생 **중단** → Phase 1 라이브 확인 ②의 의미가 "새로 생기면 회귀"로 반전 (NEXT_TODO 갱신)
- 복구 로그 문구 변경: "[복구 완료] 파이프라인 재실행 성공" → "[유지보수 패스]" 계열

## D3 — 예측 저장 멱등화

### 설계 확정 사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 순서 | ① 중복 정리 → ② UNIQUE 인덱스 → ③ `INSERT OR IGNORE` | OR IGNORE는 **제약이 있어야만** 동작한다 — 인덱스 없이 바꾸면 무의미 |
| 마이그레이션 위치 | `init_predictions_db()` — "인덱스 생성 시도 → 실패(중복 존재) 시 정리 후 재시도" 패턴 | 매 기동마다 도는 함수라 무거운 검사 금지. `CREATE UNIQUE INDEX IF NOT EXISTS`는 인덱스가 이미 있으면 no-op |
| 백업 | 파일 복사 **금지**(860MB) → 삭제 대상 행만 `predictions_dup_archive` 테이블로 이동 | `_purge_extreme_conf.py`의 `predictions_archive` 선례 |
| 남길 행 | 그룹당 1행: **채점된 행(actual NOT NULL) 우선**, 동급이면 최소 id | 첫 기록 승리 + 라벨 보존. STEP 1 fetchone이 최소 id를 채점하므로 대개 일치 |
| 쓰기 의미론 | `INSERT OR IGNORE` — ⚠ **`OR REPLACE` 금지**: 재삽입이 채점된 행을 미채점 새 행으로 갈아치워 라벨을 잃는다 | |
| 적용 지점 4곳 | `save_step9_batch`의 predictions·ensemble / 레거시 `save_prediction` / 레거시 `save_ensemble_decision` | 전수 grep 확인 — 이 4곳뿐 |
| ensemble UNIQUE | `(ts)` 단독 | 분당 1행이 설계 의미 |

## D4 — 격자 방어선 2겹

| # | 위치 | 내용 |
|---|---|---|
| 1 | `BarAggregator.push()` | 직전 push와 같은 ts → 경고 로그 + `{1: bar, 나머지 None}` 반환(버퍼·age 무변화). `reset_daily()`에서 추적 ts 초기화 |
| 2 | `run_minute_pipeline` 입구 | ts가 직전 처리분과 동일 → WARNING + return. D1 이후 유일한 중복 주입 경로인 **stale oscillation 중복 BAR-CLOSE**(경고만 찍고 콜백은 그대로 나가는 기존 동작)를 파이프라인 전체에서 차단 |

## 롤백

각 D는 독립 커밋 불가(서로 얽힘이 적어 1커밋으로 묶되), revert 시 주의 1건:
D3의 UNIQUE 인덱스는 revert 후에도 DB에 남는다 — plain INSERT로 돌아가면 중복 삽입이
**IntegrityError로 죽는다**. revert 시 `DROP INDEX ux_pred_ts_hz; DROP INDEX ux_ens_ts;`
동반 필수 (이 사실을 커밋 메시지에 명기).
