### 1-2. 이 결손이 이미 만들고 있는 편향 (부수 발견)

- **학습 라벨 절단**: `_path_conditioned_label()`은 `close_map.get(future_ts)`가
  없으면 `DIRECTION_FLAT`을 돌려준다. 즉 매일 **14:39~15:08의 30m 라벨, 14:54~15:08의
  15m 라벨 …이 전부 FLAT으로 학습**된다. 시간대 피처(`is_open_volatile` 등)가 있으면
  GBM이 "15시 근처 = FLAT"을 그대로 배운다. 15:09~15:35 봉이 있으면 이 절단이
  15:35 이전 구간에서 사라진다. ⚠ 이것은 **학습 분포를 바꾸는 변경**이라 4단계에서
  게이트를 두고 넣는다(§5).
- **08:45 봉의 O·V가 틀리다**: 09-04 실측 — 스냅샷(08:45:18) 가격 1045.30 →
  첫 틱(08:45:19) 1045.64가 `open`이 됐고, 개장 체결 수량은 스냅샷의 누적거래량
  기준선에 흡수돼 `volume=419`에서 빠졌다. GapOffset이 이 봉의 close로 잡히므로
  방향에는 무해하나, **"개장 체결가" 자체는 어디에도 없다.**

## 2. 설계 원칙 (이 프로젝트에서 이미 산 교훈)

1. **`raw_candles`를 직접 늘리지 않는다.** 소비처가 46파일이고 그중
   `load_features_for_warmup(lookback_bars=30)`·`fetch_recent_raw_candles(limit=60)`
   같은 **"최근 N행" 조회가 다수**다. 행을 추가하면 어제 마지막 30분이 "14:39~15:08"에서
   "15:16~15:45(단일가 포함)"로 조용히 바뀐다 — 스케일러 워밍업 분포가 바뀌는데
   아무 로그도 안 남는다. 461차 `mdd_pct`·493차 수수료와 같은 유형의 사고다.
2. **세션 태그는 저장 시점에 기록자가 박는다**(계측 4원칙 ②·④). 나중에 시각으로
   역산하면 만기일(15:20)·거래소 CB 단일가·재기동 복구봉을 구분 못 한다.
3. **미측정 ≠ 0.** 체결유형코드를 못 받은 봉은 `auction_code=NULL`, 예상가 없음은 NULL.
4. **소비는 opt-in.** 데이터가 먼저 쌓이고 품질이 실측된 뒤에 학습·워밍업·분석이
   하나씩 옮겨온다. 자동 통합 금지(절대원칙 §6과 같은 취지).
5. **15:10 강제청산·15:40 마감 체인은 건드리지 않는다.** 수명 연장은 "마감 이후에
   6분을 덧붙이는" 형태로만 한다.

### Phase 1 — `session_bars` 적재 (메인 프로세스 · 저장만 · 판단 무변경)

**스키마** (`utils/db_utils.py:init_raw_data_db` 옆에 추가, 같은 `raw_data.db`):

```sql
CREATE TABLE IF NOT EXISTS session_bars (
    ts            TEXT PRIMARY KEY,   -- 'YYYY-MM-DD HH:MM:00'
    session       TEXT NOT NULL,      -- PRE_AUCTION | PRE_MARKET | REGULAR |
                                      -- POST_FORCE_EXIT | CLOSE_AUCTION | CLOSE_FILL |
                                      -- EXPIRY_CLOSE | EXCHANGE_CB
    open, high, low, close REAL NOT NULL,
    volume        INTEGER NOT NULL,

    anchor_buy, anchor_sell INTEGER,  -- 22/23 봉내 증분 (NULL=미계측, 452차 규약)

    auction_ticks INTEGER,            -- 28≠0 틱 수
    source        TEXT NOT NULL,      -- 'rt' | 'chart_backfill' | 'rt_recovered'
    created_at    TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_session_bars_session ON session_bars(session, ts);
```

3. `main.py:_on_candle_closed` **최상단**(프리장 분기보다 앞) —

### Phase 2 — 프로세스 수명 +6분 (마감 단일가·15:45 체결 회수)

바꾸는 것은 **"언제 구독을 끊고 언제 종료하나"** 뿐이다. 15:10·15:40 앵커는 그대로다.

| 항목 | 현행 | 변경 | 근거 |
|---|---|---|---|
| `realtime_data.stop()` 호출 | `daily_close` 진입(15:40:17) | **`SESSION_COLLECT_END`(15:46:00, 만기일 15:21:00)** 도달 시 스케줄러 틱에서 | 15:45 체결(`28=30`) 수신 후 여유 60초 |
| 자동 종료 | daily_close 완료 +15초(15:40:39) | `max(daily_close 완료+15s, SESSION_COLLECT_END+15s)` | 수집 종료 뒤 종료 |
| `FREEZE_WATCHDOG_WINDOW` 끝 | 15:45 | 15:47 | 감시 창이 수집 창을 덮어야 한다 |
| `EOD_RETRAIN_SCHEDULE_HM` / 작업 스케줄러 `MireukiEODRetrain` | 15:45 | **15:50** | 메인이 쓰는 중 py310 재학습이 DB를 읽기 시작하지 않게. 예산 15:50~16:10(현행 +5분, 702행 주석의 20분 예산 내) |
| 구독 시작 | 08:45 EarlyWarmup 틱(실측 08:45:18) | **08:44:30** 별도 조건(스케줄러 30초 틱 → 08:44:30~08:45:00 창) | 개장 체결(`28=10`) 수신. EarlyWarmup 워밍업 로직은 그대로 08:45 |

⚠ 주의점
- `daily_close`는 15:40에 그대로 돈다. 그 안의 **DBWriter 센티널·WAL 체크포인트·
  prune**이 15:40~15:46 사이의 `session_bar` 쓰기와 겹친다 → Phase 1-4의 동기 우회로
  해결하고, WAL TRUNCATE 체크포인트는 **수집 종료 뒤 한 번 더**(종료 직전) 수행.
