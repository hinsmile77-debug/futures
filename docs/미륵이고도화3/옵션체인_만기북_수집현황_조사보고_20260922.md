## 2. Q1 — UI ATM PCR 의 정체

### 2-2. 종목 선택 파이프라인 (오늘 실측)

```
CpUtil.CpOptionCode        → 4,600 종목  (data/option_chain.json, saved_at=2026-09-22)
_filter_front_month()      → ym=2610 만 남김            682 종목
_filter_atm(window=30.0)   → spot±30pt = 24 행사가      48 종목  (콜 24 + 풋 24)
_compute_atm_oi()          → 그중 최근접 콜 1 · 풋 1     2 종목
```

당일 워커 로그와 일치한다 — `[OptionChain][Worker] 완료 3050ms | target=48 valid=48`.

### 2-3. 캐시에 위클리가 없다는 증거

`data/option_chain.json` 전수 집계:

| 항목 | 값 |
|---|---|
| 종목 수 | 4,600 |
| 코드 접두 | **`B01`(콜) 2,300 · `C01`(풋) 2,300 — 이 둘뿐** |
| `ym` 분포 | 2610, 2611, 2612, 2701, 2702, 2703, 2706, 2709, 2712, 2806, 2812 — **전부 월 단위** |
| 코드 예시 | `B016AA01`, `C016AA01` (8자) |

`_filter_front_month()` 는 「만기(해당월 2번째 목요일)가 오늘 이후인 첫 `ym`」을 고른다
(`option_chain_worker.py:113~134`). 2609 는 이미 목록에서 빠졌으므로 오늘은 **2610**,
만기 **2026-10-08**, 잔존 16일.

### 2-4. 짚어둘 점

조사일(2026-09-22, 화) 기준 **(목)위클리 만기는 이틀 뒤인 9/24** 였다. 1분봉 초단기
판단에서 감마가 가장 크고 딜러 헤지가 실제로 걸리는 북은 그쪽인데, 체인 축은
잔존 16일짜리 먼스리를 보고 있었다.

## 3. Q2 — 위클리 지표에 필요한 데이터 4종

### 3-1. 현황

| # | 필요 데이터 | 먼스리 | 위클리(월·목) | 원천 |
|---|---|---|---|---|
| ① | 종목코드 + 행사가 + 콜/풋 + 만기 | ✅ 4,600 | ❌ **0** | `CpUtil.CpOptionCode` |
| ② | 행사가별 OI | ✅ | ❌ (①부재로 호출 불가) | `Dscbo1.OptionMst` `GetHeaderValue(99)` |
| ③ | 행사가별 gamma | ✅ | ❌ (〃) | 같은 TR |
| ④ | 스팟 | ✅ | ✅ | 선물 실시간 체결가 (공용) |

②③은 `mst_obj.SetInputValue(0, code)` → `BlockRequest()` 의 **종목코드 단위 조회**다
(`option_chain_worker.py:372~379`). 코드만 확보되면 계산 로직
(`_compute_pcr` · `_compute_atm_oi` · `_compute_gex`)은 **수정 없이** 그대로 돈다.

**즉 병목은 ① 하나다.**

### 3-2. 이미 있는 위클리 데이터는 성격이 다르다

611차(2026-09-21)가 `CpSvrNew7222` 로 위클리 수급 수집을 시작했다
(`config/settings.py:7568~7599`, `data/db/option_flow.db`).

| 보유 | 미보유 |
|---|---|
| 시장코드별(월콜·월풋·목콜·목풋·먼스리콜·먼스리풋·현물) 투자자별 순매수 **계약수/금액** | 행사가 · OI · 그릭 |

**PCR·GEX 를 만들 수 없다.** 같은 주석의 실측 —
「계약수 기준 (월)위클리 5,575 vs 먼스리 273, **20.4배**」.
수급 축은 위클리가 주무대임을 이미 확인해 두고, 체인 축은 여전히 먼스리만 본다.
**같은 시스템의 두 축이 서로 다른 만기를 보고 있다.**

```
5|B01610745|KR4B016A7454|C 202610   745.0|2|00745.00| |2001|KOSPI200
L|B09FEW937|KR4B09FE9375|위클리C 2609W4   937.5|2|00937.50| |2001|KOSPI200
```

**두 가지가 확정된다.**

1. Cybos `CpOptionCode` 가 준 4,600 개는 type 5/6 과 **정확히 일치**한다
   → 이 API 는 **먼스리 전용**이 맞다. 설정 실수나 필터 문제가 아니다.
2. 위클리 코드는 존재하고 이 PC 에 이미 있다 — 단 **KIS 단축코드 체계**다.

### 코드 체계가 다르다

| | 예시 | 구조 |
|---|---|---|
| Cybos | `B016AA01` (8자) | `B01` + `6`(2026) + `A`(10월) + `A01`(행사가 **인덱스**) |
| KIS | `B01610745` (9자) | `B01` + `6` + `10` + `745`(행사가 **숫자**) |

**KIS 마스터의 위클리 코드를 `Dscbo1.OptionMst` 에 그대로 넣을 수 없다.** 변환 규칙
확인이 선행돼야 한다.

## 7. 비용과 선행조건

위클리 2북 × 24행사가 × 2(C/P) = **96종목 추가 조회**.

| | 현재 | A/B 도입 시 |
|---|---|---|
| 조회 종목 | 48 | 144 |
| 사이클 소요 | 3,050ms (당일 실측) | **~9초 추정** |

**폴링 예산 재설계가 선행돼야 한다.** 612차가 이미 못박아 둔 실측:

> 「5분 폴링」이 실제로는 대개 10분이었다. 2026-09-21 실측 완료 간격 31개:
> 5분 8 / 10분 16 / 9분 3 / 14분 2 / 그 외 2.
> — `collection/options/option_chain_snapshot.py:is_due()`

지금도 목표의 2배로 벌어져 있다. 여기에 3배 부하를 그대로 얹으면 **먼스리 갱신이
20분대로 밀린다.** 위클리 추가의 선결 조건은 폴링 구조이지 코드 확보가 아니다.

대안: 북별 차등 주기(먼스리 5분 / 위클리 격분) — 마흐디가 쓰는 방식
(`mahdi/data/db.py:996`, `main.py:120`).

## 8. 미검증 — 다음에 확인할 것

1. **Cybos 가 위클리 코드를 주는 서비스가 있는가.** 이번 조사의 셸은 리눅스 VM
   이라 COM 에 닿지 못했다. Windows 에서 프로브 필요.
2. **`Dscbo1.OptionMst` 가 위클리 코드를 받는가.** 코드를 확보해도 이 TR 이
   먼스리 전용일 가능성이 남는다.
3. **Cybos ↔ KIS 코드 변환 규칙.** 특히 Cybos 의 행사가 인덱스 인코딩
   (`A01`…) 이 위클리에도 같은 규칙인지.
4. `docs/CyBos ref/CYBOS_선물옵션_API_목록.md` 에 `Dscbo1.OptionMst` 자체가
   **없다** — 이미 쓰고 있는 TR 이 문서에 누락돼 있다. 문서 보강 대상.
