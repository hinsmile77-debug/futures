## 0. 한 줄 요약

> 이번 세션에서 나온 결함 4건은 **서로 다른 버그가 아니라 하나의 구조 문제**다:
> **원천 응답을 보존하지 않고, 즉석에서 소수 필드만 뽑아 피처로 만들었다.**

## 4. Phase 1 — 원천 보존 계층 **(이 제안의 핵심)**

### 1-1. `raw_program_trade` 테이블 — 8111 56필드 전량 보존 🟢 **추가 COM 호출 0**

```sql
CREATE TABLE IF NOT EXISTS raw_program_trade (
    ts      TEXT PRIMARY KEY,   -- 'YYYY-MM-DD HH:MM' (분 단위)
    market  TEXT NOT NULL,      -- '1'=거래소
    fields  TEXT NOT NULL       -- JSON {"0":날짜, "1":시간, ..., "55":순매수체결금액}
);
```

- **왜 JSON인가**: `raw_features.features`와 같은 관례이며, TR 필드가 바뀌어도 스키마
  마이그레이션이 없다. 56개를 컬럼으로 펼치면 다음 변경 때 또 못 담는다.
- **쓰기 경로**: `api_connector.request_program_investor()`가 `raw["fields"]`로 헤더 전량을
  통과시키고, `investor_data.fetch_program_investor()`(또는 `main._fetch_investor_data`)가
  `INSERT OR REPLACE`. 60초 주기 · 단일 INSERT.
- **라이브 피처 경로 무변경** → 위험 0. 실패해도 try/except로 삼키고 수집만 건너뛴다.

| 항목 | 추정 |
|---|---|
| 추가 COM 호출 | **0** (이미 `range(64)` 전량 읽는 중) |
| 추가 메인스레드 비용 | INSERT 1회 ≈ 1ms (현행 `_fetch_investor_data` 예산 500ms) |
| 용량 | 370행/일 × 250일 × ~600B ≈ **55MB/년** (현재 DB 488MB) |

### 1-2. 7221 전량 보존 — **비용 측정 후 결정** ⚠

7221은 헤더가 아니라 `GetDataValue(열, 행)` 격자다. 상시 파싱 폭이 15열이라
전량(공식 type 0~51)을 매분 읽으면 **행 5개 기준 75 → 260회**로 COM 호출이 는다.

**절차**: ① 후속4가 배포한 첫 호출 `field_limit=64` 구간의 실제 소요시간을 다음 거래일
로그에서 확인 → ② 증가분이 예산 안이면 `raw_investor_flow` 테이블 신설, 아니면
**저장 주기를 낮춘다**(예: 5분마다 전량 / 매분은 15열).

⚠ **7221 전량 보존이 성사되면 gross PCR(0-3)의 "하루 1건" 한계가 자동으로 풀린다.**

### 1-3. 보존 계층 자체의 건강 감시

`scripts/feature_health_report.py`와 같은 취지로, 보존 테이블에 대해
**"응답은 왔는데 특정 필드가 상시 상수"** 를 점검하는 항목을 추가한다.
451차의 유령 피처가 raw tier에서 재현되지 않도록 하는 최소 장치.

## 5. Phase 2 — 피처 후보 (Phase 1 이후, 검증 절차 진입)

### 2-1. 8111 Δ(차분) — 누계를 흐름으로

현재 `program_arb_net`(=idx19)은 **일중 누계**다. 실측: 2026-08-07 비차익
`09:02 +134,498 → 15:34 −738,388`. 1분봉 예측에 필요한 것은 레벨이 아니라 흐름이다.

**신규 피처(기존 2종은 그대로 둔다)**

| 이름 | 정의 |
|---|---|
| `program_arb_net_delta` | 직전 성공 fetch 대비 idx19 증분 |
| `program_non_arb_net_delta` | 〃 idx37 |
| `quality_program_delta_ready` | 직전값 존재 여부 (0/1) |
| `program_delta_age_sec` | 직전 성공 fetch로부터 경과초 |

🔴 **설계상 반드시 지켜야 할 3가지 — 전부 이번 세션이 만든 교훈이다**

1. **일일 리셋 필수**: 8111은 일중 누계라 다음날 아침 0부터 다시 쌓인다.
   `reset_daily()`에서 prev를 지우지 않으면 **전일 마감 대비 거대한 음수 Δ**가 첫 틱에 튄다.
2. **실패 fetch를 "변화 없음"으로 만들지 말 것**: 현재 `_program_arb`는 조회 실패 시
   직전값을 유지한다 → 그대로 Δ를 계산하면 **Δ=0**이 되어 "정말 안 움직임"과 구분이 안 된다.
   → `supported=True`일 때만 Δ 계산·prev 갱신, 아니면 `ready=0`.
3. **미정의를 0으로 위장하지 말 것**: `ready=0`이면 Δ는 0으로 저장하되 **반드시 플래그로
   구분**한다. 그리고 `feature_health_report`의 게이트 맵에
   `program_*_delta → quality_program_delta_ready`를 등록해 **자동 감시 대상에 넣는다**
   (451차 PHANTOM 장치와 연결).

⚠ 폴링 간격이 불규칙하다(09:00~09:02 스킵, CB⑤ 방어, 실패). **정규화(Δ/경과초)는 하지 않고**
원시 Δ + age를 함께 준다 — 정규화 여부는 검증 단계에서 데이터로 판단한다.

### 2-2. gross 파생 — **Phase 1 데이터가 쌓인 뒤 오프라인에서 산출**

후보(전부 8111 원시에서 계산 가능, 추가 수집 불필요):

| 이름 | 정의 | 의도 |
|---|---|---|
| `program_arb_imbalance` | (idx13−idx7)/(idx13+idx7) | **무차원** [−1,1], 순매수의 스케일 요동 회피 |
| `program_nonarb_imbalance` | (idx31−idx25)/(idx31+idx25) | 〃 |
| `program_gross_turnover` | (idx43+idx49)의 **Δ** | 분당 프로그램 거래대금 = 활동량 |
| `program_prop_ratio` | (idx42+idx48)/(idx43+idx49) | 증권사 자기(프랍) 개입도 |

> **여기서 파생을 미리 확정하지 않는 것이 요점이다.** Phase 1이 원시를 보존하는 순간
> 위 목록은 언제든 바꿔도 되고, 과거 구간에 소급 적용도 된다. 지금 급한 건 **저장 시작**이다.

### 2-3. 검증 절차 (생략 금지)

`scripts/ic_probe_pending_features.py` → `horizon_feature_sets.json:pending_validation`
등재 → purged Walk-Forward 게이트. 초기에는 **어느 호라이즌에도 넣지 않는다**(학습 영향 0).

⚠ **표본 현실**: 신규 피처는 과거 DB에 없다. `CpSvr8116`으로 **일 단위** 백필은 되지만

## 8. 실행 순서와 의존성

```
Phase 0  (오프라인·주석)        ── 승인 불필요, 즉시
   │
   ├─ 0-1 라이브 검증 3건 ──────────────┐
   │                                    │
Phase 1  (원천 보존)  ★핵심             │
   ├─ 1-1 raw_program_trade  ← 무비용, 최우선
   └─ 1-2 7221 전량 ← 1-1 이후, 0-1의 비용 측정 결과에 의존 ─┘
   │
Phase 2  (피처 후보)  ← 1-1 배포 후 데이터가 쌓이는 만큼
   ├─ 2-1 Δ 4종
   └─ 2-2 gross 파생 (오프라인 산출)
   │
Phase 3  (장중 프로브 1회)  ← Phase 1과 **병렬 가능**
   │
Phase 4  ← Phase 3 결과 의존
```

**가장 중요한 것 하나만 고른다면 `1-1`이다.** 추가 COM 호출 0, 라이브 피처 경로 무변경,
그리고 **오늘 시작해야 검증 시계가 오늘부터 돈다.** 나머지는 전부 그 위에서 나중에 결정해도 된다.
