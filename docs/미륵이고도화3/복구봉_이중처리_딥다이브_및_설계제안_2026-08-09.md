## 1. 복구 경로의 실제 동작 (실측)

### 1-1. 발동 구조

```
분봉 90초 미수신 (dashboard 워치독, 30s QTimer)
  → _on_pipeline_watchdog(90s)  → 300ms 후 _try_pipeline_recovery()
     → raw_candles 마지막 봉 SELECT → run_minute_pipeline(bar) 전체 재실행
  → 150s: 경보만
  → 240s: 브로커 연결 정상이면 ExchangeCB 조기 확정 / 이상이면 재복구
  → 300s: ExchangeCB 대기 모드 (복구 중단)
```

로그 실측 (2026-05-28 ~ 08-04): **시도 51회 · 완주 42회 · 스킵 40회.**
발생일 분포는 06-25(16회)·07-31(13회)·08-04(15회)에 집중 — Phase 1의 55개 파괴 봉과
같은 날들이다.

### 1-2. 🔴 완주 1회가 시계 2개를 되감는다 — ExchangeCB 감지가 ~90초 늦다

복구가 `run_minute_pipeline`을 완주하면 파이프라인 말미(`main.py:9161-9164`)가
`_last_real_pipeline_dt`(ExchangeCB 판정용 실경과 시계)와 `notify_pipeline_ran()`
(워치독 시계)을 **둘 다 리셋**한다. 228차가 "복구 **스킵** 경로는 시계를 건드리지
않는다"로 고친 것과 정확히 같은 취지의 구멍이 **완주 경로**에 그대로 남아 있다.

```
실제 스톨 시퀀스:
  T+90s   복구 완주 → 시계 2개 리셋 (+ 이중 처리 발생)
  T+180s  워치독 다시 90s → 복구 시도 → 같은 ts라 스킵 (시계 유지)
  T+240s~ 에스컬레이션 재개
→ ExchangeCB 확정이 설계 의도(240/300s)보다 약 90초 지연
```

### 1-3. "이중"이 아닐 때도 있다 — 두 시나리오

`raw_candles` 행은 **파이프라인 자신(STEP 4)**만 쓴다. 따라서:

| 시나리오 | 원 실행 상태 | 복구 재실행의 성격 |
|---|---|---|
| **A. 피드 스톨** (파이프라인은 건강) | 마지막 봉 **완주** | **순수 이중 처리** — 전 단계 중복 |
| **B. 파이프라인 중도 사망** (STEP 4 이후 예외) | STEP 4까지 (누산기 급식 완료 + 행 저장) | STEP 4는 이중, STEP 5~9는 **첫 실행** |

08-04가 시나리오 B의 실증이다: 복구 봉들의 predictions 행이 (ts,horizon) 중복
없이 **2행**(1m + 30m — 스톨 중 N분봉이 stale해 배포정책상 이 둘만 예측)뿐이다.
즉 그날 원 실행은 STEP 9에 도달하지 못했고 복구가 그 구간을 처음 실행했다.
**시나리오 B가 존재하므로 "복구를 그냥 없앤다"는 답이 아니다** — 무엇을 잃는지
정확히 계산해야 한다(§4-1 손실 분석).

## 2. 이중 처리가 오염시키는 상태 — 전수 목록

STEP별로 재실행 시 무슨 일이 나는지 코드로 전수 추적했다.

| STEP | 재실행 시 | 판정 |
|---|---|---|
| 1 예측 채점 | `WHERE actual IS NULL` 필터 → 이미 채점된 건 재조회 안 됨 | ✅ **자연 멱등** |
| 2 SGD 학습 | STEP 1이 빈 목록 반환 → no-op (+ 호라이즌별 봉단위 dedup 이중 방어) | ✅ **자연 멱등** |
| 4 피처 생성 | 🔴 누산기 전부 재급식 + 🔴 **N분봉 격자 밀림**(§3-1) | ❌ 오염 |
| 5~6 예측·앙상블 | SGD 상태가 달라져 같은 봉에 다른 예측 — 그 자체로는 무해하나 STEP 9로 전파 | ⚠ |
| 7 진입 | 90초+ 묵은 데이터로 **실주문 가능** — 신선도 가드 없음(§3-3) | ❌ 구조적 위험 |
| 8 청산 감시 | pending 가드·동일 입력 재평가라 멱등. **이것이 복구의 유일한 존재 가치** | ✅ |
| 9 예측 저장 | 🔴 plain INSERT + UNIQUE 없음 → (ts,horizon) 중복 행(§3-2) | ❌ 오염 |
| 말미 | 🔴 시계 2개 리셋(§1-2) | ❌ |

### 3-1. 🔴 최악의 오염 — N분봉 격자 밀림 (지금까지 아무도 몰랐다)

[bar_aggregator.py:34](../../features/bar_aggregator.py#L34) — `push()`는 ts를 보지
않고 무조건 버퍼에 append한다. `len(buf) >= h`가 봉 완성 조건이므로, **중복 1분봉
1개가 들어오면 그 뒤 모든 N분봉 경계가 1분씩 밀린다. 되돌아오지 않는다.**

```
08-04 실측: 12:07 / 12:11 / 13:09 / 13:27 / 13:47 / 13:58 / 14:05 — 7회 완주
→ 14:05 이후 30m 봉은 정시 경계에서 최대 7분 어긋난 채 마감됨
→ 그 봉으로 만든 raw_features_horizon 행·호라이즌 예측·bar_only 배포판정 전부 오염
```

집계량도 이중이다: 중복 봉의 volume/buy_vol/sell_vol이 N분봉에 두 번 합산된다.
Phase 0의 anchor 열은 아직 이 경로에 없지만, 방치하면 **Phase 2 앵커 대사
리포트가 N분봉 레벨에서 유령 잔차를 보게 된다.**

### 3-2. predictions/ensemble 중복 — 단, 복구가 유일한 원인은 아니다

실측 (predictions.db 94,743행):

```
(ts,horizon) 중복 그룹  423개
영구 미채점 고아 행      800개   (fetchone이 한 행만 채점, 나머지는 actual NULL 방치)
ensemble_decisions 중복  91개 ts
```

날짜 분포가 중요하다 — 복구 다발일(06-25: 35, 07-31: 35)과 일치하는 부분도 있지만
**06-23은 복구 2회뿐인데 중복 144건**이고, 05월에는 매일 6건씩 깔려 있다.
즉 **장중 재시작 등 별도 경로도 같은 중복을 만든다.** 복구만 고치면 이 오염은
계속된다 → 쓰기 자체를 멱등화해야 한다(D3).

고아 행 800개는 리포트류가 `actual IS NULL`을 "채점 대기"로 세는 모든 집계를
조용히 부풀린다.

### 3-3. 진입 위험 — 구조적이지만 실현 사례는 미확인

복구 재실행은 STEP 7까지 그대로 지나간다. FLAT + 등급 통과면 **90초~4분 묵은
가격으로 실주문**이 나갈 수 있다. trades.db를 복구 다발일 전수 대조한 결과
복구 완주 시각과 일치하는 진입은 **없었다**(가장 근접: 08-04 12:03:51 진입 vs
12:07:20 복구 — 진입이 먼저). 실현되지 않은 이유는 등급·게이트가 우연히 막았기
때문이며, 구조적 방어는 없다.

### 3-4. Phase 1과의 관계

Phase 1은 이 재실행이 **DB 행을 파괴하는 것**만 막았다(멱등 재저장 + `bar_recovered=1`).
인메모리 오염(§3-1)·중복 행(§3-2)·진입 위험(§3-3)·시계 리셋(§1-2)은 전부 남아 있다.

## 4. 🔴 부수 발견 — 절대원칙 §1의 마지막 구멍

이번 조사에서 원 안건보다 심각한 것이 나왔다. **완전 피드 스톨이 15:10을 관통하면
포지션을 청산할 주체가 없다.**

시간 청산(15:10 강제 / 15:18 FINAL_CLOSE)의 발화 지점을 전수 추적한 결과:

| 경로 | 15:10 시간 청산 발화 가능? | 스톨 중 상태 |
|---|---|---|
| 파이프라인 STEP 8 (`main.py:8841`) | ✅ 유일한 정규 경로 | ❌ 분봉 없음 — 죽음 |
| 틱 하드스톱 (`_process_tick_stop`) | ❌ 가격 스톱만 | ❌ 틱도 없음 |
| 워치독 → 복구 | (재실행 경유로 가능했음) | ❌ **15:10 이후 `is_force_exit_time` 가드로 둘 다 정지** (`main.py:11050, 11293` — 경보 무한루프를 막은 정당한 수정이었으나 이 부작용을 남김) |
| `_scheduler_tick` (30s QTimer, **피드 독립**) | ❌ 시간 청산 로직 없음 | 살아 있으나 할 일이 없음 |
| `daily_close` (15:40) | ❌ 통계·재학습만, 청산 로직 없음 | — |
| `EmergencyExit` | CB/KillSwitch 발동 시에만 — 그것들도 파이프라인 구동 | ❌ |

즉 14:50에 피드가 완전히 죽고 포지션이 있으면: 15:10 미청산 → 15:18 미청산 →
15:40 daily_close도 안 닫음 → **오버나이트.** 1분봉 시스템에 야간 데이터가 없어
갭 리스크가 시스템 전체를 무력화한다는 절대원칙 §1의 정확한 실패 모드다.
아직 실현된 적은 없지만(스톨이 늘 장중 이른 시간이었다), 복구 설계를 바꾸는 김에
반드시 함께 막아야 한다 — **복구 재실행이 사실상 이 구멍의 부분 땜질 역할을 하고
있었기 때문에, 재실행을 없애려면 이 구멍부터 정식으로 막는 것이 순서다.**

## 5. 설계 제안

### 설계 원칙

> 복구의 진짜 요구사항은 "지난 분을 다시 계산한다"가 아니라
> **"피드가 죽어도 포지션 안전과 에스컬레이션이 살아 있다"** 이다.
> 전자를 버리고 후자만 정확히 남긴다.

### D1 — 복구를 "전체 재실행"에서 "유지보수 패스"로 교체 (핵심)

`_try_pipeline_recovery()`가 `run_minute_pipeline(bar)`를 호출하지 않는다.
대신 신설 `_run_maintenance_pass()`를 호출한다:

```python
def _run_maintenance_pass(self, price, bar):
    """피드 스톨 중 포지션 안전 유지 — 계산·저장·진입·시계 리셋 없음.

    하는 것:   _check_exit_triggers(price, 캐시된 features/decision, bar)
               — pending 가드·동일입력 멱등이라 반복 호출 안전
    안 하는 것: STEP 1~7·9 전부. notify_pipeline_ran() / _last_real_pipeline_dt
               갱신 없음 → ExchangeCB 에스컬레이션 시계 보존 (228차 취지 완성)
    """
```

- **가격**: `_last_pipeline_price`(틱 경로가 갱신 — 봉만 죽고 틱이 살아 있으면 DB
  종가보다 신선) 우선, 없으면 복구 봉 종가.
- **features/decision**: 파이프라인 말미에서 `self._maint_ctx = (features, decision)`
  로 캐시해 둔 마지막 완주분을 사용. STEP 8이 features에서 실제로 쓰는 것은
  `atr` 하나뿐이라(`main.py:12509`) 1~4분 묵은 캐시로 충분하다 — 현행 재실행도
  같은 봉에서 재계산한 같은 값을 쓰므로 열화가 아니다.
- 기존 골격 유지: `_last_recovery_ts` 스킵 분기, ExchangeCB 600s 강제 진입 분기,
  15:10 이후 가드 — 전부 그대로.

**효과**: 이중 급식 0 · 격자 밀림 0 · 중복 행 기여 0 · 묵은 진입 위험 0 ·
ExchangeCB 감지 ~90초 단축(시계 리셋 소멸).

**손실 — 시나리오 B의 "반쯤 처리된 분 완성"을 포기한다.** 정확한 대가:
그 1분의 predictions/horizon 저장 누락(STEP 1이 그 target을 그냥 건너뜀 —
15:10 이후·CB 구간의 정상 공백과 동일 패턴), 그 1분의 진입 기회 소멸(묵은
데이터 진입은 애초에 원치 않음). **바운드가 1분이고 하류가 전부 공백 내성이
있으므로 수용한다.**

### D2 — 시간 청산의 피드 독립화 (§4의 구멍 봉합, 동반 필수)

`_scheduler_tick`(30s QTimer — 피드와 무관하게 돈다)에 시간 청산 안전망 추가:

```
장중 and position != FLAT and is_force_exit_time(now):
    → pending 없음 + 미발동 플래그 확인 후 _ts_broker_direct_force_exit()
      (브로커 직접 조회 후 잔량 청산 — 15:18 FINAL_CLOSE와 동일 함수 재사용)
```

- 정규 경로(STEP 8)와의 이중 발동은 기존 가드 그대로 방지: `_has_pending_order()`
  + `_final_close_done` + 자체 1회 플래그. 피드가 정상이면 STEP 8이 15:10:00에
  먼저 처리하고 스케줄러 안전망은 no-op이 된다.
- 이것이 들어가면 시간 청산의 **권위 경로가 피드 독립**이 되므로, D1의 유지보수
  패스는 가격 스톱 평가만 남아도 안전하다(심층 방어로 둘 다 유지).

### D3 — 예측 저장 멱등화 (복구 외 원인까지 한 번에)

§3-2에서 중복의 원인이 복구만이 아님이 확인됐으므로 쓰기 자체를 방어한다:

1. 기존 중복 정리 — (ts,horizon) 그룹당 **채점된 행 우선** 1행만 남기고 삭제
   (백업 후. 고아 800행이 이때 함께 소거된다)
2. `CREATE UNIQUE INDEX ux_pred ON predictions(ts, horizon)` /
   `ux_ens ON ensemble_decisions(ts)`
3. `INSERT` → **`INSERT OR IGNORE`** (⚠ `OR REPLACE` 금지 — 재삽입이 이미 채점된
   행을 미채점 새 행으로 갈아치워 라벨을 잃는다. 첫 기록 승리가 옳은 의미론)
4. 쓰기 지점 2곳 모두 적용: `save_step9_batch` + 레거시 `save_prediction`

### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| A. `run_minute_pipeline` 입구에 ts 멱등 가드만 | 중복 진입은 막지만 시나리오 A에서 청산 감시까지 죽는다(가드가 그냥 return하면 STEP 8도 안 돈다). "가드 + 내부에서 유지보수 모드로 분기"로 확장하면 15,000줄 모놀리스에 숨은 제2 모드가 생긴다 — D1처럼 **밖에서** 전용 함수로 푸는 쪽이 추론 가능 |
| B. 파이프라인에 `skip_stateful` 플래그 | 위와 동일 — 모드 폭발. 400차 UnboundLocalError처럼 조건분기 누락 사고의 온상 |
| C. 현행 유지 + STEP 9 저장만 억제 | 격자 밀림·누산기 이중·묵은 진입이 그대로 남는다 — 가장 나쁜 오염을 안 고침 |
| D. BarAggregator에 ts 중복 가드 추가"만" | 격자만 지켜지고 나머지 오염 전부 잔존. 단 **D1과 별개로 방어선으로는 가치 있음** — 아래 선택 항목 |

**선택 항목 (D4, 저비용 방어선)**: `BarAggregator.push()`에 "직전 push와 같은 ts면
무시 + 경고 로그" 가드. D1이 들어가면 정상 경로에서 발동할 일이 없지만, 미래의
어떤 경로가 또 중복 주입할 때(stale oscillation 중복 BAR-CLOSE가 이미 경고 로그로
존재하는 실제 위험) 격자만은 지켜준다.

## 6. 구현 순서 제안

| 순서 | 항목 | 규모 | 위험 | 근거 |
|---|---|---|---|---|
| 1 | **D2** 시간 청산 피드 독립화 | 소 (~30줄 + 테스트) | 중 — 주문 전송 코드. 단 기존 `_ts_broker_direct_force_exit` 재사용 + 3중 가드 | 절대원칙 §1 직결. D1의 전제 |
| 2 | **D1** 유지보수 패스 전환 | 중 (~60줄 + 테스트) | 저 — 실행을 **줄이는** 방향. 롤백 = revert 1커밋 | 본 안건 |
| 3 | **D3** 저장 멱등화 | 소 (마이그레이션 + 2곳 수정) | 저 — `OR IGNORE`는 동작 보존적. 정리 스크립트는 백업 후 | 중복 원인이 복구 밖에도 |
| 4 | **D4** BarAggregator ts 가드 | 극소 (~5줄) | 극소 | 심층 방어 |

각 단계 테스트 골자:
- D2: 스텁 브로커로 15:10/15:18 발화·이중발동 차단·정규 경로 우선 3종
- D1: 유지보수 패스가 (i) 누산기 상태를 건드리지 않음 (ii) DB에 아무것도 쓰지 않음
  (iii) 시계 2개를 리셋하지 않음 (iv) 포지션 보유 시 exit triggers를 호출함 — 4불변식
- D3: 중복 삽입 → 1행 유지, 채점된 행이 IGNORE로 보존됨
- D4: 같은 ts 재push → 버퍼 불변 + 경고
