## 결론

1. **철회는 수급 데이터 수정이 아니라 엔진의 R3 신호 선택 순서 결함이다.**
   - 엔진은 신호를 **터치 시각 순서**로 훑는다.
   - 그래서 「먼저 터치했지만 확인(반전 ≥ 50)이 **나중에** 온 신호」가, 「나중에 터치했지만 **먼저** 확인돼 이미 진입한 신호」의 자리를 **소급해서 빼앗는다.**
   - 14건 모두 이 구조다(**14/14**). 빼앗은 신호는 1–4분 먼저 터치했고, 4–10분 늦게 확인됐으며, 언제나 **반대 방향**이다.
2. **라이브 실집행이 맞고 재생이 틀렸다.**
   - 라이브는 그 시각에 확인된 신호를 탄다(인과적).
   - 재생은 나중에 들어온 확인으로 과거 선택을 다시 쓴다(미래 참조).
3. **이 결함이 재생 성적을 부풀려 왔다.** 22거래일(09-21–10-26) MAIN 재생이 현행 엔진 **+764만**, 인과 엔진 **+120만**이다.
   - `shindong.db` 채점과 그 위에서 한 반사실(TR44 승격 · 711차 수량 · 보완 판정)이 모두 같은 왜곡을 공유한다.
   - 실계좌(인과)가 재생보다 계속 나빴던 차이의 상당 부분이 여기서 나온다.
4. **대책 1순위는 엔진 R3를 「확인 시각 우선」으로 고치는 것이다**(값 변경 없음 · 선택 순서만 바꿈).
   - 분 단위 라이브 흉내에서 철회가 **6 → 0**이 된다(10-22·10-26).
   - **전략 후보**: 같은 인과 엔진에서 「V2 + F2(흐름 순응)」가 22일 **+797만**(MAIN +120만)이고 전·후반 모두 플러스였다 → 사전등록 섀도로 검증할 1순위다.

## 2. 메커니즘

`strategy/shindong/engine.py` R3 루프(요지):

```python
for t in R3 분들(터치 시각 순):
    if t <= busy: continue                 # 보유 중 터치는 무시
    sig = 맥점 터치(t)
    ent = 터치 후 10분 안 「콜−풋 반전 ≥ 50」 첫 분
    if ent: 거래 생성 → busy = 청산 시각   # ← 확인이 늦어도 터치가 빠르면 먼저 차지
```
