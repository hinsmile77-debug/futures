## 2. P1 — 종료 의도 3분기

### 현행

```
start_mireuk.bat:583   SET "_EXIT_KIND=일시적 크래시"
start_mireuk.bat:584   IF EXIST "data\_exit_normally" SET "_EXIT_KIND=정상 종료"
```

`_exit_normally` 기록 주체는 3곳뿐이다.

| 경로 | 위치 | 플래그 |
|---|---|---|
| daily_close | `main.py:14147` | 기록 |
| auto_shutdown | `main.py:14295` | 기록 |
| X → **완전 종료** | `dashboard/main_dashboard.py:15872` | 기록 |
| X → **재시작** | 〃 (분기 없음) | **미기록** ← 여기 |
| 강제 종료·크래시 | — | 미기록 |

마지막 두 줄이 같은 상태로 뭉개진다. 15:08 이 "일시적 크래시"로 남은 이유다.

### 설계

`data\_exit_intent` 파일 신설(한 줄: reason). `_exit_normally` 는 **그대로 둔다**
— 런처의 "재시작 안 함" 판정은 건드리지 않는다(하위호환).

| reason | `_exit_intent` | `_exit_normally` | 런처 동작 | 런처 라벨 |
|---|---|---|---|---|
| `daily_close` | 기록 | 기록 | 재시작 안 함 | 정상 종료 |
| `auto_shutdown` | 기록 | 기록 | 재시작 안 함 | 정상 종료 |
| `user_close` | 기록 | 기록 | 재시작 안 함 | 사용자 종료 |
| `user_restart` | **기록** | 미기록 | 재시작 | **사용자 요청 재시작** |
| (파일 없음) | — | — | 재시작 | 비정상 종료 |

`user_restart` 는 재시작 카운터(`_RESTART_CNT`)에 **올리지 않는다**. 5회 초과
경고 팝업은 진짜 비정상 종료만 세야 한다.

### 변경 파일

1. `main.py:14298` `_write_exit_normally_flag(reason)` →
   `_write_exit_flags(reason, keep_alive: bool)` 로 일반화.
   `keep_alive=True` 면 `_exit_intent` 만, `False` 면 둘 다 기록.
   기존 호출 2곳은 `keep_alive=False` 로 그대로.
2. `dashboard/main_dashboard.py:15868` `closeEvent` —
   `_btn_restart` 분기에 `_write_exit_flags("user_restart", keep_alive=True)` 추가.
   `_btn_full` 분기는 `"user_close"` 로 명시(현재 문자열 `user_close` 유지).
3. `start_mireuk.bat`
   - `583~587` `_EXIT_KIND` 3분기 확장 (`_exit_intent` 내용 읽어 라벨 결정)
   - `587` 카운터 초기화 조건에 `user_restart` 는 증가 자체를 건너뛰도록 추가
   - `428` 기동 시 잔존 파일 정리 블록에 `_exit_intent` 추가
   - `602~603` 읽은 직후 삭제 규약을 `_exit_intent` 에도 동일 적용
4. `main.py` 종료 경로에 SYSTEM 로그 1줄:
   `[Shutdown] intent=<reason> keep_alive=<bool>`
   — 사후 점검이 파일(이미 삭제됨)이 아니라 **로그**로 읽게 한다.

### 검증

- X → 재시작: 런처 로그에 `사용자 요청 재시작`, `RestartCnt` 불변
- X → 완전 종료: `사용자 종료`, 재시작 없음
- 작업관리자 강제 종료: `비정상 종료`, `RestartCnt` +1
- daily_close: 회귀 없음 (`auto_shutdown` 라벨 그대로)

### 위험

낮음. `_exit_normally` 의미를 바꾸지 않고 파일 하나를 **추가**만 한다.
런처가 새 파일을 못 읽어도 현행 동작으로 자연 퇴화한다.

## 3. P2 — 결손봉: **라이브 백필을 채택하지 않는다**

### 처음 떠올린 안과 그것을 버린 이유

`session_bars` 에 이미 그 3봉이 있으므로(차트 TR 백필), 기동 직후
`session_bars → raw_candles` 로 갭을 메우면 된다 — 새 TR 호출도 필요 없다.

**그런데 이미 같은 판단을 한 기록이 있다.** `utils/db_utils.py:1908~1914`:

> `raw_candles` 는 08:45~15:08 봉만 담고(10거래일 실측 매일 384행) 소비처가
> **46파일**이다. 그중 `load_features_for_warmup(lookback_bars=30)` ·
> `fetch_recent_raw_candles(limit=60)` 같은 **"최근 N행"** 조회가 다수라,
> 행을 더하면 어제 마지막 30분이 "14:39~15:08" 에서 "15:16~15:45" 로
> 조용히 바뀐다. (…) 그래서 원천은 원천끼리 둔다.

533차가 `session_bars` 를 별도 테이블로 뗀 이유가 정확히 이것이다.
결손 3봉을 중간에 끼워 넣는 것도 **같은 유형의 무언 변경**이다. 끝에 붙이든
중간에 끼우든 `LIMIT 60` 창은 3칸 밀린다.

추가로 `raw_features` 는 복원 자체가 불가능하다 — CVD·OFI·VWAP 는 틱이 있어야
한다. 없는 값을 0 으로 채우면 학습 오염이고, 비우면 `raw_candles` 와
`raw_features` 의 ts 집합이 어긋나 `batch_retrainer._load_from_db`
(`learning/batch_retrainer.py:2385~2398`) 가 두 테이블을 ts 로 맞추는 전제가 깨진다.

**결론: 라이브 기동 경로에 백필을 넣지 않는다.**

### 대신 채택하는 것

**P2-a 결손 감지 (필수).** 기동 시 `session_bars` 기준으로 당일
`raw_candles` 결손 ts 목록을 계산해 로그에 남긴다. 메우지 않는다.

```
[BarGap] raw_candles 결손 3봉 (09:41, 09:42, 15:08) — session_bars 로 보존됨, 백필 안 함
```

**P2-b 오프라인 백필 스크립트 (선택, 기본 미실행).**
`scripts/backfill_raw_candles_gap.py` — `--date`, `--dry-run` 필수.
`bar_recovered=1` 을 반드시 박는다(452차 규약 승계, 컬럼 이미 존재).
`raw_features` 는 **건드리지 않는다**.
라이브에서 자동 호출하지 않는다. 특정 날짜 분석이 결손 때문에 막힐 때만
사람이 판단해서 돌린다.

**P2-c 선결 과제 (P2-b 착수 조건).**
`raw_candles` 의 "최근 N행" 조회 소비처 전수 조사. 46파일 중 `LIMIT`·
`ORDER BY ts DESC`·`lookback_bars` 를 쓰는 곳 목록화. 이 목록 없이는
P2-b 를 돌리지 않는다.
