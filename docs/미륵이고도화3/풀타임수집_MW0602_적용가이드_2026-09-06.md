## 1. 무엇이 문제였나 (MW0602도 같은 코드라 같은 결손이 있을 가능성이 높다)

MW0601 실측(2026-08-24~09-04, 10거래일 전부 동일): `raw_candles`는 매일 **정확히 384행**,
08:45:18 ~ **15:08** 봉까지만 담는다. 15:09 봉과 15:10~15:34 봉 25개는 **수신·집계까지
끝난 뒤 저장만 안 된다** — `main._on_candle_closed`의 `is_force_exit_time` 가드가 저장 코드
앞에서 return 하기 때문이다. 15:35 이후는 15:40 `daily_close`가 구독을 끊고 프로세스가
15:40:39에 종료돼 마감 단일가·15:45 마감 체결이 없다. 08:45 개장 체결도 구독(08:45:18)보다
먼저 지나가 08:45 봉의 open·volume이 오염돼 있다.

**MW0602에서 먼저 확인할 것** (장후, 읽기전용):

```sql
SELECT substr(ts,1,10) d, COUNT(*), MIN(ts), MAX(ts)
FROM raw_candles WHERE ts >= '2026-08-24' GROUP BY d ORDER BY d;
```

`MAX(ts)`가 매일 `15:08:00`이고 행수가 384면 같은 상태다. dev가 v9-dev와 구조가 달라
값이 다를 수 있으니 이 쿼리로 **자기 PC 수치를 먼저 잡고** 시작할 것.

부수 발견: `learning/batch_retrainer.py:_path_conditioned_label`은 미래 종가가 없으면 FLAT을
돌려주므로 **매일 14:39~15:08의 30m 라벨이 전부 FLAT으로 학습**된다. dev도 같은 함수를
쓰면 같은 절단이 있다. 이건 Phase 4 안건이며 학습 분포를 바꾸므로 게이트 없이 손대지 말 것.

**충돌이 날 곳** (dev와 v9-dev는 `config/settings.py`가 5천 줄 넘게 다르다):

- `config/settings.py` — 두 상수만 가져오면 된다. 충돌 시 손으로:
  `EOD_RETRAIN_SCHEDULE_HM`(§4-1 참조) · `SESSION_BARS_ENABLED: bool = True`.
- `main.py` — 훅 3곳: ① `__init__` DBWriter 스레드 start 직후 `self._db_writer_closed: bool = False`
  ② `_on_candle_closed` 첫 줄(`now = ...` 다음) `self._persist_session_bar(candle)`
  ③ `_db_write_worker`의 `elif op == "session_bar":` ④ `daily_close` 센티널 `put(None)` 직전
  `self._db_writer_closed = True`. 그리고 `_persist_session_bar` 메서드 본문·import
  `save_session_bar`. dev의 `_on_candle_closed`가 v9-dev와 분기 구조가 다르면 **"저장 코드가
  모든 return보다 앞"**만 지키면 된다 — 테스트가 그것을 검사한다.
- `realtime_data.py`·`db_utils.py`·`time_utils.py`·`batch_retrainer.py`는 충돌 가능성이 낮다.

## 4. MW0602에서 다른 것

### 4-1. EOD 작업 스케줄러 — 반드시 함께 옮길 것

`EOD_RETRAIN_SCHEDULE_HM="1550"`은 MW0601이 작업 스케줄러 `MireukiEODRetrain` 트리거를
**15:45 → 15:50으로 옮긴 뒤** 맞춘 값이다. MW0602는 스케줄러가 별개다.

- 스케줄러를 안 옮기면 상수만 1550으로 두지 말 것 — 15:40 마감 경보가 진짜 실패를 놓친다(435차).
  그 경우 상수는 `"1545"` 유지.
- 옮기려면(Phase 2 대비): 작업 스케줄러에서 트리거 15:50으로 변경 후
  `Get-ScheduledTask MireukiEODRetrain | % Triggers | % StartBoundary`로 확인, 그다음 상수 변경.
- Phase 1만 쓰면 옮길 필요가 없다(메인은 여전히 15:40:39에 끝난다).

### 4-2. 채널·코드

- MW0602는 **CREON** 채널이지만 실시간 객체는 같은 `Dscbo1.FutureCurOnly`·`CpSysDib.FutureJpBid`다.
  헤더 28이 CREON에서도 오는지는 **첫날 로그로 확인** — `[CybosRT-AUCTION] 헤더 28 읽기 실패`
  WARNING이 뜨면 그 세션은 `auction_code=NULL`로 남고(0으로 채우지 않는다), 세션 분류는
  시각만으로 된다. 적재 자체는 정상이다.
- 프로브 기본 코드는 `data/ui_prefs.json:symbol_code` 앞 5자(`A0569000`→`A0569`)다. MW0602
  종목이 다르면 `--code`로 지정.

### 4-3. 채널 번호·리포트

캠페인 채널 번호를 재배정하지 않았고 리포트 채널도 추가하지 않았다(489차 B-3 — 번호 대조 금지).
`session_bars`는 리포트에 안 나온다. 대조는 `scripts/session_bars_recon.py`로만.
