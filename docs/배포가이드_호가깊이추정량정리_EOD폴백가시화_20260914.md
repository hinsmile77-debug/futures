## 2. 무엇이 바뀌었나

### 2-1. T-BOOK-1 — 호가깊이 추정량 정리

| | 내용 |
|---|---|
| **1a** | `book_bid_max` / `book_ask_max` **신설** (`raw_candles` · `session_bars` 양쪽) |
| **1b** | `_tot` 2종 **폐기 예정 강등** — 스키마·`constants.py` 주석에 명시 |
| **1c** | 소비처 이동 — 일일 점검기 적재 센서 `_tot`→`_avg`, 분석 스크립트 2종 |
| **1d** | `_tot` **제거는 보류** (아래 §5) |

**왜 열을 늘렸나 — 개명도 즉시 폐기도 안 되기 때문이다.**
사용자 제안은 「폐기하거나 `_last_snapshot` 을 박자」였다. 개명은 기존 행 9만여 개의
조회를 전부 깨고, 즉시 폐기는 552~566차 구간의 극단값을 볼 수단을 없앤다.
**오용을 부른 것은 이름이 아니라 「그 이름이 유일한 선택지」라는 사실**이었다 —
`_avg`(대표값)·`_max`(극단)가 나란히 있으면 `_tot` 을 집을 이유가 없어진다.

⚠ **`min` 은 신설하지 않았다.** 5단 합의 하한이 5 에 붙어 있어(실측 min=5·중앙 8)
사실상 상수다. 대칭을 위해 넣으면 쓰지 않을 열이 하나 더 생길 뿐이다.

### 2-2. F2-3ⓑ — EOD 폴백 가시화

563차 후속이 Phase 1 미달 시 Phase 2 폴백을 넣어 **EOD 전멸은 막았다.**
그러나 그것을 「EOD 복구 완료」로 읽으면 틀린다 — MW0601 실측 2026-09-14:

    3m·5m·10m·15m·30m  = 2026-09-14 17:09~17:15   ✅ 교체됨
    1m                 = **2026-09-11 15:50**     ❌ 3일째 그대로

566차가 `retrain_eod.py` 에 경고 두 줄을 추가했다:

    [EODFallback] 폴백 경로에서 **미교체** 호라이즌 1개: 1m — 구모델 유지.
    [EODFallback] 🔴 1m 은 폴백으로 학습할 수 없다 — 표본 부족이 아니라 구조다.
                  … 현행 1m 모델은 2026-09-11 15:50:48 학습본(약 3일 경과).

나이는 `acc.txt` 가 아니라 **사이드카 `gbm_1m_meta.json`** 에서 읽는다 —
`acc.txt` 는 교체 시에만 쓰여 「이미 존재하지 않는 모델의 성적」일 수 있다(456차 F6·F7).

⚠ **경고일 뿐 동작을 바꾸지 않는다.** 임계·경로 무변경(458차 D6).

## 3. 🔴 배포 전 반드시 — 미륵이 **재기동**

**이것을 빠뜨리면 배포가 무효다.** `book_*_max` 가 통째로 안 쌓인다.

`ALTER TABLE` 은 `init_all_dbs()` 안에서 도는데, 이 함수는 `main.py` **기동 시 1회**만
호출된다(`main.py` 하단). 그리고 **자동 재기동이 없다**:

- 런처(`start_mireuk.bat`)의 재시작 루프는 **장중 크래시 전용**이고,
  15:10 이후 종료 시엔 그냥 끝난다(오버나이트 금지).
- 등록된 예약 작업은 `MireukiEODRetrain` **하나뿐**이다 — 본체 기동 작업은 없다.
- 본체는 장 마감 후에도 살아서 「내일 08:45 매크로 수집 재개」 상태로 대기한다.

⇒ **어제 띄운 프로세스가 오늘도 그대로다.** 새 코드를 안 읽고, ALTER 도 안 돈다.

**절차**: 포지션이 **FLAT** 인 것을 확인하고(장 마감 후면 대개 FLAT),
본체를 종료한 뒤 `start_mireuk.bat` 로 다시 띄운다. 장 마감 후라 비용 0 이다.

**확인**: 기동 로그 `logs/YYYYMMDD_SYSTEM.log` 의 `[Runtime]` 줄 시각이
배포 시각 이후인지. 그리고:

```sql
PRAGMA table_info(raw_candles);   -- book_bid_max / book_ask_max 가 보여야 한다
PRAGMA table_info(session_bars);  -- 〃
```

## 4. 인수 조건 (배포 다음 거래일 장후)

`python scripts/defect3_collection_check.py` **한 번**이면 1~3 이 함께 나온다.

| # | 항목 | 기준 |
|---|---|---|
| 1 | `book_*_max 적재율` | **≥ 98%** (양 테이블) |
| 2 | `불변식 tot<=max` | **위반 0** — 위반이면 max 누적이 틀렸다 |
| 3 | `불변식 avg<=max` | **위반 0** |
| 4 | 배포 이전 거래일 | `max` **NULL** — 점검기가 `n/a(566차 배포 이전)` 로 찍어야 한다 |
| 5 | EOD 폴백 경고 | 폴백이 걸린 날이면 `[EODFallback]` **2줄**이 로그에 |

🔴 **4번을 0 으로 채우지 말 것.** 미측정이지 「깊이 0」이 아니다(계측 4원칙 ②).
그리고 **백필할 수 없다** — 봉내 최댓값은 스냅샷 전량을 봐야 나오는데 DB 에 남은
것은 마지막 1건(`_tot`)과 평균(`_avg`)뿐이다. 원천이 없다.

## 5. 하지 말 것

- 🔴 **`_tot` 을 지금 지우지 말 것(T-BOOK-1d).** 552~566차 구간 행에는 `_max` 가
  NULL 이라 그 구간의 봉내 극단값을 볼 수단이 `_tot` 뿐이다. 그 구간이 분석에서
  빠진 뒤에 지운다.
- 🔴 **일일 점검기의 「5단 ÷ 1단 잔량비」를 `_avg` 로 바꾸지 말 것.** 거기만은
  **의도적으로 `_tot`** 이다 — `bid_qty` 도 같은 마지막 스냅샷의 1단 잔량이라
  같은 시점끼리 짝지어야 「5단합 ≥ 1단」 불변식이 성립한다. 코드에 사유를 적어 뒀고
  `tests/test_566_book_depth_max.py::test_ratio_check_keeps_tot_on_purpose` 가 고정한다.
- 🔴 **`MIN_TRAIN_BARS`(15,000)를 낮추지 말 것.** F2-3ⓑ 경고를 보고 임계를 내리는
  것이 가장 흔한 오조치다 — 458차 D6 사전등록 위반이다. Phase 1 은 전 호라이즌이
  같은 X 를 쓰는 전부-아니면-전무 경로라 15,000 은 실제로 1m 이 요구하는 값이다.
  라이브 행이 쌓이면 풀린다(MW0601 산술: 부족 445행 ÷ 순증 약 338행/거래일 ≈ 1.3 거래일).
- **`min` 열을 추가하지 말 것** — §2-1 참조. 가드가 잡는다.
