**작성일**: 2026-08-09
**목표**: 서버가 주는 정답지(`누적체결매수`/`누적체결매도`)와 올바르게 파싱한 체결구분을

## 1. 이 Phase의 계약 — 무엇을 하지 않는가

Phase 0의 가치는 "고쳤다"가 아니라 **"손실 위험 없이 사실을 확보한다"** 이다.
따라서 아래는 **명시적 비목표**이며, 하나라도 어기면 Phase 0이 아니다.

| 하지 않는 것 | 이유 |
|---|---|
| `buy_vol` / `sell_vol` 값 변경 | 이 두 열이 지금 모델의 학습 입력이다. 건드리는 순간 train/serve skew(Phase 3 안건) |
| `is_buy_tick` 판정 로직 변경 | 위와 같음. **버그를 그대로 둔 채 옆에 정답을 적는다** |
| COM 호출 추가 | 이미 수신 중인 `FutureCurOnly` 이벤트의 **안 읽던 필드**만 읽는다. 요청 한도(15초/60건) 무영향 |
| 콜백 내 `dynamicCall` / `emit` | 절대원칙 §4. 신규 코드는 `GetHeaderValue` 읽기와 지역 상태 갱신뿐 |
| 피처 생성·전략·사이징 경로 접촉 | 신규 4열은 DB에만 적재. `feature_builder`가 읽지 않는다 |
| 대시보드 변경 | 판단이 안 바뀌는 단계에서 PyQt 탭을 늘리지 않는다 |
| main.py 복구 경로 수정 | **Phase 1 범위**다. Phase 0에서 손대지 않는다 (§6 잔여 위험 참조) |

## 2. 사실 확인 — 무엇을 근거로 이 필드를 읽는가

`docs/CyBos ref/Excel_Example/FutureCurOnly(SbPb).xls` (대신 제공 공식 캡처본):

```
13_누적거래량    1,525
22_누적체결매도    342      ← 22가 매도다. 순서 주의
23_누적체결매수  1,183
24_체결구분       50.0      ← 문자 '2'의 코드값. 문자열이 아니다
                            342 + 1,183 = 1,525  (항등식 정확히 성립)
```

로그 실측(`[CybosRT-TICK] ... flag=`, 75,264건): `49` 37,156 / `50` 38,108 / 그 외 0건.
호가 대조로 의미 확정 — `49`=매수(매도호가 체결 30.1% vs 매수호가 1.1%),
`50`=매도(매수호가 체결 29.9% vs 매도호가 1.2%).

> ⚠️ **인덱스를 추측하지 않는다.** 상한가/하한가 인덱스를 추측했다가 겪은 2026-05-10 B51
> 사고와 같은 계열의 위험이다. 22/23/24는 **공식 캡처본에 이름과 값이 같이 찍혀 있어**
> 추측이 아니다. 반면 `FutureMst` 스냅샷(`request_futures_snapshot`)에 누적체결매수/매도가
> 있는지는 **미확인이므로 읽지 않는다** — 기준선은 첫 틱에서 잡는다(§3-3).

## 3. 설계

### 3-1. `decode_trade_side()` — 체결구분 디코더

모듈 레벨 함수로 둔다(테스트 대상 + 향후 재사용).

```python
def decode_trade_side(raw):
    """FutureCurOnly `24_체결구분` → 'BUY' | 'SELL' | None.

    COM은 문자 '1'/'2'의 **코드값 49/50을 숫자로** 준다(공식 xls 캡처 확인).
    '1'/'2' 문자열로 오는 경우도 함께 받아 원천/런타임 변경에 견디게 한다.

    🔴 판정 불가면 None — **절대 매수로 폴백하지 않는다.**
       그 폴백(`is_buy_tick = price >= last_price`, 보합을 매수로 흡수)이
       매수비중 63% 편향의 원인이다.
    """
```

허용 입력: `49`, `49.0`, `"49"`, `"1"`, `1` → BUY / `50`, `"50"`, `"2"`, `2` → SELL.
그 외(`None`, `""`, `0`, `"9"`) → `None`.

> 주의: `1`/`2`(정수)와 `49`/`50`(코드값)이 **둘 다 유효**하다. 정수 1·2가 코드값
> 체계에서는 제어문자라 실제 체결구분일 수 없으므로 충돌하지 않는다.

### 3-2. 신규 상태 (인스턴스 변수)

| 변수 | 의미 |
|---|---|
| `_last_cum_buy` / `_last_cum_sell` | 앵커 기준선(직전 틱의 누적값) |
| `_anchor_primed` | 기준선 확보 여부. **`0`인 것과 "아직 못 받았다"를 구분**하기 위해 별도 bool |
| `_anchor_available` | 원천이 이 필드를 준 적이 있는가(둘 중 하나라도 >0 관측) |
| `_anchor_reset_count` | 누적값 역행(재접속·세션 리셋) 횟수 — 진단용 |
| `_flag_decoded_ticks` / `_flag_unknown_ticks` | 체결구분 디코딩 성공/실패 틱 수 — 진단용 |

### 3-3. 증분 산출 규칙

```
cum_sell = GetHeaderValue(22)      # 22가 매도
cum_buy  = GetHeaderValue(23)

if cum_buy > 0 or cum_sell > 0:  _anchor_available = True

if not _anchor_available:            d_buy = d_sell = None      # 원천 미제공
elif not _anchor_primed:             d_buy = d_sell = None      # 기준선만 세움
elif d_buy < 0 or d_sell < 0:        d_buy = d_sell = None      # 역행 → 버리고 재기준
else:                                d_buy, d_sell = 증분
기준선 갱신은 위 모든 경우에 수행
```

**역행을 `max(0, …)`으로 뭉개지 않는다.** 기존 `volume` 계산은 그렇게 하지만
(`_handle_tick:225`), 이 계층의 목적이 정확한 계측이므로 버리고 로그를 남긴다.
**기존 `volume` 라인은 변경하지 않는다**(비목표).

### 3-4. 봉 누적 규칙 — NULL의 의미를 지킨다

```
봉 안에서 쓸 수 있는 앵커 틱이 0건       → anchor_buy/anchor_sell = NULL
봉 안에서 디코딩된 체결구분 틱이 0건      → buy_vol_flag/sell_vol_flag = NULL
그 외                                   → 사용 가능한 틱만 합산
```

🔴 `.get(key, 0)` 폴백을 두지 않는다 (`feedback_no_schema_fallback_in_collection`).
**행이 없는 것(NULL)과 0인 것은 다르다.** 451차 `program_*` 유령 피처가 정확히 이
구분을 잃어서 2개월간 안 잡혔다.

**부분 손실은 스스로 드러난다**: 일부 틱이 역행으로 버려지면 그 봉은
`anchor_buy + anchor_sell < volume`이 되고, Phase 2 리포트의 잔차가 그것을 잡는다.
같은 이유로 미분류 틱도 `volume − (buy_vol_flag + sell_vol_flag)`로 정량화되므로
별도 열이 필요 없다. 다만 원인 구분을 위해 역행은 **로그로 남긴다**.

### 3-5. 진단 로그

| 로그 | 빈도 | 내용 |
|---|---|---|
| `[CybosRT-TICK]` (기존) | 100틱마다 | `flag=` 뒤에 `side=`(디코딩 결과) 추가 |
| `[CVD-ANCHOR]` (신설) | 봉 마감마다 1줄 | `vol` / `buy_vol`(현행) / `buy_vol_flag`(섀도) / `anchor_buy` / 잔차 |
| `[CVD-ANCHOR][RESET]` (신설) | 발생 시 | 누적값 역행 — 재접속·세션 리셋 신호 |
| `[CVD-ANCHOR][UNAVAIL]` (신설) | 세션당 1회 | 원천이 22/23을 주지 않음 (가설 반증 시 즉시 알기 위함) |

`[CVD-ANCHOR]` 1줄/분 = 하루 약 385줄. `[BAR-CLOSE]`와 같은 수준이라 부담 없다.

### 3-6. DB 스키마

`raw_candles`에 4열 추가. **DEFAULT 없음 → 기존 88,558행과 미계측 봉은 NULL.**

```sql
anchor_buy    INTEGER    -- 서버 누적체결매수(23) 봉내 증분
anchor_sell   INTEGER    -- 서버 누적체결매도(22) 봉내 증분
buy_vol_flag  INTEGER    -- 체결구분(24) 올바른 파싱 기준 매수량 (섀도)
sell_vol_flag INTEGER    -- 〃 매도량 (섀도)
```

기존 `buy_vol`/`sell_vol` 마이그레이션과 같은 `ALTER TABLE … ADD COLUMN` try/except
패턴을 따른다(`db_utils.py:1353-1358`).

## 5. 검증

### 5-1. 오프라인 (배포 전, 지금 가능)

스텁 COM 객체로 `_handle_tick()`을 직접 구동한다 — 실제 COM 없이 전 경로가 돈다.

| # | 불변식 |
|---|---|
| T1 | `decode_trade_side` 매핑표 (49/50/'1'/'2'/1/2 → BUY/SELL, 그 외 → None) |
| T2 | **정상 흐름**: `anchor_buy+anchor_sell == volume`, `buy_vol_flag+sell_vol_flag == volume` |
| T3 | **발견 A 재현**: 같은 틱열에서 현행 `buy_vol`이 섀도 `buy_vol_flag`보다 크다(보합틱이 매수로 흡수됨) |
| T4 | **원천 미제공**(22/23이 항상 0): anchor 2열 NULL, 섀도 2열은 정상 |
| T5 | **체결구분 미제공**(24가 빈값): 섀도 2열 NULL, anchor 2열은 정상. **0으로 채우지 않음** |
| T6 | **누적값 역행**: 해당 증분 폐기, 기준선 재설정, 이후 틱 정상, `_anchor_reset_count` 증가 |
| T7 | **기존 동작 불변**: 같은 틱열에서 `volume`/`buy_vol`/`sell_vol`/`high`/`low`/`close`가 변경 전과 동일 |
| T8 | DB 왕복: 4열 마이그레이션 후 NULL 저장·판독, 기존 행 NULL 유지 |

### 5-2. 라이브 1일차 (배포 후)

```sql
SELECT COUNT(*)                                        AS bars,
       SUM(anchor_buy IS NULL)                         AS anchor_null,
       SUM(buy_vol_flag IS NULL)                       AS flag_null,
       SUM(anchor_buy + anchor_sell <> volume)         AS anchor_residual_bars,
       SUM(buy_vol_flag + sell_vol_flag <> volume)     AS flag_residual_bars,
       SUM(buy_vol) * 1.0 / SUM(buy_vol + sell_vol)    AS legacy_buy_share,
       SUM(anchor_buy) * 1.0 / SUM(anchor_buy + anchor_sell) AS anchor_buy_share
FROM raw_candles WHERE ts >= '<배포일>';
```

**기대 판정**:

| 지표 | 기대 | 어긋나면 |
|---|---|---|
| `anchor_null` | ≈ 0 | 22/23 미제공 → **가설 반증**. Phase 3·4 재설계 |
| `anchor_residual_bars` | ≈ 0 | 항등식 불성립 → 필드 의미 재확인 |
| `legacy_buy_share` | ≈ 0.63 | 기존 실측 재현 |
| `anchor_buy_share` | **≈ 0.50** | **핵심 판정.** 0.63에 가까우면 편향이 시장 실체이고 발견 A는 틀렸다 |
| `buy_vol_flag` vs `anchor_buy` 괴리 | ≈ 0 | 체결구분 분류 자체의 한계 노출 |

> 이 한 줄 쿼리가 Phase 3 착수 여부를 가른다. `anchor_buy_share`가 0.5 근방이면
> 발견 A가 라이브에서 확정되고, 0.63이면 **내 진단이 틀린 것이므로 Phase 3을 취소**한다.

## 6. 위험과 잔여 문제

| 위험 | 평가 |
