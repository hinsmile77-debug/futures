## 1장. 주기 설계 — 3단 주기 (새 캘린더를 만들지 않는다)

사용자 질문 ①("어떤 주기로 자동생성할지")에 대한 답. CLAUDE.md 317차 원칙
("관리 포인트가 늘수록 '재검토하기로 했는데 안 함'으로 방치된다")에 따라
**기존 주기 2개에 편입하고, 월간만 기존 금요일 체인 안의 조건 분기로 구현**한다.

| 주기 | 트리거 | 내용 | 비용 | 산출물 |
|---|---|---|---|---|
| **주간** | 금요일 EOD 체인 (`campaign_steps.py` 기존 스텝 추가) | L0 건강도 + L4 conf-층화 + 후보 축적 현황판 | 읽기전용, 초 단위 | `featureset_health_YYYYMMDD.md` |
| **월간** | 같은 체인, **매월 첫 금요일 분기** (`today.day <= 7`) | L1 전수 IC 스크리닝 + L1' pending 후보 + L2 비용차감 거래성 → **KEEP/DROP/ADD 제안 리포트** | 읽기전용, 분 단위 | `featureset_proposal_YYYYMMDD.md` |
| **26주** | 기존 WFA 재검증 주기 (사람 세션) | L3 purged CV + L3' ablation 전면 재검증 (07-30 실행계획 2-4 그대로) | **py310_64 재학습** | DECISION_LOG 차수 기록 |

**주기 선정 근거** (사전등록 — 사후에 "주간이 답답하니 매일로" 식 변경 금지):

- **건강도(L0)가 주간인 이유**: 배선 사망은 빨리 잡아야 한다 — exhaustion 6종·
  `macro_nasdaq_chg`가 2개월간 전부 0으로 방치된 실사례. 20거래일 창 읽기전용이라 비용도 없다.
- **제안(L1/L2)이 월간인 이유** 두 가지:
  1. **반복 관측(repeated looks) 부풀림** — 같은 데이터를 매주 다시 검정하면 Bonferroni를
     해도 "언젠가 한 번 유의"가 나올 확률이 누적된다. 월간 + 지속성 규칙(§3-3)으로 통제한다.
  2. **표본 회전 속도** — L1 최소 표본이 MIN_DAYS=20거래일(약 4주)이다. 주간으로 돌려도
     신규 후보의 표본이 늘 미달이라 같은 판정만 반복 출력된다.
- **L3/L3'가 26주인 이유**: py310_64 재학습이 필요해 자동 체인에 넣을 수 없고(30분 타임아웃,
  환경 분리), 07-30 실행계획이 이미 Hurst·PSI와 같은 26주 목록 편입을 설계했다 — 중복 설계 금지.

## 2장. 통계 지표 배터리 — 기존 6층에 "모델정합" 1층 추가

사용자 질문 ②("어떤 통계적 지표로 검증할지")에 대한 답. 07-30 실행계획의 L0~L4를
그대로 계승하고, 피처셋 관점에 필요한 **L5(모델정합)** 하나만 추가한다.

| 층 | 지표 | 판정 기준 (전부 관측 전 고정) | 도구 | 주기 |
|---|---|---|---|---|
| **L0 건강** | 분산=0 / zero·최빈값 비중 | DEAD / ≥95% CRITICAL / ≥80% WARN | `feature_health_report.py` (있음) | 주간 |
| **L1 정보** | **일자단위** Spearman IC(t), hit-rate(중심화 부호일치) | Bonferroni(피처수×호라이즌수) α=0.05, MIN_DAYS=20, MIN_DISTINCT=20 | `core_feature_discovery.py` (있음) | 월간 |
| **L1' 후보** | pending/POOL 후보 동일 검정 | 동일 + split-half 부호 일치 | `ic_probe_pending_features.py` (있음) | 월간 |
| **L2 수익성** | 왕복비용 0.133pt 차감 일평균 pnl(pt), t | t 유의 + 양(+), 비중복 거래, 미래참조 없음(당일 러닝 중앙값 게이트) | `horizon_signal_tradability.py` (**07-30 계획 신설분 — 공유**) | 월간 |
| **L3 모델** | purged WFA CV 3클래스 acc + 방향적중률 (폴드별 병기) | `EOD_MODEL_GUARD_DROP_TOLERANCE` 이상 악화 시 기각 | `validate_feature_set_purged_cv.py` (있음, py310_64) | 26주 / A-B시 |
| **L3' 분해** | 피처별 한계기여(ablation 순계) | 순계·단독 둘 다 병기 (3m poc/bb 사례 방지) | `feature_ablation_purged_cv.py` (있음, py310_64) | 필요 시 |
| **L4 신뢰도** | conf-층화 two-proportion z (경계 0.55) | 07-30 실행계획 2-3 사전등록값 그대로 | `horizon_conf_stratified_test.py` (**07-30 계획 신설분 — 공유**) | 주간 |
| **L5 모델정합** (신설) | 호라이즌별 **SHAP 중요도 × L1 IC 크로스탭** | 아래 2×2 분면 판정 | 월간 리포트 내 합성 (SHAP_DB + L1 결과 join) | 월간 |

**L5를 추가하는 이유**: L0~L4는 "피처에 정보가 있나"와 "모델이 잘 맞히나"를 따로 보지만,
피처셋 최적화 질문은 그 **교차**에 있다. 5m 진단이 실증했다 — `ema_cross` 단독 부호일치율
53.7%(정보 있음)인데 모델과의 일치율 49.7%(모델이 안 씀) = "신호 희석" 병리는 L1도 L4도
단독으로는 못 잡았다.

| | L1 유의 (정보 있음) | L1 비유의 (정보 없음) |
|---|---|---|
| **SHAP 상위 (모델이 씀)** | ✅ 정상 현역 | ⚠️ **DROP 후보** — 잡음을 크게 쓰는 중 (5m `va_bandwidth` 사례) |
| **SHAP 하위 (모델이 안 씀)** | ⚠️ **희석 진단** — 제거 아닌 잡음 제거·재학습 대상 | 무해 — 관찰만 |

**강건성 지표 보강 (신설, 월간 리포트 내)**:
- **롤링 IC 추세**: 최근 120거래일을 4주 단위 롤링 창으로 IC를 재계산해 추세를 병기한다.
  근거: 알파 감쇠는 이 프로젝트의 실측 반복 패턴(`opt_gex_bn` 설계 시점 IC 0.198 → 최신
  0.013, `basis_pt` 소멸)이고, SOP Phase 0이 인용한 Kolm(2023) 감쇠곡선의 실무 적용이다.
  "지금 유의한가"만 보면 감쇠 중인 피처를 늦게 잡는다.
- **표본확대 재검증 자동 추적**: 후보별 최초 유의 시점의 표본수를 레지스트리(§3-3)에 기록하고,
  표본이 2배를 넘긴 월간 리포트에서 자동으로 재검정 결과를 병기한다(SOP Phase 4 "2배 규칙"의
  기계화 — 지금은 사람이 기억해야 한다).

## 3장. 월간 제안 리포트 — KEEP / DROP / ADD (사용자 요구 1번)

### 3-1. 출력 형식 (호라이즌별)

```
## 5m — 피처셋 제안 (2026-09-04)
현행 active: 14개 | 건강: OK 13 / WARN 1 / CRITICAL 0
| 판정 | 피처 | 근거 요약 |
|---|---|---|
| KEEP    | ema_cross      | L1 IC +0.041(t=3.2, Bonf✓) · split ✓ · SHAP 3위 |
| DROP 후보 | macro_vix    | L1 p=0.54 (2회 연속) · SHAP 7위 — L5 ⚠️분면 |
| ADD 후보  | vkospi       | L1' IC +0.077(p<0.0001) 2회 연속 · L2 +0.21pt/일(t=2.1) · 표본 2,900 |
| 보류    | opt_gex_sign   | L1' 유의 1회차 — 지속성 규칙 미충족, 차월 재확인 |
| 📌결정  | basis_pt       | 기각(2026-07-26) — 표본확대 후 소멸, 재검정 금지 |
```

### 3-2. 제안 규칙 (사전등록 — 리포트 코드에 하드코딩, 사후 변경 금지)

| 제안 | 요건 (전부 충족) |
|---|---|
| **DROP 후보** | active 피처가 ① L0 DEAD/CRITICAL, **또는** ② L1 비유의 **2회 연속**(월간 2회=약 2개월) + L5 ⚠️분면 |
| **ADD 후보** | POOL/pending 피처가 ① L0 OK ② L1' Bonferroni 유의 **2회 연속** + split-half 안정 ③ L2 통과(비용차감 양) 또는 게이트로서 해상도 확인 ④ 표본 MIN_DAYS=20 이상 |
| **CORE 피처** | DROP 제안 자체를 출력하지 않는다 — CLAUDE.md §3 교체 불가. 비유의여도 "CORE 경보"로만 표기(사람 판단 회부) |
| **제안의 효력** | **없음.** 제안은 26주 배터리(L3→L3')와 주간회의 수동 승인의 **입력 후보**일 뿐이다. 리포트는 `horizon_feature_sets.json`·registry·pkl 어디에도 쓰지 않는다(§6 자동 통합 금지) |

**"2회 연속" 지속성 규칙의 근거**: 반복 관측 부풀림 통제(§1) + `basis_pt`(소표본 1회 유의
→ 확대 후 소멸) 재발 방지. 1회 유의는 "보류(차월 재확인)"로만 출력한다.

### 3-3. 피처 판정 레지스트리 (신설) — 판정≠결정 분리

CLAUDE.md "검증 캠페인 운영 모드"가 문서화한 사고 — "이행된 권고를 신규 안건으로 오인" /
"기각 결정이 기록 안 돼 재검정 반복" — 는 피처 제안에서 똑같이 재발한다. 월간 리포트가
매달 판정을 재계산하므로, 기각된 `basis_pt`는 **매달 다시 비유의로 뜨고**, 언젠가 우연히
유의로 뜨면 재제안된다. `VALIDATION_CAMPAIGN_DECISIONS`와 동일 패턴으로 막는다.

```python
# config/settings.py (신설) — 확정 결정만 등록. 갱신 시 DECISION_LOG.md 병기 필수.
FEATURE_SET_DECISIONS = {
    "basis_pt": {"decision": "기각", "date": "2026-07-26",
                 "reason": "표본확대(2,953행) 후 전 호라이즌 무정보 — 소표본 우연",
                 "re_eval": None},   # None=재검정 금지, 날짜=그때 재론
    # 예: 조건부채택(섀도 유지) — exhaustion 6종 유형
}
```

리포트는 이 레지스트리 항목을 📌 마커로 렌더링하고 **제안 대상에서 제외**한다.
추가로 각 후보의 `first_significant`(최초 유의 시점 표본수)를 리포트가 JSON 부속 파일에
자동 누적해 §2의 "2배 규칙" 추적에 쓴다(이건 결정이 아니라 관측 캐시이므로 코드가 써도 됨
— 단 `docs/정기점검/` 커밋 대상 밖, `data/`에 둔다).

## 4장. 개선 피처셋 손익 분석 (사용자 요구 2번) — 정직한 3단 근사

"개선 피처셋을 도입하면 손익이 얼마나 좋아지는가"에 **단일 숫자로 답하는 것은 불가능**하고,
시도하면 자기기만이 된다(394차: 189회 검정 중 비용차감 생존 0개 — IC와 손익은 다른 질문).
리포트는 아래 3단을 **구분해 병기**하고, 어느 단까지 통과했는지를 명시한다.

| 단계 | 무엇을 재나 | 방법 | 시점 |
|---|---|---|---|
| **P1 신호 거래성** | 피처 단독이 비용을 넘나 | L2: 왕복 0.133pt 차감, 비중복, 전·후반 분할 → **pt/일 ± t** | 월간 (제안 시 자동) |
| **P2 오프라인 세트 A/B** | OLD vs NEW 피처셋의 모델 성능 차 | L3 purged CV 방향적중률 델타 + OOS 폴드에서 비용차감 모의 pnl 병기 (폴드별) | 승인 후보 확정 시 (사람 세션, py310_64) |
| **P3 온라인 섀도 A/B** | 라이브 분포에서 재현되나 | 07-30 실행계획 4-2: 섀도 pkl 병행학습, 점수만 기록, 부트스트랩 우위확률 ≥0.95 + Bonferroni, 최소 100건·20거래일 | P2 통과 후 선택적 |
| **실손익** | 진짜 답 | 배포 후 L4 주간 감시 + `entry_horizon`별 실현손익 (주간 캠페인 리포트 기존 채널) | 배포 후 |

월간 리포트의 ADD/DROP 후보 행에는 P1 수치가 자동으로 붙는다. P2·P3는 자동 체인이
아니라 **승인된 후보에 대해서만** 사람이 착수한다 — 모든 후보에 P2를 자동으로 돌리면
py310_64 재학습이 월간 체인에 들어와 07-30 실행계획의 주기 설계를 깨고, 다중비교도
통제 불능이 된다.

## 5장. 신규 알파 발굴 파이프라인 (사용자 요구 3번) — 반자동이 상한이다

### 5-1. 완전 자동화가 불가능한 구조적 이유 (먼저 명시)

1. **raw_features는 계산 모듈이 있어야 쌓인다** — FeatureBuilder가 계산한 dict만 저장되므로
   (`피처_데이터_3계층_구분.md` §②), "발굴 → 축적" 사이에는 반드시 **코드 구현**(계산 모듈
   신설 + POOL 등록 커밋)이 있다. 이것은 사람 세션의 일이다.
2. **데이터 취득 가능성은 실계정 프로브로만 확정된다** — `cancel_ratio` 함정(SOP Phase 1).
   웹에서 아무리 좋은 피처를 찾아도 Cybos TR로 원천을 못 받으면 구현불가다.
3. **POOL 등록은 git 커밋** — 자동 스크립트가 `constants.py`를 편집하는 것은 §6 정신에
   반한다(POOL은 active가 아니지만, "검증 스크립트는 로그만 쓴다"는 SOP 읽기전용 원칙 위반).
4. **발굴 품질은 판단 노동이다** — SOP Phase 0이 요구하는 산출물은 URL 목록이 아니라
   "계산식 + 원천 데이터 + 이론적 근거 + 예상 부호"의 후보 명세다. 스크래핑으로 안 나온다.

### 5-2. 운영 설계 — 발굴 세션(사람+Claude) / 현황판(자동)

```
[자동] 주간 현황판(§6-1)이 후보 파이프라인 재고를 집계
   후보 재고 = (축적중 + 검증중 + 보류) 상태의 POOL 피처 수
   재고 < 3 이면 리포트에 "🔍 발굴 세션 권고" 줄 출력   ← 캘린더가 아니라 재고 트리거
   ↓
[사람+Claude 세션] 알파 발굴 세션 (WebSearch/문헌 — 트레이딩 런타임 밖에서)
   입력: 발굴 런북(§5-3) + 최신 월간 리포트(어느 호라이즌이 빈약한지)
   산출: 후보 명세 md (SOP Phase 0 형식) → docs/Spec for feature/후보명세/
   ↓
[사용자 승인] 명세 검토 — 여기서 기각되면 명세 md에 사유 기록 후 종료
   ↓
[사람 세션] SOP Phase 1 — 프로브로 실취득 확정 → 계산 모듈 구현 → POOL 등록 커밋
   ↓
[자동] raw_features 매분 축적 → 주간 현황판이 "축적중 D+n/20" 표시
   → MIN_DAYS 도달 시 월간 L1' 스크리닝에 자동 편입 → 이후 §3 제안 경로
```

**웹 스크래핑을 런타임 스크립트로 만들지 않는 이유**: py37_32 런타임에 스크래핑 의존성을
넣는 것은 안정성 리스크만 추가하고(400차 크래시 교훈 — 연속 수정 금지), 발굴의 병목은
접근이 아니라 선별이다. Claude 세션의 WebSearch가 이미 그 역할이며, 세션 산출물이
명세 md로 남으므로 추적 가능성도 더 좋다.

### 5-3. 발굴 런북 (신설 문서 `docs/Spec for feature/알파발굴_런북.md`)

세션마다 재현 가능하도록 고정한다: ① 탐색원(arXiv q-fin·SSRN·JFE/JFQA 계열 + 실무 블로그,
KOSPI200 선물/지수선물 미시구조 우선) ② 검색 축(호라이즌별 약점 병리 기준 — 예: 5m 신호
희석이면 "feature selection noise dilution", 15m 무스킬이면 중기 예측력 문헌)
③ 산출 형식(SOP Phase 0 후보 명세 그대로) ④ 제외 목록(FEATURE_SET_DECISIONS 기각분 +
`constants.py` 사장 처리 주석 — 같은 아이디어 재발굴 방지) ⑤ 세션당 후보 상한 3개
(한 번에 많이 등록하면 축적·검증이 병목이라 명부만 비대해진다 — POOL은 이미 수십 개다).

#### 구현 중 확정한 사항 4가지 (계획 대비 변경 — 근거 포함)

1. **파일명은 `featureset_health_report_YYYYMMDD.md` / `..._metrics_....json`.**
   계획 초안의 `featureset_health_YYYYMMDD.md`가 아니다. `campaign_report_paths.py`가
   `<stem>_(report|metrics)_YYYYMMDD.(md|json)` 형태만 FIFO·`latest()` 대상으로 인식하므로,
   규약을 따르지 않으면 보관정리와 경로조회를 이 계열만 따로 만들어야 한다.
2. **`campaign_report_paths.py`에 `stem` 인자를 추가**해 계열을 분리했다(기본값이
   `validation_campaign`이라 기존 호출부 3곳은 무변경). **FIFO는 stem별로 따로 센다** —
   같은 폴더에서 한 카운터를 공유하면 새 계열이 끼어들어 주간 검증 리포트를 조기 삭제한다.
   샌드박스에서 계열 격리·수동 스냅샷 보존·`latest()` 분리를 실측 검증했다.
3. **§2-b "전체 `raw_features` 신규 이상" 절을 추가**했다(계획에 없던 것). 계획대로 배포
   피처셋만 보면 이 리포트가 수동 `feature_health_report.py`보다 **덜 보는** 도구가 된다 —
   실측에서 수동 도구는 신규 이상 8건(`bear_reversal_signal`·`microprice`·
   `macro_vix_abs`·exhaustion_shadow 2종 등)을 잡는데, 그 8건 전부가 배포 피처가 아니라
   호라이즌 관점 표에는 한 줄도 뜨지 않았다. 소진 6종 2개월 방치가 정확히 이 사각지대다.
4. **§1에 `실이상` 열을 추가**했다. `is_*`/`quality_*`처럼 "항상 같은 값이 정상"인
   상태플래그가 CRITICAL/WARN 열을 채워(첫 실행에서 `is_close_volatile` 97.8% 등) 경보
   피로를 만들었다. `실이상`은 DEAD·CRITICAL·raw부재 중 KNOWN도 상태플래그도 아닌 것만
   센다 — `feature_health_report.py`의 "신규 이상"과 같은 정의다.

부수 수정: `scripts/feature_health_report.py`가 Windows 기본 콘솔(cp949)에서 `—`(U+2014)
출력 시 `UnicodeEncodeError`로 죽어 **수동 실행 자체가 불가능**했다(리다이렉트 없이는
이 도구를 쓸 수 없었다는 뜻). 다른 리포트 스크립트와 같은 stdout/stderr utf-8 재설정
가드를 넣어 수정. 이 도구가 본 리포트의 판정 단일 출처라 교차대조를 위해 필요했다.
