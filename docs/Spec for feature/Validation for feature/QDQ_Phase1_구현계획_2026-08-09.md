## 1. 무엇이 고장났나

`main.py:11317-11326` — 파이프라인이 멎으면 DB의 마지막 봉을 읽어 재처리한다.

```python
bar = {
    "ts": ts, "open": ..., "high": ..., "low": ..., "close": ...,
    "volume":   int(row["volume"] or 0),
    "buy_vol":  0,        # ← 하드코딩
    "sell_vol": 0,        # ← 하드코딩
}                          # ← bid1 / ask1 / oi 는 키 자체가 없다
self.run_minute_pipeline(bar)
```

이 bar가 파이프라인을 타고 `save_candle_and_features()` → `INSERT OR REPLACE`에
도달하면서, **읽어온 그 행을 열등한 값으로 덮어쓴다.**

```
읽기 전:  volume=308  buy_vol=193  sell_vol=115  bid1=969.82  ask1=969.98  oi=93197
쓰기 후:  volume=308  buy_vol=0    sell_vol=0    bid1=NULL    ask1=NULL    oi=NULL
```

`db_utils.py:1494`의 `candle.get("buy_vol", 0)`이 두 번째 방아쇠다 — 키가 없어도
0을 만들어 준다.

### 실측 피해

라이브 틱 개시(2026-06-08) 이후 16,270봉 중 **55봉**.

```
06-25 16봉 · 07-31 13봉 · 08-04 15봉 · 그 외 9일 각 1봉
```

비율은 0.34%로 작지만 **파이프라인이 멎을 만큼 험했던 날에 집중**된다 —
피처 품질이 가장 중요한 순간이다. 그리고 그 봉들은 마스킹 없이 하류로 흘러간다.

**원본은 소실됐다. 과거 55봉은 복구 불가**이며, 이 Phase는 재발만 막는다.

### 왜 세 번째인가

`feedback_no_schema_fallback_in_collection`(451차)의 세 번째 재발이다.

| # | 위치 | 형태 |
|---|---|---|
| 1 | `investor_data.py` (451차 폐기) | `nets.get(key, 0)` → `program_*` 상수 0 |
| 2 | `aggregate_and_backfill.py:187` | `"buy_vol": 0` 하드코딩 |
| 3 | `main.py:11325` | `"buy_vol": 0` 하드코딩 **+ 원본 파괴** |

세 번 같은 방식으로 당했으므로, **한 번 더 안 당할 구조**로 고치는 것이 이 Phase의
진짜 목표다(§2-1).

## 2. 설계

### 2-1. 🔴 핵심 — 열 목록을 손으로 적지 않는다

가장 중요한 결정이다. 복구 bar를 이렇게 만들지 **않는다**:

```python
bar = {"ts": ..., "open": ..., ..., "buy_vol": row["buy_vol"], ...}   # ✗
```

이러면 **다음에 raw_candles에 열이 추가될 때 또 조용히 누락된다.** Phase 0이 방금
4열을 추가했고, Phase 4가 더 추가할 예정이다. 네 번째 재발이 예약돼 있는 셈이다.

대신 **행이 가진 열을 그대로 순회**한다.

```python
def _bar_from_raw_candle_row(row):
    """sqlite3.Row → 파이프라인 bar dict. 열 목록을 하드코딩하지 않는다."""
    for key in row.keys():           # ← 스키마가 커지면 자동으로 따라온다
        ...
```

### 2-2. NULL은 키를 만들지 않는다

| DB 값 | bar dict | 이유 |
|---|---|---|
| 실측값 | 그대로 실음 | — |
| **NULL** | **키 자체를 넣지 않음** | `None`을 실으면 `bar_aggregator.py:70`의 `sum(b.get("buy_vol", 0))`이 `TypeError`로 죽는다. 키가 없으면 `.get(…, 0)`이 0을 주고, `feature_builder.py:184`의 `.get("buy_vol")`은 `None`을 받아 **가격기반 프록시 경로**로 정상 분기한다 |
| `created_at` | 제외 | DB가 자동 생성 |
| `ts` | `datetime`으로 파싱 | 파이프라인 규약 |

### 2-3. 복구 봉에 표식을 남긴다 — 단, 피처가 아니라 DB 열로

`raw_candles.bar_recovered` 신설.

```
NULL — 452차 이전 행 (이 열 도입 전)
0    — 정상 실시간 경로
1    — 복구 재처리 봉
```

> **상위 계획서의 1-4에서 의도적으로 벗어난다.** 원안은 "피처에 실어 하류가 구분
> 가능하게"였으나, 신규 피처 키는 **99.7%가 0인 상수**가 되어
> `scripts/feature_health_report.py`가 즉시 `DEAD`/`CRITICAL`로 잡는다. 이 프로젝트가
> 세 번이나 싸운 **유령 피처를 스스로 하나 만드는 꼴**이다.
> "이 봉이 재처리됐다"는 것은 신호가 아니라 **봉의 내력(provenance)** 이므로 DB 열이
> 맞는 자리다. 라이브 마스킹은 Phase 3에서 소비 설계와 함께 다룬다.

`bar_recovered`는 측정값이 아니라 **기록자가 항상 아는 플래그**다. 따라서
`int(bool(...))`로 0을 쓰는 것은 §2-2의 "NULL 원칙" 위반이 아니다 — 그 원칙은
*원천이 안 준 측정값*을 0으로 위장하지 말라는 것이다.

### 2-4. 저장 계층 방어선

`db_utils.py`의 `.get("buy_vol", 0)` → `.get("buy_vol")`.

§2-1이 원인을 막으므로 이건 2차 방어선이다. 앞으로 어떤 호출자가 키를 빠뜨리면
DB에 **"모른다(NULL)"** 가 남는다 — 지금처럼 "매수 0계약이었다"는 거짓말이 아니라.

**NULL 판독 안전성 확인 완료**:
- `scripts/exhaustion_restore_replay.py:153` — `if bvol is not None` 분기 있음 ✅
- `utils/db_utils.py:fetch_recent_raw_candles` — buy_vol 미조회 ✅
- `scripts/aggregate_and_backfill.py` — 미조회(§2-5에서 조회하며 None 처리 동반) ✅
- 그 외 `raw_candles.buy_vol` 판독처 없음 (전수 grep)

### 2-5. 백필 스크립트의 같은 안티패턴 (재발 #2)

`scripts/aggregate_and_backfill.py`는 `raw_candles`에서 buy_vol/sell_vol을
**조회조차 하지 않고** 0을 넣는다(`:187`).

> ⚠️ **초안 정정.** 이 문서 초안은 그 0이 `cvd_direction` 재계산을 막아
> `raw_features_horizon` 23,276행을 틀리게 만들었다고 적었다. **틀렸다.**
> 이 스크립트는 **자체 `override_horizon_features()`**(`:53-73`)를 갖고 있고, 그 함수는
> `atr`/`bar_volume`/`ret_Nm` 세 개만 덮어쓴다 — buy_vol/sell_vol을 **아예 소비하지
> 않는다.** 따라서 0 하드코딩이 산출물을 직접 오염시킨 적은 없다.

**대신 더 중요한 것이 드러났다 — 백필과 라이브가 다른 함수를 쓴다.**

| 경로 | 사용 함수 | `cvd_direction` |
|---|---|---|
| 라이브 (`main.py` Phase 2) | `features/feature_builder.py:838` | **N분봉 buy/sell로 재계산** |
| 백필 (이 스크립트) | 자체 로컬 함수 `:53` | 1분봉 값 그대로 |

호라이즌 모델의 **학습행과 추론행이 같은 이름의 피처를 다르게 채우고 있다**
(train/serve 불일치). 다만 이건 데이터 파괴가 아니고, 고치면 학습 데이터 의미가
바뀌므로 **Phase 1 범위 밖 — NEXT_TODO 별건 등록**.

수정 범위(이번): 거짓값만 없앤다. 실측값을 조회해 그대로 쓰고, NULL인 구간
(2026-06-08 이전)은 **1분봉마다** 바 기하학 프록시로 채운다 —
`feature_builder.py:190-192` 및 `exhaustion_restore_replay.py:157-159`와 **같은 공식**.
지금은 소비처가 없지만, 위 두 함수를 정렬하는 순간 바로 밟게 될 지뢰를 미리 없애는
것이다.

```
buy  = vol × (close − low)  / (high − low)
sell = vol × (high − close) / (high − low)
```

N분봉 집계 후 한 번 계산하지 않고 **1분봉마다 계산해 합산**한다 — 라이브
(분당 귀속의 합)와 같은 의미가 되게 하기 위함이다. 프록시 사용 봉 수를 로그에 찍는다.
