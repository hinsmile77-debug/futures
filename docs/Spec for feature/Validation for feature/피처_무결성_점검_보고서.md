# 피처 데이터 무결성 점검 체계 보고서

**대상 환경**: 대신 CYBOS Plus / CREON Plus (32비트 로컬 수집) · KOSPI200 선물·옵션 · 분봉/틱·호가
**범위**: 전체 ML 피처의 무결성 점검 프레임워크
**작성일**: 2026-08-09

## 0. 요약

말씀주신 3단계 프레임워크는 뼈대로 타당해서 대부분 그대로 채택했습니다. 다만 두 가지를 다르게 구현했고, 하나를 새로 추가했습니다.

| 구분 | 내용 |
|---|---|
| **그대로 채택** | 장중 실시간 감시(타임스탬프 연속성·하트비트·Zero/NaN 차단) · EOD 공식 분봉 대사 · 피처 수학적 한계 점검 |
| **다르게 구현 ①** | "거래량 오차 0.1% 이하" → **오차의 크기·부호·집중도 3축**으로 분리. 크레온에서는 거래량이 맞아도 CVD가 틀리는 구조적 사각지대가 있습니다 (§2) |
| **다르게 구현 ②** | "Hurst는 0~1을 벗어나면 버그" → **이론값 경계와 추정량 경계를 분리**. R/S 추정량은 정상적으로 1을 넘습니다 (§3.1) |
| **새로 추가** | 피처마다 점검 코드를 짜지 않고 **계약서(Contract)를 선언하면 점검이 자동 생성**되는 엔진. CVD·Hurst는 이 틀의 두 사례일 뿐입니다 (§3) |
| **구현 현황** | 체크 71개(게이팅 50개) · 자체 검증 183건 전량 통과 · 3초 판독 대시보드 탭 |

## 1. 크레온/사이보스 환경 검토 결과

공식 문서에서 확인한 제약입니다. 점검 임계치는 전부 이 숫자에서 역산했습니다.

| 항목 | 실측 사양 | 점검 항목 |
|---|---|---|
| 프로세스 | Plus API가 32bit COM → **파이썬도 32비트 필수** | `CREON.MEMORY` (2GB 벽) |
| 시세 요청 | **15초당 60건** (초과 시 대기) | `CREON.REQUEST_QUOTA` |
| 주문 요청 | **15초당 20건** (초과 시 함수가 4 반환) | 〃 |
| 실시간 구독 | **최대 400건** (초과 시 오류) | `CREON.SUBSCRIBE_SLOTS` |
| 상태 API | `CpCybos.IsConnect`, `ServerType`, `GetLimitRemainCount(LT_*)`, `LimitRequestRemainTime`, `OnDisConnect` | `CREON.CONNECT` |
| 분봉 조회 | `CpSysDib.FutOptChart` — 차트구분 `'m'`, 주기 `1` → 1분봉 (미결제약정 포함) | `RECON.*` |
| 파생 실시간 | `DsCbo1.FutureCurOnly` | 아래 참조 |

### 1.1 실무에서 가장 중요한 발견 — FutureCurOnly는 체결수량을 주지 않습니다

`FutureCurOnly`가 제공하는 필드는 다음과 같습니다.

```
1-현재가  13-누적거래량  14-미결제약정  15-시각
18~21-최우선 매도/매수 호가·잔량
22-누적체결매도  23-누적체결매수  24-체결구분
```

**체결가·체결수량 필드가 없습니다.** 따라서 틱 볼륨은 `누적거래량(13).diff()` 로 만들 수밖에 없는데, 여기에 함정이 있습니다.

> **비유**: 수도 계량기만 보고 있는 상황.
> 검침을 몇 번 건너뛰어도 **총 사용량은 정확히 맞습니다.** 계량기가 누적이니까요.
> 하지만 "언제 얼마나 썼는지"는 검침 간격이 벌어질수록 뭉개집니다.

큐 적체나 재접속으로 이벤트를 놓치면:

1. 다음 이벤트의 차분이 **놓친 물량을 통째로 흡수**합니다 → 거래량 총량은 그대로 맞습니다
2. 그런데 그 물량 전체가 **다음 틱의 체결구분(24)으로 잘못 분류**됩니다 → CVD만 틀립니다

즉, 제안하신 "거래량 오차 0.1% 이하 확인"은 **이 사고를 통과시킵니다.** 크레온 환경에서는 예외 상황이 아니라 기본 동작입니다.

### 1.2 실제 재현 결과

09:47~09:50 구간 이벤트 70%를 드롭한 시나리오를 돌린 실측입니다.

```
RECON.VOLUME_BIAS  → PASS   총 거래량 오차 0.0000% (자체 93,601 vs 공식 93,601)
RECON.OHLC_DIFF    → WARN   종가·시가 일치, 고가·저가만 불일치 → 봉 내부 틱 유실 패턴
CONTRACT.ANCHOR    → FAIL   앵커 대비 최대 괴리 45.30%, 이탈 3/404봉
```

거래량 대사는 완벽히 통과하고, 고가·저가 불일치가 힌트를 주며, **앵커 대조만이 사고 지점을 정확히 3개 봉으로 특정**합니다.

### 1.3 해법 — 서버가 정답지를 준다

다행히 `누적체결매수(23)` / `누적체결매도(22)` 가 제공됩니다. 내가 체결구분으로 분류해 쌓은 CVD를 이 값과 대조하면 분류 로직 버그와 이벤트 유실을 한 번에 잡습니다.

```yaml
cvd_cum:
  anchor: "cum_buy - cum_sell"     # 서버가 주는 정답지
  anchor_scale: "cum_volume"
  anchor_diff: true                # 반드시 증분 비교
```

`anchor_diff: true`가 중요합니다. 누적끼리 비교하면 오전에 생긴 오차가 오후에는 누적거래량으로 나눠지면서 작아 보입니다. 초기 구현에서 이 문제로 오후 사고를 놓쳤고, 증분 비교로 바꾼 뒤 정상 탐지됩니다.

### 1.4 구독 슬롯 400개 — 조용히 비어버리는 종목

옵션 체인 하나(행사가 40 × 콜/풋)를 체결+호가로 구독하면 그것만 160슬롯입니다. 만기 2개면 320슬롯. 여기에 선물 몇 개만 얹으면 한도를 넘습니다.

문제는 **구독 등록만 실패하고 프로그램은 멀쩡히 돌아간다**는 점입니다. `CREON.SUBSCRIBE_SLOTS`는 소진율뿐 아니라 **"구독 요청한 종목 vs 실제 이벤트가 들어오는 종목"**을 대조해서, 등록에 실패한 종목을 즉시 잡아냅니다. 이걸 안 보면 "왜 이 옵션만 데이터가 없지?"를 몇 주 뒤에 알게 됩니다.

## 2. 제안하신 3단계 프레임워크 검토

### 2.1 1단계 — 장중 실시간 모니터링 ✅ 채택 (+ 크레온 항목 추가)

| 제안 항목 | 반영 |
|---|---|
| 타임스탬프 연속성 검사 | `BAR.GRID_COMPLETE` — 세션 캘린더 기준 기대 봉 수 대비 결측률. 추가로 `CREON.TICK_CONTINUITY`로 **누적거래량 역행·비정상 증분**을 봅니다 (역행 = 재접속·세션 리셋 신호) |
| 하트비트 로깅 | `CREON.HEARTBEAT` — 결번 횟수 + 최신성. 말씀대로 **메인 스레드와 별개 스레드**에서 기록해야 합니다. 메인이 멈추면 하트비트도 같이 멈춰서 아무것도 못 알려주니까요 |
| 메모리 모니터링 | `CREON.MEMORY` — 레벨뿐 아니라 **증가 기울기(MB/h)**를 봅니다. 크레온 장애는 에러가 아니라 조용한 정지라서, "임계 도달까지 0.9시간" 같은 예보가 훨씬 유용합니다 |
| Zero/NaN 실시간 차단 | `CREON.ZERO_VALUE` — 오염 봉의 타임스탬프를 결과에 담아 반환. `blocked_timestamps()` 헬퍼로 전략 코드에서 `signal.loc[block] = 0` 한 줄로 차단 |
| — | (추가) `CREON.QUEUE_DEPTH` · `CREON.SUBSCRIBE_SLOTS` · `CREON.REQUEST_QUOTA` · `CREON.CONNECT` |

**한 가지 보완**: 결측을 `0`이나 `ffill`로 메우지 마십시오. `ffill`은 스테일 가격을 정상 데이터로 위장시켜 `BAR.STALE_PRICE` 점검까지 무력화합니다. NaN으로 남기고 그 시점 피처를 마스킹하는 편이 안전합니다.

### 2.2 2단계 — EOD 교차 검증 ✅ 채택 (판정 방식 변경)

`FutOptChart` 조회 → 대조 → 확정 흐름은 그대로입니다. 다만 **"거래량 오차 0.1% 이하"** 단일 조건은 세 축으로 나눴습니다.

> **비유**: 가계부와 은행 거래내역서 대조.
> 총액만 맞춰보면 "얼추 맞네" 하고 넘어갑니다. 제대로 하려면 세 가지를 봐야 합니다.

| 축 | 무엇을 알려주는가 |
|---|---|
| **① 크기** `\|Σ자체 − Σ공식\| / Σ공식` | 전체 규모 |
| **② 부호 편향** 불일치 봉 중 '자체 < 공식' 비율 | **1.0에 가까우면 틱 유실**, 0에 가까우면 중복 집계. 원인이 정반대입니다 |
| **③ 집중도** 불일치가 몇 %의 봉에서 발생했나 | 0.05%가 하루에 고르게 퍼진 것과 3개 봉에 몰린 것은 완전히 다른 사고입니다 |

여기에 **`RECON.OHLC_DIFF`(항목별 불일치율)** 를 추가했습니다. 종가는 마지막 틱만 맞으면 맞지만, **고가·저가는 틱 하나만 놓쳐도 틀립니다.** 그래서 "종가 일치 + 고저가 불일치" 패턴이 나오면 봉 내부 틱 유실이라고 바로 진단할 수 있습니다.

**확정(Commit) 정책 — 덮어쓰기에 대한 단서**

말씀하신 "오차가 크면 공식 데이터로 덮어쓰기"에 두 가지를 덧붙였습니다.

1. **자체 조립본을 지우지 말고 `_raw` 테이블에 보존**하십시오. 두 버전이 다 있어야 "그날 왜 유실됐나"를 추적할 수 있습니다.
2. **덮어쓰기는 OHLCV 복구이지 피처 복구가 아닙니다.** `FutOptChart`는 OHLCV·미결제약정까지만 줍니다. 체결구분별 물량은 안 줍니다. 따라서 **CVD 등 틱 기반 피처는 복원 불가이고, 해당 구간은 마스킹**해야 합니다.

`commit_decision()` 이 이 판정을 자동으로 내리고, 마스킹할 타임스탬프 목록을 함께 반환합니다.

```
COMMIT            대사 통과 → 자체 조립본 확정
COMMIT_WITH_MASK  경미한 불일치 → 확정하되 해당 구간 피처 마스킹
OVERWRITE         공식 데이터로 OHLCV 덮어쓰기 + 틱 기반 피처 마스킹
```

### 2.3 3단계 — 피처 수학적 검증 ✅ 채택 (일반화)

여기가 가장 크게 바꾼 부분입니다. **개별 점검을 프레임워크로 승격**시켰습니다 (§3).

말씀하신 두 항목에 대한 기술적 보완만 먼저 적습니다.

**CVD**: `|CVD_1min| ≤ Volume_1min` 은 맞지만 **약한 조건**입니다.

```
매수 60 / 매도 30 / 총 100  →  |60−30| = 30 ≤ 100  ✅ 통과
```

10이 증발했는데 통과합니다. 분류 로직 버그는 대개 이 형태로 나타나므로 **항등식**이 필요합니다.

```
buy_volume + sell_volume == volume    ← 이게 진짜 검증
cvd_1m == buy_volume - sell_volume
```

실제 데모에서 매도량을 30% 깎았을 때 부등식은 통과하고 항등식만 잡아냈습니다.

**Hurst**: "0~1을 벗어나면 버그"는 절반만 맞습니다. 구분이 필요합니다.

| | |
|---|---|
| **이론값** H | 정의상 (0, 1) 구간의 파라미터 |
| **추정량** (R/S, DFA) | 유한 표본에서 이 구간을 **정상적으로 벗어납니다.** 짧은 윈도우 + 강한 추세면 R/S 추정치가 1을 넘는 일이 생깁니다 |

"1.05가 찍혔으니 무조건 버그"로 처리하면 오탐이 계속 나고, 오탐이 반복되면 **일주일 안에 아무도 알림을 안 봅니다.** 그래서 3단계로 나눴습니다.

```
NaN / inf                    → 즉시 FAIL   (분모 0, 상수 구간, log(0))
[-0.1, 1.1] 밖               → FAIL        (추정량으로도 설명 안 되는 값)
(0, 1) 밖이지만 위 범위 안    → WARN        (윈도우·추세 효과 가능성)
```

그리고 말씀하신 진짜 원인 — **윈도우 내 가격 변동이 0** — 을 별도 축(`정의구간`)으로 직접 진단합니다. NaN이 났을 때 "분모≈0이 원인 13건 / 원인불명 0건"처럼 원인을 분해해서 보여줍니다. 원인불명 NaN이 더 위험합니다.

**정규화**: 범위 이탈률만 보면 함정이 있습니다. **클리핑을 걸어두면 이탈률은 영원히 0**이 됩니다. 문제가 사라진 게 아니라 보이지 않게 된 것뿐입니다. 그래서 **클리핑 포화율**(경계값에 딱 붙은 비율)을 같이 봅니다.

> **비유**: 최고 눈금 100kg짜리 저울. 120kg인 사람이 올라가도 100으로 찍힙니다.
> 저울은 고장 나지 않았지만, 그 측정값으로는 아무 판단도 할 수 없습니다.

실제로 이 점검이 데모의 `ret_z` 설계 결함을 잡아냈습니다. z-score를 그대로 ±1로 클리핑하면 **1σ 밖(정규분포 기준 약 32%)이 전부 경계에 눌립니다.** 포화율 24.8%로 검출됐고, 3σ로 나눈 뒤 클리핑하도록 고쳤습니다.

## 3. 본론 — 전체 피처를 대상으로 하는 범용 프레임워크

### 3.1 문제: 피처별 점검 코드는 확장되지 않는다

CVD 점검 함수, Hurst 점검 함수를 각각 짜면 피처 100개일 때 점검 코드도 100개가 됩니다. 그러면 **새 피처가 추가될 때 점검이 빠지고, 빠진 줄도 모릅니다.**

가장 위험한 피처는 임계치를 넘은 피처가 아니라 **아무도 점검을 안 짜둔 피처**입니다. 그건 영원히 통과합니다.

### 3.2 해법: 피처가 스스로 자기 성질을 선언한다

> **비유**: 식품 영양성분표.
> 제품마다 검사 방법을 새로 발명하지 않습니다. 성분표 양식이 정해져 있고, 검사는 그 양식의 항목을 확인할 뿐입니다. 새 제품이 나와도 검사 체계는 그대로입니다.

**피처 무결성의 7개 축** — 어떤 피처든 이 7가지로 환원됩니다.

| 축 | 무엇을 선언하나 | 예시 |
|---|---|---|
| **① 치역** | 값이 있을 수 있는 구간. **이론 경계와 절대 경계를 분리** | RSI `[0,100]` (절대) · Hurst `(0,1)` 이론 / `[-0.1,1.1]` 절대 |
| **② 불변식** | 항상 참이어야 하는 등식·부등식. **가장 강력한 축** | `buy+sell == volume` · `\|obi\| <= 1` |
| **③ 정의구간** | 계산이 성립하지 않는 조건 (분모 0, log 음수, 표본 부족) | RSI의 `loss_ma_14` · Hurst의 `rolling_std_64` |
| **④ 인과성** | 계산에 미래 데이터가 들어갔는가 | `lookback: 64` · 타깃만 `allow_forward: true` |
| **⑤ 앵커** | 외부에 정답지가 있는가. 있으면 '말이 되는지' 대신 **'맞는지'** 를 본다 | `cum_buy - cum_sell` |
| **⑥ 위생** | 결측·inf·상수화·워밍업 | `null_fail: 0.05` · `warmup: 64` |
| **⑦ 안정성** | 분포 드리프트·스케일러 고정·재현성 | `psi_fail: 0.25` · `stationary: false` |

**CVD와 Hurst는 이 틀의 두 사례일 뿐입니다.**

- CVD → ② 불변식 + ⑤ 앵커가 강한 피처
- Hurst → ① 치역 + ③ 정의구간이 강한 피처
- RSI → ① + ③
- OBI → ① + ② + ③
- 정규화 피처 → ① + ⑥(고유값 = 포화 탐지)

같은 틀로 IV·베이시스·롤링 상관·임베딩 무엇이든 채울 수 있습니다.

### 3.3 실제 사용법

계약서(YAML)에 선언하면 점검이 **자동 생성**됩니다. 점검 코드는 피처 이름을 하나도 모릅니다.

```yaml
hurst_64:
  desc: 64봉 Hurst 지수 (R/S 추정)
  lo: 0.0                        # ① 이론 경계 → 벗어나면 경고
  hi: 1.0
  soft_lo: -0.1                  #   절대 경계 → 벗어나면 실패
  soft_hi: 1.1
  denominator: "rolling_std_64"  # ③ 이게 0이면 계산 불가
  lookback: 64                   # ④ 과거 64봉만 참조
  warmup: 64
  null_warn: 0.02
  null_fail: 0.08

cvd_cum:
  invariants:                    # ②
    - "abs(cvd_cum) <= cum_volume"
  anchor: "cum_buy - cum_sell"   # ⑤ 서버 정답지
  anchor_scale: "cum_volume"
  anchor_diff: true
  anchor_warn: 0.005
  anchor_fail: 0.02
```

**새 피처를 추가할 때 코드가 아니라 계약서에 8줄을 씁니다.**

### 3.4 자기 점검 — 계약 커버리지

`CONTRACT.COVERAGE` 가 두 가지를 감시합니다.

1. **계약서가 없는 피처** — 한 개라도 있으면 경고
2. **축이 빈약한 계약** — 7축 중 3개 이하만 채운 계약

데모에서 `new_alpha_v2` 라는 피처를 슬쩍 추가했더니(내부에 미래참조까지 포함) 즉시 검출됐습니다. 실무에서 가장 흔한 사고 유형입니다 — 누가 피처 하나 추가했는데 아무도 모르는 상황.

### 3.5 검증 결과

15개 피처(수익률·변동성·RSI·VWAP괴리·CVD·누적CVD·OBI·스프레드·Hurst·베이시스·IV·OI변화·정규화 2종·타깃)에 계약을 채우고 5종 사고를 주입했습니다.

| RSI 분모 0 (강한 상승 구간) | ③ 정의구간 — "분모≈0이 원인 13건" · ⑥ 위생 — inf 13건 |
| 체결 분류 버그 (매도량 30% 누락) | ② 불변식 — **부등식은 통과, 항등식만 위반** |

## 4. 대시보드 — 3초 판독 설계

기존 대시보드에 **"데이터 무결성" 탭**으로 붙입니다.

### 4.1 시선의 순서를 시간으로 설계

> **비유**: 비행기 조종석의 계기 배치.
> 고도계를 제일 크게, 정중앙에 둡니다. 조종사는 평소 0.5초씩 훑고, 이상할 때만 시선을 내립니다.

| 시간 | 요소 | 답하는 질문 |
|---|---|---|
| **0.5초** | 탭 라벨의 상태 점(●▲■) | 다른 탭을 보고 있어도 **이상이 있는가** |
| **1초** | 히어로 판정 (초대형) | **매매 가능인가 차단인가, 그리고 왜** |
| **2초** | 파이프라인 4칩 (수신→조립→대사→피처) | **어느 단계에서** 깨졌나 |
| **3초** | 세션 타임라인 (1칸 = 1분봉) | **언제** 깨졌나 |
| 이후 | KPI 타일 → 접힌 상세 테이블 | **얼마나** 깨졌나 |

### 4.2 설계 원칙

**히어로는 판정과 조치를 함께 보여줍니다.** "매매 차단"만 크게 띄우면 그다음에 뭘 해야 할지 모릅니다. 차단 사유 상위 3건과 복구 플레이북 첫 조치를 나란히 놓았습니다.

**타임라인이 '3초'의 핵심입니다.** 1분 = 1칸으로 세션 전체를 한 줄에 압축하면, 구멍이 눈에 그냥 보입니다. 숫자를 읽을 필요가 없습니다.

두 가지 실무적 처리를 넣었습니다.

- **이상 셀에 최소 폭 4px 강제** — 405칸을 그리면 1px짜리 이상 구간은 사실상 안 보입니다. 그러면 3초 판독이 성립하지 않습니다.
- **경고 구간을 손으로 지정하지 않음** — 점검 결과의 샘플에서 실제 사고 시각을 긁어옵니다. 손으로 찍으면 실제 사고 시각과 어긋납니다.
- **시각은 KST 표기** — 09:47에 난 사고가 00:47(UTC)로 찍히면 타임라인의 존재 이유가 사라집니다. 초기 렌더링에서 실제로 이 실수가 있었고 수정했습니다.

**색만으로 상태를 표현하지 않습니다.**

| 요소 | 부호화 |
|---|---|
| 상태 배지 | 색 + 아이콘(●▲■✖○) + 한글 라벨 (삼중) |
| 타임라인 | 색 + **막대 높이** (정상 100% / 경고 52% / 미수신 점선 빈칸) |

색각 이상이나 흑백 출력에서도 판독됩니다.

### 4.3 KPI 타일

값만 크게 띄우지 않고 **기준선을 함께** 둡니다. "1490MB"만 보면 판단이 안 되지만 "한계 2048MB · 경고 1331MB"가 붙으면 즉시 읽힙니다.

```
봉 유실률      거래량 대사 오차   CVD 앵커 괴리    구독 슬롯      메모리(32bit)   이벤트 큐
0.00%          0.000%            45.30%          392/400        1490MB         1830
기준 < 0.20%   기준 < 0.20%      기준 < 2.0%     경고 > 340     한계 2048MB    경고 > 500
```

이 화면이 §1.2의 사각지대를 그대로 보여줍니다 — **거래량 오차는 0.000%인데 CVD 앵커 괴리가 45.30%.** 두 타일을 나란히 두면 왜 두 점검이 다 필요한지 설명이 필요 없습니다.

계약 점검 탭은 축별로 집계합니다.

```
불변식 위반   치역 이탈   정의구간 붕괴   앵커 괴리   위생 이상   미선언 피처
3/8          2/13        1/10           1/1        1/15        1개
```

## 5. 점검 주기와 게이팅

| 주기 | 시점 | 대상 | 실패 시 |
|---|---|---|---|
| **realtime** (1분) | 장중 | 접속·메모리·큐·구독슬롯·하트비트·누적거래량 연속성·Zero/NaN | 실시간 신호 차단, 해당 봉 마스킹 |
| **intraday** (5분) | 장중 | 분봉 완결성·OHLC 제약·CVD 앵커·계약 치역/불변식/정의구간 | 해당 구간 피처 무효화 |
| **eod** (16:10) | 마감 후 | `FutOptChart` 대사 3축·계약 위생·커버리지 | **익일 신호 차단**, 재처리·덮어쓰기 |
| **weekly** (일 09:00) | 주 1회 | PSI 드리프트·상관 구조·스케일러 파라미터·계약 축 빈약도 | 재학습 검토 |
| **monthly** | 월 1회 | 골든 데이터셋 재현성·임계치 재보정 | 임계치 튜닝 |

**게이팅 원칙은 fail-closed 입니다.** 게이팅 체크가 하나라도 실패하면 신호 생성과 주문을 차단하고, **점검기 자체가 예외로 죽어도 차단**합니다. 품질이 불확실한 날 안 하는 손실이 오염 데이터로 베팅하는 손실보다 쌉니다.

스케줄러는 종료코드로 후속 잡을 제어합니다.

| 코드 | 의미 | 후속 잡 |
|---|---|---|
| 0 | 정상 | 실행 |
| 1 | 경고 있음 | 실행 + 알림 |
| 2 | **게이트 CLOSED** | 신호·주문 잡 **중단** |
| 3 | 점검기 오류 | 중단 (fail-closed) |

## 6. 임계치를 정하는 법

숫자를 처음부터 맞히려 하지 마십시오. 3단계로 수렴시킵니다.

1. **관측 (2~4주)** — 모든 체크를 `gating: false`로 돌리고 지표 분포만 쌓습니다
2. **보정** — 각 지표의 p99를 warn, 그 1.5~2배를 fail로. 단 **물리적 불가능(OHLC 제약, crossed book, 항등식 위반)은 무조건 0 허용**
3. **운영** — 오탐이 주 3회를 넘으면 올리고, 미탐이 1회라도 있으면 내립니다. **임계치 변경은 반드시 커밋 이력으로 남기십시오.** 조용히 완화된 임계치가 가장 위험합니다

## 7. 한계 — 이 체계로도 못 잡는 것

정직하게 적습니다.

- **크레온이 애초에 틀린 값을 보내는 경우.** 실시간과 `FutOptChart`가 같은 원천이면 대사가 무의미합니다. 진짜 독립 검증을 원하시면 KRX 공식 데이터나 2차 벤더가 필요합니다.
- **점진적 품질 저하.** 하루 0.1%씩 나빠지는 오염은 임계치를 넘지 않습니다. 주간 PSI/IC를 **레벨이 아니라 기울기**로도 보셔야 합니다.
- **계약서가 틀린 경우.** 잘못 선언된 계약은 잘못된 점검을 만듭니다. `CONTRACT.HYGIENE`이 "실제 워밍업 20행 > 선언 5행" 같은 계약서 오류는 잡지만, 치역을 너무 넓게 잡은 계약은 못 잡습니다. **축 빈약도 리뷰를 주기적으로** 하십시오.
- **시장 구조 변화 vs 데이터 사고 구분.** PSI 급등이 서킷브레이커 때문인지 파이프 사고인지는 자동 판정이 불가능합니다. 알림에 **최근 배포 이력**을 함께 붙여야 사람이 30초 안에 판단할 수 있습니다.
- **32비트 메모리 한계 자체.** 점검은 사고를 예보할 뿐 늘려주지 않습니다. 근본 해결은 수집 프로세스를 32비트 브리지(COM 전용, 최소 기능)와 64비트 처리 프로세스로 분리하는 것입니다.
