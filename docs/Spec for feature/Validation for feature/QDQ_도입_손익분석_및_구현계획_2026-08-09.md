## 2. 발견 — 보고서가 겨눈 사각지대는 실재한다

### 발견 A 🔴 **체결구분 필드가 2개월째 통째로 버려지고 있다** (라이브 버그)

[realtime_data.py:223-243](../../../collection/cybos/realtime_data.py#L223-L243)

```python
buy_sell_flag = _safe_str(obj.GetHeaderValue(24))   # ← 실제 반환값: 49 또는 50
...
is_buy_tick = True
if buy_sell_flag == "2":                 # ← 절대 참이 되지 않는다
    is_buy_tick = False
elif buy_sell_flag not in ("1", "2"):    # ← 항상 여기로 온다
    is_buy_tick = price >= self._last_price if self._last_price else True
```

`GetHeaderValue(24)`는 문자 `'1'`/`'2'`가 아니라 **그 문자의 코드값 49/50을 숫자로** 반환한다.
`_safe_str`([api_connector.py:268](../../../collection/cybos/api_connector.py#L268))이 그것을
`"49"`/`"50"` 문자열로 만들고, 아래 비교는 `"1"`/`"2"`를 찾으므로 **한 번도 매칭되지 않는다.**

**로그 실측** (전 기간 `[CybosRT-TICK]`, 100틱마다 1건 샘플):

```
flag=50   38,108건
flag=49   37,156건
그 외        0건        ← "1"·"2"는 단 한 번도 나온 적이 없다
```

**필드 의미 검증** — 같은 로그 줄의 호가와 대조했다(부호가 맞는지 독립 확인):

| flag | n | 체결가 = 최우선매도호가 | 체결가 = 최우선매수호가 | 판정 |
|---|---|---|---|---|
| **49** | 22,039 | **30.1%** | 1.1% | 공격적 **매수** (`'1'`) |
| **50** | 22,880 | 1.2% | **29.9%** | 공격적 **매도** (`'2'`) |

27:1 비대칭이다. 필드는 정상이고 **읽는 쪽이 틀렸다.**

**결과**: 모든 틱이 폴백인 틱룰(`price >= 직전가`)로 분류된다. 그리고 그 틱룰은
**보합(가격 무변화)을 전부 매수로 넣는다**(`>=`). 그래서:

```
raw_candles 실측 (2026-06-08 라이브 틱 개시 ~ 2026-08-07, 44거래일)
  매수 비중 평균 63.08%   (buy 3,911,528 / sell 2,289,360)
  44거래일 전부 50% 초과  최소 60.55% · 최대 68.03%
  → 함의 보합틱 비중 26.2%  ((1+tie)/2 = 0.631)
```

44일 연속 한 방향 편향은 시장 현상일 수 없다. 이것은 계측 결함이다.
같은 파일의 `features/technical/cvd.py:46-53`은 **보합을 매수로 넣으면 롱 바이어스가
누적된다고 정확히 경고하고 중립 처리**하는데, 상류 수집기가 그 규칙을 우회하고 있었다.

### 발견 B 🔴 CVD CORE 피처가 상수화됐다 — 원인은 둘이고, 둘 다 고쳐야 한다

`raw_features` 최근 13거래일(2026-07-20~08-07) 5,642분:

```
cvd == 1.0     98.6%
cvd >= 0.99    99.3%
cvd <= -0.99    0.0%      ← 하방은 2개월간 단 한 번도 없다
평균            0.993
```

**원인 ①** = 발견 A. 매수 63% 편향 → 일중 누적 CVD가 단조 증가.

**원인 ②** = 정규화 자체. [cvd.py:104-105](../../../features/technical/cvd.py#L104-L105)

```python
cvd_abs_max = max(abs(v) for v in cvds) or 1.0     # 버퍼에 현재값이 들어 있다
cvd_norm    = self._cumulative_cvd / cvd_abs_max   # 단조 계열이면 항상 최신값 = 최대값
```

분모가 **자기 자신을 포함한 창의 최대값**이라, 계열이 단조이기만 하면 결과는 수학적으로
항상 ±1이다. 원인 ①을 고쳐도 ②가 남으면 포화는 완전히 풀리지 않는다.
보고서 §2.3의 "클리핑 포화율" 지적이 정확히 이 형태다.

**이 편향에 이미 3중으로 우회책이 쌓여 있다** — 즉 증상은 계속 관측됐지만 원인이 끝내
규명되지 않은 상태로 시스템이 그 위에 지어졌다:

| 시점 | 우회책 | 위치 |
|---|---|---|
| 2026-06-25 | CORE 체크리스트 `4_cvd`를 `cvd_direction` → `cvd_delta_norm`(가격기반)으로 교체 | [checklist.py:174-179](../../../strategy/entry/checklist.py#L174-L179) |
| 2026-06-25 | `cvd_direction`을 AutoMask 면제 목록에서 제외("+0.5 고착이라 보호 불필요") | [multi_horizon_model.py:183-185](../../../model/multi_horizon_model.py#L183-L185) |
| 394차 | `bear_exhaustion` 구조적 발화불가 → detrend 오실레이터 섀도 배선 | [cvd_exhaustion.py:38-46](../../../features/technical/cvd_exhaustion.py#L38-L46) |

`cvd_exhaustion.py`의 주석은 편향을 **"분봉 delta 평균 +57.3, t=93.1"** 까지 정량화해
놓고도 "Cybos buy_vol에 구조적 매수편향이 있다"로 결론지었다. 원천이 아니라 **우리 파서**가
원인이었다. 부수 피해: `kyle_lambda`([kyle_lambda.py:45](../../../features/technical/kyle_lambda.py#L45))도
같은 `buy_vol - sell_vol`을 쓴다.

> ⚠️ **이것은 CORE 피처 교체가 아니라 수집 버그 수정이다** — CLAUDE.md §3의 "CORE 교체
> 불가" 원칙에 저촉되지 않는다. 다만 **학습 데이터가 편향된 값으로 채워져 있으므로**
> 라이브에서 즉시 뒤집으면 train/serve skew가 생긴다. §5 Phase 3에서 별도로 다룬다.

### 발견 C 🟠 파이프라인 복구 경로가 **정상 데이터를 0으로 덮어쓴다**

[main.py:11317-11326](../../../main.py#L11317-L11326)

```python
bar = {
    "ts": ts, "open": ..., "high": ..., "low": ..., "close": ...,
    "volume":   int(row["volume"] or 0),
    "buy_vol":  0,        # ← 하드코딩
    "sell_vol": 0,        # ← 하드코딩
}
self.run_minute_pipeline(bar)
```

파이프라인이 멎으면 **DB에서 마지막 봉을 읽어와** 재처리한다. 그런데 다시 만든 dict에
`buy_vol/sell_vol`을 0으로 박고, `bid1`·`ask1`·`oi`는 키 자체가 없다. 이 봉이
`save_candle_and_features()` → `INSERT OR REPLACE`를 타면서 **원래 행에 들어 있던 진짜
값을 파괴한다**([db_utils.py:1494](../../../utils/db_utils.py#L1494) — `candle.get("buy_vol", 0)`).

실측 피해 (라이브 틱 개시 이후):

```
16,270봉 중 55봉이 buy_vol=sell_vol=0 & bid1/ask1/oi=NULL
날짜 분포: 06-25 16봉 · 07-31 13봉 · 08-04 15봉 · 나머지 9일 각 1봉
```

비율은 0.34%로 작지만 **하필 파이프라인이 멎을 만큼 시장이 험했던 날에 집중**된다.
게다가 그 봉들은 마스킹되지 않고 정상 피처로 하류에 흘러간다 — 보고서 §2.2의
**"덮어쓰기는 OHLCV 복구이지 피처 복구가 아니다"** 가 정확히 이 사례다.

같은 안티패턴이 [aggregate_and_backfill.py:187-188](../../../scripts/aggregate_and_backfill.py#L187-L188)에도
있다(호라이즌 집계 시 `buy_vol: 0` 하드코딩). 사용자 규칙
`feedback_no_schema_fallback_in_collection`(451차)의 **세 번째 재발**이다.

## 4. 무엇을 채택하고 무엇을 버리나

### ✅ 채택

1. **⑤ 앵커** — `누적체결매수(23)`/`누적체결매도(22)`. **이 계획의 심장.** 발견 A를 즉시 잡고,
   앞으로도 잡는다.
2. **② 불변식** — `buy+sell == volume`. 단 미륵이 코드 구조상 이 항등식은 **라이브 경로에서
   자명하게 성립**한다(`buy_v`/`sell_v`가 같은 `volume`에서 갈라져 나온다). 그래서
   **서버 앵커와의 증분 대조(`anchor_diff: true`)가 아니면 의미가 없다** — 보고서 §1.3의
   지적이 우리에게 정확히 적용된다.
3. **③ 정의구간 / ① 치역(이론경계 vs 절대경계 분리)** — Hurst·정규화 피처에 그대로 유효.
4. **RECON 3축(크기·부호편향·집중도)** + `commit_decision` 정책. 특히 **"OHLCV 복구 ≠ 피처
   복구, 틱 기반 피처는 마스킹"** — 발견 C의 정확한 처방이다.
5. **계약 커버리지 자기점검** — 144개 피처 대비 계약 0개인 현 상태를 드러낸다.

### ❌ 채택하지 않음

| 항목 | 이유 |
|---|---|
| 71체크 전량 이식 | §3.1 — 8개 무의미, 9개 중복, 22개는 없는 데이터를 전제 |
| `CREON.SUBSCRIBE_SLOTS` | 구독 3개 / 한도 400 |
