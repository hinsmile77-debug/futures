# 피처 데이터 3계층 구분 — DYNAMIC_FEATURES_POOL / active_features / raw_features

> 작성: 2026-08-02 (MW0601)
> 관련: `docs/Spec for feature/피처_발굴_표준절차.md`, `CLAUDE.md` §3·§6

세 가지는 같은 "피처"라는 말을 쓰지만 **계층이 전혀 다르다.**
하나는 코드 상수, 하나는 런타임 설정 파일, 하나는 DB 테이블이다.

## 핵심 차이 세 가지

### ① POOL vs active — "후보"와 "현역"

POOL 등록은 **자동 편입이 아니다.** 표준절차 Phase 1이 명시하듯
*"주간 SHAP 심사가 교체 후보로 제안할 수 있게 문을 여는 것"* 뿐이다
(`피처_발굴_표준절차.md` Phase 1-3).

실제 편입은 Phase 6 승격 심사 6항목을 통과하고 사람이 대시보드에서 승인해야
`active_features`로 옮겨진다 (`main.py:_on_apply_shap_candidate_requested`) —
`CLAUDE.md` §6 **자동 통합 금지** 원칙.

예: `opt_gex_sign` · `opt_atm_pcr` · `micro_regime_code` · `queue_directional_depletion`은
현재 POOL에만 있고 active에는 없다.

### ② active vs raw — "쓰는 것"과 "기록하는 것"

`raw_features`는 편입 여부와 **무관하게** FeatureBuilder가 계산한 dict 전체를
JSON으로 통째 저장한다 (`main.py:5142` → `utils/db_utils.py:save_features()`).

그래서 active에 없는 후보 피처도 값이 계속 쌓이고, 그 축적분이 나중에
IC 검증 · ablation · 백필의 원천이 된다. 즉 **raw ⊃ active**이며,
raw는 POOL 후보의 값도 이미 담고 있다.

이 구조 덕분에 **"먼저 기록하고 나중에 검증한다"**가 가능하다:

```
POOL 등록  →  raw_features 축적 대기  →  Phase 3~5 검증  →  사람 승인  →  active 편입
(코드 커밋)     (매분 자동)              (읽기 전용)         (대시보드)      (registry)
```

### ③ active_features는 "선언"이지 "배선"이 아님

주의할 뉘앙스다. 모델이 진짜로 쓰는 것은 `feature_names.pkl`이고,
`registry.active_features`는 그것과 어긋날 수 있어 시작 시 정합성 검사가 돈다
(`model/multi_horizon_model.py:_check_registry_feature_consistency()`, L901~921).

**불일치 시 예측은 pkl 기준으로 진행**되고 registry는 경고만 남는다.
즉 registry를 고쳤다고 모델이 바뀌는 게 아니라, 재학습이 돌아 pkl이 갱신돼야 실제로 바뀐다.

## 실제로 사고가 났던 지점

`shap_feature_registry.json`이 커밋 대상이 아니라서(PC별 런타임 산출물),
MW0602에서 active에 편입한 8종이 이 PC(v9-dev)에 전파된 적이 없었다.
문서상 "편입됨"인데 라이브 1m 모델은 8피처만 쓰고 있던 상태였다.

근거: `config/constants.py:199~223` 주석,
`docs/미륵이고도화2/무스킬_피처셋_딥다이브_보고서_2026-07-13.md` F1

> **POOL은 git으로 동기화되지만 active는 PC마다 따로 논다** —
> 이 세 가지를 헷갈리면 안 되는 가장 실전적인 이유다.
