- 결정: **실거래는 `atr_profit`으로 통일하고, `breakeven`은 카운터팩추얼 재생으로만 감시한다**

## 1. 왜 이 결정인가

`tp1_single_contract_mode`는 `data/session_state.json`에 저장되는 **PC 로컬 대시보드 설정**이다
(gitignore 대상). 코드 기본값은 `atr_profit`인데 MW0601만 `breakeven`으로 설정돼 있었다.

| 근거 | 내용 |
|---|---|
| MW0602 실측 | 23건 재생에서 `breakeven`은 현행 `atr_profit` 대비 **건별 우세 0/23**, 즉 22/23 열위 ([config/settings.py:1612-1615](../../../config/settings.py#L1612-L1615) 사전등록 고지) |
| 대조 손실 없음 | `[25]`의 `variants`에 `breakeven`이 **이미 사전등록돼 있다**. 실거래를 통일해도 카운터팩추얼 재생은 계속된다 |
| 교란 제거 | 두 PC의 라이브 모드 차이를 A/B로 쓰는 것은 모델·거래모집단이 달라 교란된다(§대조문서 §3). 같은 거래 위 재생이 비교할 수 없이 강하다 |
| 계측 정상화 | MW0601 `[25]`가 n=0으로 죽어 있다. 통일하면 자동으로 살아난다 |

**`[25-B]` 신설은 하지 않는다.** 통일만 하면 `[25]`가 MW0601에서 그대로 돌기 시작하고
`breakeven` 변형도 함께 재생되므로, 별도 채널이 불필요하다.

## 2. 조사에서 나온 블로커 3건

계획을 세우며 코드를 확인한 결과, 단순 모드 변경만으로는 안 되는 문제가 있다.

### B-1. `breakeven` 행은 ATR 복원이 원리적으로 불가능하다

`[25]`는 ATR을 **저장된 offset에서 역산**한다
([scripts/tp1_protect_offset_shadow.py:160-165](../../../scripts/tp1_protect_offset_shadow.py#L160-L165)):

```python
off_from_entry = abs(float(h["stop_after"]) - ep)
atr = off_from_entry / _LOCK_MULT_CURRENT if off_from_entry > 0 else 0.0
if atr <= 0:
    skipped += 1     # ← breakeven 행은 전부 여기서 버려진다
```

`breakeven`은 offset=0이라 `stop_after == entry_price`다. MW0601 29건 중 **25건이 offset=0**.
→ **과거 breakeven 표본은 소급 복구 불가**. 받아들이고 라벨만 붙인다.

### B-2. 나머지 4건의 offset은 ATR이 아니다 — 역산하면 조용히 틀린다

[strategy/position/position_tracker.py:749-751](../../../strategy/position/position_tracker.py#L749-L751):

```python
protected_stop = self.entry_price + mult * protect_offset_pts
if mult * (prev_stop - protected_stop) > 0:
    protected_stop = prev_stop      # ← 기존 트레일링 스톱이 더 유리하면 그걸 유지
```

실측: MW0601 29건 중 offset>0인 4건(07-22 3건 · 07-29 1건)은 전부 이 경로다.
`breakeven`인데 offset이 0.8685 / 0.8579 / 1.1993 / 2.6164pt로 찍혀 있다.
**이 값을 `/0.25`로 나누면 ATR이 3.5~10.5로 나오지만 실제 ATR과 무관하다.**

### B-3. B-2는 `atr_profit` 행에도 적용된다 — 기존 잠재 결함

`prev_stop` 오버라이드는 모드와 무관하게 걸린다. 즉 **MW0602의 `[25]`도
"트레일링 스톱이 이미 우세했던 행"에서 잘못된 ATR을 역산해 6개 변형 전부를
그 위에 쌓고 있을 수 있다.** 이번 조사 전까지 아무도 보지 않던 경로다.

> 정직하게: MW0602 DB가 없어 **몇 건이 해당하는지는 확인하지 못했다.** MW0601에서
> 4/29(13.8%)였다는 사실만 안다. B-2/B-3 수정은 이 불확실성을 없애는 것이 목적이다.

### A — 실거래 모드 통일

`session_state.json`은 gitignore 대상 PC 로컬 파일이라 **커밋되지 않는다.**
MW0602는 이미 `atr_profit`이므로 MW0601만 바꾸면 두 PC가 코드 기본값과 일치한다.

대시보드 토글로도 바꿀 수 있지만([main.py:2347](../../../main.py#L2347) `_on_tp1_protect_mode_changed`),
장 시작 시 `_restore_tp1_protect_mode_setting()`이 파일에서 읽으므로 파일을 직접 고친다.

### B — ATR을 저장한다 (B-1·B-2·B-3의 근본 해결)

`arm_tp1_single_contract_with_mode(price, atr, ...)`는 **이미 `atr`을 인자로 받고**
`protect_offset_pts`를 반환한다. INSERT 지점([main.py:11413](../../../main.py#L11413))에서 둘 다 스코프 안에 있다.
즉 새로 계산할 것이 없고 **이미 있는 값을 버리고 있었을 뿐**이다.

- `atr REAL` — 역산 불필요해짐 (B-1 해결: breakeven 행도 ATR을 갖는다)
- `protect_offset_pts REAL` — 모드가 의도한 offset. `abs(stop_after-entry)`와 다르면
  `prev_stop` 오버라이드가 걸린 행이다 (B-2·B-3 식별 가능)

**소급 적용 불가** — 기존 29건은 NULL. 08-03부터 쌓인다.

### C — `[25]` ATR 소스 정정

> **설계 수정 (구현 중 변경)**: 처음에는 `protect_mode='atr_profit'` 필터를 제거해
> breakeven 행까지 판정 모집단에 넣으려 했으나, **그러면 판정식이 깨진다.**
> `current` 변형은 `ATR × 0.25`로 정의돼 있어 "실제로 일어난 일"이어야
> `delta_vs_current`가 의미를 갖는데, breakeven 행에서는 실제 일어난 일이 offset=0이다.
> → **필터는 유지하고**, 빠진 건수와 사유만 노출하도록 범위를 좁혔다. 사전등록 무저촉.

```
판정 모집단: atr_profit 행 (변경 없음)
ATR 우선순위: 저장된 atr 컬럼  →  (없으면) 기존 역산
역산 폴백 시: 저장 offset과 |stop_after-entry|가 불일치하면 오버라이드 행으로 보고 제외
노출 카운터: n_other_mode(모드별 제외) / n_backout_legacy(역산 사용) / n_excluded_override
```

기존 판정식·합격선은 **건드리지 않는다.** `_load_hooks`는 전량을 읽되 `compute()`가
모드로 가르므로 판정 모집단은 종전과 동일하다.

### D — `[24]` mode별 분리 집계

DB 스키마 변경 불필요. 행마다 `mode`가 이미 있고 `by_mode` 분포까지 출력 중인데
평균·중앙값·상관만 통째로 계산하고 있다. 그룹핑만 추가한다.
`[24]`는 **verdict가 항상 OBSERVE**라 판정 영향이 없다.

### E — `[25]` 표기

현재 MW0601은 `⏳ INSUFFICIENT | 표본 부족 (n=0<20)`으로 나와 "곧 표본이 차면 판정된다"고
읽히지만, breakeven 행만 있는 한 영원히 차지 않았다. A 적용 후에는 자연히 해소되지만
**과거 29건이 남아 있는 동안** 원인을 표기한다.
