VALIDATION_CAMPAIGN — 전체 구조 정리
배경
docs/260705_OFFENSE_READINESS_AUDIT_AND_NEXT_PHASE.md §3에서 사전 등록(pre-registration)한 섀도우 채널 승격 기준입니다. 
아이디어는: 실험적/개선 컴포넌트를 바로 실거래에 반영하지 않고, 
별도 계측 테이블에 "가상 결과"를 쌓은 뒤 사전에 정해둔 합격선을 넘기면 그때 사람이 검토해서 수동으로 켜거나 끈다 
— 데이터를 보기 전에 기준을 고정해야 사후 과적합(합격선을 결과에 맞춰 조정)을 막을 수 있다는 원칙입니다. 
기준값은 config/settings.py:VALIDATION_CAMPAIGN에 있고 "변경 금지" 주석이 붙어 있습니다(바꾸려면 
DECISION_LOG에 사유 기록 + 검증 시계 리셋).

사용자가 결과를 받는 방법
파일로 저장: 실행할 때마다 data/validation_campaign_report.md(사람이 읽는 표+설명 형식)와 
data/validation_campaign_metrics.json(원본 수치)에 덮어쓰기 저장됩니다.

콘솔 출력: 실행 시 리포트 전문이 그대로 콘솔에도 출력됩니다.
대시보드에는 노출되지 않습니다 — main.py에는 이 모듈에 대한 주석만 있고 UI 패널로 연결된 배선이 없습니다. 
즉 지금 구조에서 결과를 확인하려면 금요일 이후 data/validation_campaign_report.md를 직접 열어보거나, 
저처럼 스크립트를 실행해서 콘솔/파일을 확인해야 합니다 — 별도 알림(로그 경고, 대시보드 배지 등)은 없습니다.

두 산출 파일 모두 .gitignore 대상(PC별 로컬 산출물, 재생성 가능) — 커밋되지 않고 각 PC에 로컬로만 쌓입니다.

어제 한 작업과의 관계
어제 실행한 건 이 7개 채널 중 [6]번 하나만 따로 골라 resolve_and_eval_hurst_gate() 함수를 직접 호출한 것이고, 
전체를 다 돌리려면 build_report()/main() 경로(=전체 스크립트 실행)를 타야 [0]~[6] 전 채널이 한번에 리포트에 담깁니다. 
다른 채널(특히 [1] TB, [2] Meta-Gate)은 모델 pickle 로딩 등 더 무거운 의존성이 있어 미리 확인 없이 돌리기보다, 
필요하시면 전체 리포트를 한번 생성해서 지금 상태를 종합적으로 보여드릴 수 있습니다.
