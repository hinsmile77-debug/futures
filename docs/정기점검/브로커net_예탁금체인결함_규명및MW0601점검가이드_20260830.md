## 0. 세 줄 요약

1. `CpTd6197`의 **예탁현금·익일가예탁현금은 장 마감 정산 전후로 의미가 바뀐다.**
   장중엔 `익일가 − 예탁 = 그날 net`이지만, 정산 후엔 `= −수수료`다.
2. 로그 파서와 라이브 저장부가 **둘 다 마지막 판독을 무조건 채택**해서, 거래일
   저녁에 세션이 살아 있던 날의 net이 수수료로 대체됐다(MW0602 실측 **4일**).
3. 별개로, `is_krx_trading_date()`의 **음성 영구 캐싱** 때문에 493차 F-2가 배선한
   라이브 저장이 **2026-08-25 이후 한 번도 성공하지 못했다.**

**영향 축이 갈린다** — 수수료율 재보정은 **무해**하고(오히려 그 4일이 최상의
표본이다), **일별 net(전환기준 ① 판정 원천)만** 오염된다.

## 1. 메커니즘

### 1-1. 두 필드의 의미가 정산 전후로 바뀐다

| 시점 | `예탁현금`(idx=1) | `익일가예탁현금`(idx=2) | `익일가 − 예탁` |
|---|---|---|---|
| **장중** | 당일 시가 **고정** | 시가 + gross − 수수료 | **그날 net** ✅ |
| **장후(정산 후)** | (시가 + gross)로 **롤오버** | 거기서 **수수료만** 차감 | **−수수료** ❌ |

MW0602 2026-08-06 로그 실측:

```
08:41:07 ~ 14:48:25   예탁 30,180,776   익일가 → 29,820,634   실현 -317,000   ← 장중
20:06:51              예탁 29,820,658   익일가    29,777,516   실현        0   ← 장후 재기동
```

- 장중 기준 net = 29,820,634 − 30,180,776 = **−360,142**
- 장후 판독 = 29,777,516 − 29,820,658 = **−43,142** ← 이게 기록됐다

**−43,142는 그날 수수료다.** 손익이 통째로 빠졌다.

### 1-2. 결함 3종

| # | 결함 | 위치 | 성격 |
|---|---|---|---|
| **D1** | 로그 파서가 마지막 줄(롤오버 판독) 채택 | `scripts/commission_rate_recon.py:_scan_lines` | **소급 적재 오염** — 이미 발생 |
| **D2** | 라이브 저장부에 롤오버 가드 없음 | `main.py` 잔고 push → `upsert_broker_net` | **잠재** — 거래일 저녁 세션이면 재현 |
| **D3** | `is_krx_trading_date()`가 음성을 **영구 캐시** | `utils/db_utils.py` | **활성** — 라이브 저장이 통째로 무동작 |

### 1-3. 🔴 D3가 가장 심각했다

```
08:41:18  [BrokerNet] state=SKIP_NON_TRADING date=2026-08-27   ← 첫 호출
09:00:00  predictions 첫 행 생성                                ← 19분 뒤
```

`is_krx_trading_date()`는 `predictions`/`trades`에 그 날짜 행이 있는지로 판정한다.
그런데 **첫 호출이 장전 08:41 잔고 push**라 그 시점엔 근거가 없다 → `False` →
`_trading_date_cache`에 박혀 **세션 내내** 유지 → 그날 `upsert_broker_net`이 종일
스킵. 0827 로그 `SKIP_NON_TRADING` **35건 전부**가 그것이다.

**`pnl_krw`(gross)만 멀쩡했던 이유**: 그쪽은 `upsert_daily_broker_pnl(_yesterday, …)`
경로로 **다음 날** 저장되고, 그때는 새 프로세스라 캐시가 비어 있어 True가 나온다.
**두 축이 갈린 것이 이 결함의 지문이다** — gross는 있는데 net만 NULL인 날.

> 이것은 FP-CRITICAL(2개월 PSI=0.0)·TOX 죽은 섀도와 **같은 계열**이다:
> 배선은 됐는데 조용히 안 돈다. **500차 F-5가 넣은 상태 로그가 없었으면 이번에도
> 안 보였다** — 계측 4원칙 ④("폴백이 쓰였으면 그 사실을 남긴다")의 배당금이다.

## 2. MW0602 실측·조치 (참고값 — MW0601에 그대로 쓰지 말 것)

### 2-1. 전수 검사 — 오염 4일 / 49거래일

| 날짜 | 기록된 net | 정정 net | 차이 | 마지막 줄 |
|---|---:|---:|---:|---|
| 2026-06-30 | −21,073 | **−598,073** | +577,000 | 18:38:26 |
| 2026-07-01 | −20,564 | **−1,185,564** | +1,165,000 | 18:33:58 |
| 2026-07-14 | −8,241 | **+618,759** | −627,000 | 18:51:41 |
| 2026-08-06 | −43,142 | **−360,142** | +317,000 | 20:06:51 |

**차이가 매번 그날 gross와 정확히 일치한다** → `true_net = gross + 기록된_net`
(검산 4/4 로그 실측과 일치). 나머지 45일은 차이 0원.

### 2-2. 판별 규칙 — 「예탁현금은 당일 시가 고정」 불변식

그날 **첫 판독**과 예탁현금이 달라지면 롤오버다. MW0602 전 로그(49거래일 ·
2,164줄)에서 **오탐 0 · 미탐 0**.

🔴 **「실현손익 0 && 예탁≠익일가」로는 안 된다.** 미실현 손익이 익일가를 움직이는
장중 초반 줄이 걸려 **33일이 오탐**된다. 설계 중 실제로 밟은 실패이며
`tests/test_501_broker_net_postclose_guard.py::test_d1c_...`가 회귀로 고정한다.

### 2-3. ✅ 수수료율은 영향 없음 — 오히려 보강된다

정정 전후 `commission_rate_recon.py --verify` 결과가 **완전히 동일**하다
(총 수수료 737,095원 / 약정 38,796,175,000원 / 실효 0.001900% / R²=1.000000 /
PASS 편차 0.00%).

역설적으로 **오염 4일이 가장 깨끗한 수수료 표본**이었다 — 장후 판독은 순수
수수료 델타라 `gross − net = 수수료`가 정확히 성립한다. 이 사실이 §1-1의
메커니즘을 독립적으로 확증한다.

> **같은 결함이 한 축(요율)에서는 무해하고 다른 축(일별 net)에서만 유해했다.**
> 그래서 요율 검정 PASS가 net의 건강을 보증하지 않는다 — 계측 4원칙 ⑤
> ("대사는 모든 축을 걸어라")의 또 다른 사례다.

### 2-4. 전환기준 ① 영향 — 창에 따라 판정이 갈린다

MW0602 정정 후:

| 창 | 통산 | 양수일 | 판정 |
|---|---:|---|---|
| 2026-07-23~08-21 (489차 D6와 같은 창) | **−257,453** | 8/21 | 미충족 |
| 2026-07-28~08-25 (493차가 명명한 4주) | **+362,029** | 10/20 | **충족** |
| 2026-07-31~08-28 (최신 20거래일) | **−705,971** | 10/20 | 미충족 |

정정 전 D6 창은 **+59,547**(양수)이라 엔진 net(−178,004)과 **부호가 반대**였다.
정정 후 둘 다 음수로 정렬된다 — 결론은 유지되고 근거의 일관성이 회복된다.

⚠ **①의 「4주 창」 정의가 명시돼 있지 않다.** 결과를 보고 창을 고르면 사후탐색이다
(§9-4 검증 시계 리셋 대상) — **창을 먼저 정할 것**(`NEXT_TODO.md` T-6).

## 3. MW0601 점검 가이드

> 🔴 **§2의 수치를 그대로 인용하지 말 것.** MW0601은 별개 계좌(요율
> **0.0098104%** vs MW0602 0.0019%) · 별개 `trades.db` · 별개 브랜치(`v9-dev`)다.
> **오염 날짜도 다를 수 있다** — 오염은 "그날 저녁에 세션이 살아 있었는가"로
> 결정되므로 PC별 운용 습관에 달렸다. 반드시 자기 로그로 재실측할 것.

### 3-1. 진단 (읽기 전용, 5분)

```bash
python scripts/broker_net_chain_audit.py
```

이 스크립트는 **아무것도 쓰지 않는다.** D1·D2·D3를 한 번에 재고 종료코드로
알린다(0 = 이상 없음 / 1 = 발견 / 2 = 표본 없음).

`scripts/broker_net_chain_audit.py`가 그 브랜치에 없으면 `dev`에서 **그 파일 하나만**
가져오면 된다(읽기 전용이라 안전하다):

```bash
git show dev:scripts/broker_net_chain_audit.py > scripts/broker_net_chain_audit.py
```

⚠ 체리픽하면 `DECISION_LOG.md`에 **원 커밋 sha · 원 PC · 가져온 이유** 세 가지를
남길 것(CLAUDE.md 470차 규약. 문서·도구 체리픽도 예외가 아니다).

### 3-2. 출력 읽는 법

| 절 | 🔴 나오면 | ✅ 나오면 |
|---|---|---|
| **D1** | 오염일 목록과 정정값이 찍힌다 → §3-3 | 롤오버 줄이 있어도 채택되지 않았다 |
| **D2** | `전일 익일가 ≠ 당일 예탁` 목록 → 입출금인지 먼저 확인 | 체인 연속 |
| **D3** | 거래일인데 `SKIP_NON_TRADING` → §3-4 | 없음. **단 아래 ⚠** |
| **부가** | `_scan_lines`에 가드 없음 → **먼저 파서부터** | 가드 있음 |

⚠ **D3가 ✅여도 안심할 수 없다.** `[BrokerNet] state=` 로그는 **500차 F-5 이후
세대에만** 있다. 그 이전 구간은 "로그 없음"이 "정상"이 아니라 **판정 불가**다
(계측 4원칙 ②). 스크립트가 그 경우 대체 지표를 함께 찍는다 — **`pnl_krw`는
있는데 `broker_net_krw`가 NULL인 거래일**. 그게 D3의 지문이다:

```sql
SELECT date, pnl_krw, broker_net_krw FROM daily_broker_pnl
 WHERE broker_net_krw IS NULL AND pnl_krw IS NOT NULL ORDER BY date;
```

### 3-3. D1이 나왔을 때 — 정정 순서 (순서를 지킬 것)

1. **파서를 먼저 고친다.** 안 고치고 정정하면 다음 적재에서 **재오염된다.**
   `_scan_lines`가 「그날 첫 예탁현금」을 기준점으로 잡고, 달라지는 판독은
   채택하지 않게 한다. `dev`의 구현을 참고하되 자기 브랜치 문맥에 맞출 것.
2. **백업.** `cp data/db/trades.db data/db/trades.db.bak_<날짜>_pre_brokernet_fix`
3. **정정.** `python scripts/commission_rate_recon.py --backfill --force`
4. **검산.** 백업과 대조해 ① `pnl_krw`(gross)가 **전 일자 불변**인지
   ② 행 증감 0인지 ③ 변경된 날이 진단이 지목한 날과 **정확히 일치**하는지.
   `true_net = gross + 기록된_net`이 성립하는지도 확인한다.
5. **요율 재확인.** `python scripts/commission_rate_recon.py --verify`
   → **PASS이고 값이 정정 전과 동일**해야 한다. 달라졌다면 파서 수정이
   과했거나(정상 판독까지 버렸거나) 다른 문제가 있다.
6. **불연속 마커.** `strategy_events`에 `METRIC_REDEFINITION` 1행.
   메시지에 바뀐 날짜·전후 값·"이전 판정과 직접 비교 금지"를 적는다.
7. **전환기준 ① 재판정.** 이 값이 ①의 원천이다. 정정으로 **부호가 뒤집힐 수
   있다**(MW0602는 +59,547 → −257,453이었다).

### 3-4. D3가 나왔을 때

`is_krx_trading_date()`에서 **True만 영구 캐시하고, False는 그 날짜가 이미 지난
경우에만 캐시**한다. 오늘·미래 날짜의 False는 "아직 아니다"이지 "아니다"가 아니다.

재조회 비용은 인덱스 조회 2회이고 호출부가 분당 1회 수준이라 무시할 수 있다.

⚠ **캐시를 통째로 없애지 말 것** — 과거 날짜 판정은 바뀌지 않으므로 영구 캐시가
맞고, 없애면 `upsert_daily_broker_pnl(_yesterday, …)` 경로가 매번 재조회한다.

### 3-5. D2(라이브 가드) — 진단으로는 안 잡힌다

D2는 "아직 안 터진 결함"이라 로그에 흔적이 없을 수 있다. **코드로 확인**한다:

```bash
grep -n "upsert_broker_net" main.py
```

호출 직전에 **당일 첫 예탁현금과 비교하는 가드**가 없으면 취약하다. 거래일 저녁에
세션을 켜두는 습관이 있으면 언제든 재현된다.

### 3-6. 회귀 고정

`tests/test_501_broker_net_postclose_guard.py`가 D1(4건)·D2(1건)·D3(3건)을 덮는다.
**오탐 규칙 실패(`test_d1c`)까지 고정돼 있으니** 가져갈 때 그것도 함께 가져갈 것 —
「실현손익 0 && 예탁≠익일가」로 되돌아가는 것을 막는 유일한 장치다.

## 4. 이 결함에서 배울 것 (계측 규약 관점)

| 관찰 | 대응하는 규약 |
|---|---|
| gross는 맞는데 net만 틀렸다 | **계측 4원칙 ⑤** — 파생값을 대사하려면 구성요소를 각각 걸어라 |
| 요율 검정 PASS가 net 건강을 보증하지 않았다 | ⑤ — "일치" 로그에 **무엇을 비교했는지** 쓴다 |
| 배선은 됐는데 조용히 안 돌았다(D3) | **④ 폴백 가시화** — 500차 F-5 상태 로그가 없었으면 못 봤다 |
| `SKIP_NON_TRADING` 로그 없음 ≠ 정상 | **② 미측정 ≠ 0** — 로그 세대를 확인하고 대체 지표를 볼 것 |

🔴 **가장 중요한 교훈**: 이 결함은 크래시가 아니라 **그럴듯한 값**으로 나타났다.

## 부록. 빠른 확인 SQL (스크립트 없이)

```sql
-- ① 체인 불연속: 전일 익일가 vs 당일 예탁
SELECT a.date, a.next_day_deposit_cash_krw AS prev_next,
       b.date, b.deposit_cash_krw AS today_dep,
       b.deposit_cash_krw - a.next_day_deposit_cash_krw AS gap
  FROM daily_broker_pnl a
  JOIN daily_broker_pnl b ON b.date = (SELECT MIN(date) FROM daily_broker_pnl
                                        WHERE date > a.date
                                          AND deposit_cash_krw IS NOT NULL)
 WHERE a.deposit_cash_krw IS NOT NULL
   AND ABS(b.deposit_cash_krw - a.next_day_deposit_cash_krw) > 1000
 ORDER BY a.date;

-- ② D3 지문: gross는 있는데 net만 NULL
--    ⚠ 주말·휴장일 「유령 행」이 함께 잡힌다 — `upsert_daily_broker_pnl(_yesterday, …)`
--      가 **달력** 어제에 쓰기 때문이다(477차 후속2가 가드를 넣기 전 잔재).
--      MW0602 실측 12행 중 대부분이 그것이다. **거래일만 세야 한다.**
SELECT date, pnl_krw, broker_net_krw FROM daily_broker_pnl
 WHERE broker_net_krw IS NULL AND pnl_krw IS NOT NULL
   AND date IN (SELECT DISTINCT date(entry_ts) FROM trades)   -- 거래일만
 ORDER BY date;

-- ③ D1 지문 후보: |net| 이 gross 대비 비정상적으로 작다(= 수수료만 남았다)
SELECT date, pnl_krw AS gross, broker_net_krw AS net
  FROM daily_broker_pnl
 WHERE pnl_krw IS NOT NULL AND broker_net_krw IS NOT NULL
   AND ABS(pnl_krw) > 100000
   AND ABS(broker_net_krw) < ABS(pnl_krw) * 0.2
 ORDER BY date;
```

⚠ ③은 **후보**일 뿐이다 — 진짜 판정은 로그의 예탁현금 불변식으로 해야 한다.
gross가 작은 날은 정상이어도 이 조건에 걸린다.
