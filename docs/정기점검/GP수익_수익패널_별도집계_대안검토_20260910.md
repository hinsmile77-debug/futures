## 1. dev가 v9-dev보다 단순하다 — 이것이 핵심이다

v9-dev의 Phase 4가 복잡했던 이유는 GP 때문이 아니라 **그쪽 패널에 출처 필터가 있기
때문**이다. 출처 필터는 하루 거래의 **일부만** 선택할 수 있고, 그러면 「그 날 전체의
합」인 브로커 실측 net을 쓸 수 없다 — 그래서 `_day_is_whole`·`_day_total_legs`·
`_day_is_approx`가 필요했다.

**dev에는 그 필터가 없다.** 실측(HEAD 기준):

| v9-dev 함수 | dev 보유 | 왜 없는가 |
|---|---|---|
| `_assign_origins` / `_active_origins` | ❌ 0건 | 출처 필터 미보유 |
| `_load_origin_prefs` | ❌ 0건 | 〃 |
| `_day_is_whole` / `_day_is_approx` | ❌ 0건 | 항상 whole이라 필요 없다 |
| `_engine_net(r)` | ❌ 0건 | 반사실 요율 탭(504차 계열) 미보유 |
| `_refresh_approx_note` | ❌ 0건 | 〃 |
| `_effective_day_krw` | ✅ | **단일 관문 — 여기만 고치면 된다** |
| `fetch_gp_shadow_positions` / `gp_shadow_is_wired` | ✅ | 553차 체리픽분 |
| `MINI_FUTURES_PT_VALUE` | ✅ | `config/constants.py:86` |

dev의 단일 관문은 12줄이다:

```python
def _effective_day_krw(self, date_str, day_rows):
    broker_krw = self._broker_pnl.get(date_str)
    if broker_krw is not None:
        return broker_krw          # ← 조기 반환. day_rows 를 **보지 않는다**
    return sum(r["pnl_krw"] for r in day_rows)
```

## 2. 🔴 반드시 피해야 할 함정 — 「day_rows에 GP를 섞는다」

가장 자연스러워 보이는 구현이 **가장 조용히 틀린다.**

위 코드에서 브로커 값이 있으면 **`day_rows`를 아예 읽지 않고 반환한다.** 그러니 GP
행을 `day_rows`에 넣으면:

- 브로커 net이 있는 날 → GP가 **통째로 사라진다**
- 브로커 net이 없는 날 → GP가 **더해진다**

즉 날짜마다 다른 정의가 섞인다. 그리고 이 시스템에서 그건 이론적 위험이 아니다 —

> 🔴 **실측: 최근 90일 창의 일별 net 원천이 `broker` 50 / `engine` 0 — 100%다.**
> 지금 `day_rows`에 GP를 섞으면 **모든 날에서 GP가 0으로 사라진다.**
> 화면은 멀쩡해 보이고 아무 에러도 안 난다. 493차 「조용히 그럴듯한 값」 그대로다.

반대 방향 함정도 있다 — GP를 브로커 net **안에** 포함된 것처럼 보이게 하면, 예탁금
차액(실거래 전용)이 가상 포함 집합의 손익으로 표시된다. 브로커 net은 쪼갤 수 없다.

⇒ **분리 합성만이 답이다**: `day_krw = (실거래분) + (GP분)`. v9-dev의 처방과 같지만,
dev에서는 `_day_is_whole` 수술이 필요 없어 훨씬 작다.

## 4. 안 A 설계안

### 4-1. 데이터 주입 — `trades`에 넣지 않는다

```
main.py  update_pnl_history(rows)                     ← 시그니처 유지
   └ 패널이 스스로 fetch_gp_shadow_positions() 호출
```

⚠ **v9-dev처럼 `main.py`에서 kwarg로 넘기지 말 것.** dev 시그니처는 `(self, rows)`라
556차에서 그 변경을 되돌렸다(런타임 TypeError). 패널이 `refresh()` 안에서 직접 읽으면
호출부를 건드릴 필요가 없다 — `_broker_pnl`을 이미 그렇게 채우고 있다.

🔴 **`trades` 테이블에는 절대 넣지 않는다.** 브로커 대사·전환기준 ①·수수료 재환산·
승패 사후검증이 전부 그 테이블을 **실거래로 전제**한다.

### 4-2. 단일 관문 수정 (핵심 10줄)

```python
def _effective_day_krw(self, date_str, day_rows):
    # 🔴 GP(가상)는 브로커 net 분기 **밖에서** 더한다.
    #   브로커 net 은 예탁금 차액이라 그 날 전체의 합이고 거래별로 쪼갤 수 없다.
    #   day_rows 에 섞으면 브로커 날(현재 100%)에 통째로 사라진다.
    gp_krw = self._gp_day_krw(date_str) if self._gp_on() else 0.0
    broker_krw = self._broker_pnl.get(date_str)
    if broker_krw is not None:
        return broker_krw + gp_krw
    return sum(r["pnl_krw"] for r in day_rows) + gp_krw
```

- `_gp_day_krw(date)` = `Σ pnl_pt × MINI_FUTURES_PT_VALUE` (날짜별 사전 집계 dict)
- `_gp_on()` = 체크박스 상태. **기본 해제**
- ⚠ `pnl_pt → 원` 환산에 `FUTURES_PT_VALUE`(250,000)를 쓰지 말 것 — 운영 종목은
  **미니선물(A0569000) 50,000원/pt**다. 553차 Phase 0이 원문서 수치를 정정한 4건 중
  하나가 바로 이 5배 과대다.

### 4-3. 가시화 (계측 4원칙 ②·④)

| 요소 | 내용 |
|---|---|
| **체크박스** | 「GP(가상)」 — `_cb_forward`/`_cb_reverse` 옆 코너 위젯. **기본 해제** · `ui_prefs.json` 저장(기존 `_load_cb_prefs` 관례) |
| **배너 3상태** | 「미배선」 / 「배선됨 · 청산 0건」 / 「🟣 가상 포함 — GP n건이 합산돼 있다. 실적이 아니며 전환기준 ① 판정에 쓰지 말 것」 |
| **셀 마커** | 가상분이 섞인 날의 원화 칸에 🟣 (기존 `≈` 관례와 같은 자리) |

🔴 **「미배선」과 「0건」을 반드시 가른다.** `gp_shadow_is_wired()`가 그 근거다.
지금 이 PC는 **미배선**이다(재기동 전이라 GP가 아직 안 돌았다) — 그 상태를 「0건」으로
보이면 FP-CRITICAL 죽은 게이트와 같은 착시가 된다.

### 4-4. 회귀로 고정할 불변식 5개

1. **해제 시 완전 동치** — GP 체크 해제면 패널의 모든 값이 종전과 **비트 단위로 같다**
2. **브로커 날에도 GP가 반영된다** — §2의 함정을 직접 재현하는 검사
   (브로커 net이 있는 날짜에 GP를 넣고 합이 `broker + gp`인지)
3. **승수는 50,000** — 250,000을 쓰면 깨진다
4. **`trades` 무오염** — 판정 함수(`fetch_daily_net_for_verdict`)가 `challenger.db`를
   보지 않는다
5. **배너 3상태** — 미배선/0건/n건이 서로 다른 문구

### 4-5. 하지 않을 것

- 출처 필터·반사실 요율 탭 이관 (C안 영역)
- `main.py` 호출부 시그니처 변경
- `_day_is_whole`류 신설 — dev엔 부분 선택이 없으므로 **만들 이유가 없다**
  (없는 문제에 기계장치를 들이면 그것이 다음 사고의 씨앗이다)

## 5. 착수 시점 — 지금 만들면 빈 화면을 보게 된다

현재 상태 실측:

```
gp_shadow_is_wired()        → False   (아직 신호를 낸 적이 없다)
fetch_gp_shadow_positions() → 0건
```

GP 도전자는 553차 체리픽으로 **등록은 됐지만 재기동 전이라 아직 안 돌았다**.
즉 지금 배선해도 화면은 「미배선」 한 줄뿐이다.

**두 가지 순서가 가능하다:**

- **(가) 지금 배선** — 재기동 즉시 관측이 화면에 뜬다. 배너 3상태 중 「미배선 → 0건 →
  n건」 전이를 실제로 보게 되므로 계측이 맞는지 첫날에 확인된다.
- **(나) GP 거래가 쌓인 뒤 배선** — 만들자마자 값이 보인다. 다만 그때까지 GP 손익은
  `challenger.db` 직독으로만 볼 수 있다.

⇒ **(가)를 권고한다.** 배너 3상태는 값이 없을 때 가장 잘 검증된다 — 「미배선」과
「0건」을 가르는 것이 이 계측의 존재 이유이고, 그 둘은 GP가 돌기 시작하면 다시 볼 수
없는 상태다.

## 6. 남는 위험 / 미결

- ⚠ **GP는 가상손익이다.** 체크하면 그 날 수치가 실적이 아니게 된다 — 배너·셀 마커가
  유일한 방어선이다. 전환기준 ① 판정에는 절대 쓰지 말 것.
- ⚠ **`challenger_trades.pnl_pt` 시계열은 2026-09-10에 불연속**이다(556차 비용 정규화).
  패널이 90일 창을 보므로 **앞뒤 세대가 한 화면에 섞인다.** 세대는 행마다
  `commission_rate_used`가 명시하므로, 필요하면 배너에 세대 혼재 여부를 병기할 것.
- ⚠ GP 관측 60거래일 시계는 **이 PC 기준으로 따로 센다**(556차 O-2) — MW0601의
  2026-09-10을 그대로 쓰지 말 것.
- 미결: 주별·월별 집계에도 GP를 합칠 것인가. 일별과 다른 정책을 쓰면 화면 안에서
  단위가 갈린다 — **일별과 같게 하는 것을 기본**으로 하되 착수 시 확인할 것.
