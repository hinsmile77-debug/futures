## 1. 초판 서술 정정 — "BLAS 손상"이 아니다

`GOLDEN_POWER_실증검증_및_활용제안_MW0601-20260907.md` §10-1 과 §9 의
**"py310_64 numpy BLAS 손상"** 은 부정확한 서술이다. 실측:

| 실행 방식 | `np.corrcoef` |
|---|---|
| `envs\py310_64\python.exe -c ...` (활성화 없음) | ✗ `0xC06D007F` |
| 같은 명령 + `PATH` 앞에 `<env>\Library\bin` | **✓ 정상** |
| `conda run -n py310_64 python -c ...` | **✓ 정상** |

**패키지는 멀쩡하다.** 고칠 대상은 numpy 가 아니라 **호출 방식**이다.
⚠ 이 정정을 반영해 원 보고서 §9·§10 을 갱신했다.

## 2. 고장 경계 — 무엇이 죽고 무엇이 사는가

py310_64 를 활성화 없이 실행한 상태에서 연산별 생존 여부:

| 연산 | 결과 | 이유 |
|---|---|---|
| `np.sum`, 원소별 연산 | ✓ | BLAS 미사용 |
| `np.dot` (1-D) | ✓ | 내부 루프, gemm 아님 |
| **`A @ B` (2-D)** | ✗ | `dgemm` |
| **`np.cov` / `np.corrcoef`** | ✗ | 내부적으로 gemm |
| **`np.linalg.*`** (`inv`·`lstsq`·`svd`) | ✗ | LAPACK |
| **`scipy.stats.spearmanr`** | ✗ | numpy 상관 경유 |
| `sklearn` HistGBM / RandomForest | ✓ | 히스토그램·트리, 행렬분해 없음 |
| `sklearn` RobustScaler | ✓ | 분위수 |

🔴 **실패는 예외가 아니라 프로세스 즉사다.** `try/except` 로 못 잡고 stderr 도 비어 있다.
따라서 **틀린 값이 나오지 않는다** — 조용한 오답이 아니라 조용한 **부재**다.
(계측 4원칙 관점에서는 차라리 다행이다. 다만 부재를 알아채는 장치가 필요하다.)

## 3. 원인 사슬

```
conda env 미활성화로 python.exe 직접 실행
  └─ <env>\Library\bin 이 PATH 에 없음
       └─ numpy → libblas.dll → (delay-load) mkl_rt.3.dll  ← 못 찾음
            └─ STATUS_DELAY_LOAD_FAILED (0xC06D007F) → 프로세스 즉사
```

실측 근거:

- `libblas.dll` / `liblapack.dll` 이 참조하는 이름 = **`mkl_rt.3.dll`** (바이너리 문자열 스캔)
- 그 파일은 `py310_64\Library\bin\mkl_rt.3.dll` 로 **존재한다** — 이름은 맞고 경로만 안 보인다
- BLAS 제공자: `libblas-3.11.0-8_h8455456_mkl` + `mkl-2026.0.0` (conda 정상 설치)

### 3-1. 상속된 PATH 는 도움이 되지 않는다 — 오히려 함정이다

`main.py` 는 `py37_32` 로 돌고(런처 `start_mireuk.bat:188` 이 `activate py37_32`),
자식 `retrain_intraday.py` 는 그 환경을 상속한다. 그런데 두 env 의 MKL 은 **파일명이 다르다**:

| env | MKL DLL |
|---|---|
| py37_32 (32-bit) | `mkl_rt.1.dll` · `mkl_core.1.dll` |
| py310_64 (64-bit) | `mkl_rt.3.dll` · `mkl_core.3.dll` |

⇒ 상속된 `py37_32\Library\bin` 에는 `.3` 이 없다. **찾을 수가 없다.**
(이름이 겹치지 않는 것이 오히려 다행이다 — 겹쳤다면 32/64비트 혼재 크래시가 났을 것이다.)

### 6-0. F-4 감사기 설계 — 손으로 관리하는 목록을 쓰지 않는다

강제 대상을 하드코딩한 목록으로 들면 **그 목록을 갱신하는 것을 또 잊는다**(이 사고와
같은 실패). 대신 저장소에서 증거를 찾아 자동 식별한다:
`.bat` 의 python 실행 줄 / **타 env** 인터프리터 spawn / 맨손 실행 안내 문구.

🔴 **`sys.executable` spawn 은 제외한다** — 같은 env 라 이 사고가 성립하지 않는다.
초판은 이것을 구분하지 않아 `compute_canary_1m_ic.py`(main.py 가 `sys.executable` 로
띄우는 py37_32 스크립트)를 오탐했다.

🔴 **numeric 사용은 전이(transitive)로 판정한다.** `retrain_intraday.py` 는 numpy 를
**직접 import 하지 않는다**(`learning.batch_retrainer` 경유) — 직접 import 만 보면
정작 이 사고의 당사자가 감사에서 통째로 빠진다. 초판이 실제로 그랬다.

### 6-1. F-2 를 함께 하는 이유 (F-1 만으로 부족한가)

F-1 은 그 스크립트 하나만 고친다. F-2 는 **`PYTHON_64_EXEC` 로 나가는 모든 자식**을
고친다. 448차 모듈 docstring 이 "진입점 최상단에서 부를 것"이라 적었는데, 그 규약이
지켜지는지는 **사람이 기억해야** 한다 — 실제로 `retrain_intraday.py` 에서 지켜지지 않았다.
관문에서 한 번 막으면 기억에 의존하지 않는다.

⚠ **둘 다 한다.** F-2 만 하면 스케줄러가 직접 부르는 `retrain_eod.py` 계열이 안 막히고,
F-1 만 하면 다음에 추가되는 자식이 또 빠뜨린다.

### 6-2. F-2 의 위험과 완화

`main.py` 는 라이브 매매 프로세스다. `Popen` 에 `env=` 를 넘기면 **환경을 병합이 아니라
대체**하므로 `os.environ.copy()` 로 시작해야 한다. 실수하면 재학습이 통째로 실패한다.

완화:
- 환경 구성은 `utils/dll_bootstrap.py:child_env_for()` 라는 **순수 함수**로 분리하고
  단위테스트로 고정한다(`main.py` 안에서 즉석 조립하지 않는다).
- 조립 실패 시 **`env=None` 으로 폴백**해 현행 동작을 그대로 유지한다 —
  이 수정이 재학습을 새로 깨뜨릴 수 없게 한다.
- `retrain_intraday.py` 첫 줄에 `[DLL] PATH 보강` 로그를 남겨 **실제로 적용됐는지**
  다음 재학습 로그에서 눈으로 확인한다(계측 4원칙 ④ — 폴백 가시화).

## 8. 이 건이 드러낸 구조적 교훈

**"환경이 손상됐다"는 진단은 대개 틀린다.** 실제로는 **호출 방식**이 다른 경우가 많다.
이번에도 448차가 이미 같은 결론에 도달해 모듈까지 만들어 뒀는데, 초판이 그것을 모른 채
"패키지 손상"으로 적었다. 재설치 같은 파괴적 조치로 갔다면 멀쩡한 학습 환경을 망가뜨릴
뻔했다.

**교훈**: 크래시 코드(`0xC06D007F`)를 먼저 해석하고, **같은 증상의 기존 기록을 저장소에서
검색한 뒤** 조치를 정한다. `campaign_steps.py:238` 은 이미 그 코드를 문자열로 안내하고
있었다 — 검색 한 번이면 닿았다.
