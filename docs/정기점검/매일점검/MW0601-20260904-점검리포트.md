### 🔵 덤으로 찾은 것 — 아침마다 기록이 사라지던 원인을 특정했습니다 (이상점 1-1 / F-1)

G-1 계측을 붙이려고 저장 경로를 전수로 훑던 중 원인이 나왔습니다.

- **어디**: `strategy/runtime/session_recovery_service.py:120-129` `increment_session()`
- **무엇**: 저장된 날짜가 오늘과 다르면(= **새 거래일 첫 기동**) 상태를 합치는 게 아니라
  **다섯 개 키만 담은 새 통을 만들어 통째로 갈아끼웁니다.** 어제 저녁 재훈련 프로세스가
  써둔 두 기록은 그 다섯에 없으므로 그 순간 사라집니다.
- **장전 절이 세운 가설 (b)**(「날짜 전환 로직이 다른 키까지 초기화할 가능성」)와 정확히
  일치합니다. 반대로 가설 (a)(호출부 경합)는 **약해집니다** — `main.py` 쪽 저장 호출
  6곳은 전수 확인 결과 전부 "읽고 → 고치고 → 다시 쓰기"라 남의 키를 지우지 않습니다.
- **영향**: 지금까지 실거래 피해는 없었습니다. 보조 확인 절차(마커 파일 직접 열기)가
  매번 대신 작동했습니다. 다만 그 보조 절차 하나에만 의존하는 상태입니다.
- **영향(기술)**: 새 거래일 첫 `increment_session()` 호출이 `p8_last_success_date`·
  `eod_retrain_ok_date`를 누락한 dict 를 `_write_session_state()` 에 넘긴다. 두 키는
  자기 날짜 문자열을 값으로 갖고 소비처(`[PreRetrain]` `main.py:5640`, EKS 진단
  `main.py:8493`)가 그 날짜를 비교하므로, 보존해도 "옛 성공이 오늘 성공으로 보이는"
  역방향 사고는 생기지 않는다.

🔴 **그런데 오늘은 고치지 않았습니다.** 장전 절 F-1 이 회귀 위험 칸에 *"원인을 못 찾은
채로 성급히 고치면 역방향 사고를 만들 수 있다 — 원인 규명이 먼저다"* 라고 못박았고,
검증 기준도 *"3일 연속 재현되면 확정"* 으로 사전에 정해뒀습니다. 원인 후보가 특정된 것과
확정은 다릅니다. 대신 **내일 아침이 자동으로 답을 줍니다** — G-1 이 붙었으므로, 이 경로가
맞다면 09-05 첫 기동 로그에 다음 한 줄이 나옵니다:

```

```

이 줄이 나오면 원인 확정이고, 수정은 **다섯 키 통을 새로 만들지 말고 두 마커를
이어받게 하는 것** 한 곳입니다(구현계획은 `dev_memory/NEXT_TODO.md` 532-5).
이 줄이 **안 나오면** 원인은 다른 곳이며, 그때는 `retrain_eod.py`(다른 파이썬 프로세스)
