### 1-4 (P1, 신규) 원인이 불분명한 `.git/index.lock` 발생 — 판정보류, 지우지 않음

**증상**: 12:26:45에 증거 수집을 마친 시점에는 `.git/index.lock`(저장소 쓰기 작업 중임을 나타내는 표시 파일)이 없었다 — 수집기 자체 점검 문구가 "이 수집 실행은 락을 만들지 않았다"였다. 그런데 12:27:27에 0바이트 락 파일이 새로 생성된 것을 12:27~12:30 사이 세 차례 재확인으로 발견했다.

**근거**:
```
$ stat .git/index.lock
Modify: 2026-09-18 12:27:27

$ python scripts/git_lock_guard.py --check   (12:27 재확인)
futures  HOLD  판정보류 — 나이 103초 <= 임계 600초(아직 실행 중일 수 있다)

$ python scripts/git_lock_guard.py --check   (12:30 재확인)
futures  HOLD  판정보류 — 나이 160초 <= 임계 600초(아직 실행 중일 수 있다)
```
이 세션이 그 사이 실행한 git 명령은 전부 `--no-optional-locks`가 붙은 읽기 전용 명령(`branch`·`status`·`log`)과 `ls`뿐이며, 락을 만들 수 있는 명령(옵션 없는 `diff`/`status`, 또는 `--no-optional-locks` 없는 명령)은 실행하지 않았다. 이후 `git --no-optional-locks diff --ignore-space-at-eol --stat`도 락이 있는 상태에서 정상 실행됐다(옵션이 있으면 기존 락 유무와 무관하게 동작). 즉 **이 세션이 만든 락이 아니다.**

**기준 위반**: SKILL.md §0 "git 호출 규약" — 락이 생기면 안 되는 상황인데 생겼다. `scripts/git_lock_guard.py`가 정한 "나이 600초 이하면 판정보류, 지우지 말 것" 규칙을 그대로 따랐다.

**영향(평문)**: 지금 당장 거래나 프로그램 동작에는 영향이 없습니다. 다만 저장소를 만지는 다른 작업(다른 점검 세션, 사용자의 편집기·Git 프로그램, 또는 아직 끝나지 않은 무언가)이 동시에 돌고 있을 가능성이 있어, 원인을 확인하기 전까지는 이 잠금 파일을 지우면 안 됩니다.

**영향(기술)**: `.git/index.lock`이 남아 있으면 이후 이 저장소에 대한 쓰기성 git 명령(`commit`·`add` 등)이 실패한다. 이 세션은 규약상 어차피 커밋을 하지 않으므로 이 세션의 작업에는 지장이 없다. 원인 후보는 ① 사용자 컴퓨터에서 별도로 도는 IDE·Git 클라이언트의 백그라운드 상태 갱신 ② 알려지지 않은 병행 점검 세션(다만 `git --no-optional-locks log --since` 재확인 결과 오늘 커밋은 0건이라, 다른 세션이 커밋까지 진행한 것은 아니다) ③ SKILL.md가 이미 경고한 리눅스 샌드박스 마운트 경유 `unlink` 실패 계열(다만 이번엔 이 세션이 원인이 아니라는 점이 다르다). 나이가 임계(600초)를 넘는 12:37 이후 `python scripts/git_lock_guard.py --check`를 다시 돌리면 `STALE`(회수 가능) 또는 계속 `HOLD`(실행 중)로 갈릴 것이다.
