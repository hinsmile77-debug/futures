## 3. 고도화 방안

### G-1. 포지션 상태 파일(`position_state.json`)에 회전 백업 도입

- **관측 근거**: 오늘 이월 포지션의 원출처를 조사하려 했으나, 상태 파일이 청산 즉시 덮어써져 "언제 이 포지션이 생겼는가"를 보여주는 이전 스냅샷이 전혀 남아있지 않았다. 552-10·552-11이 "재시작이 상태를 지운다"는 같은 계열의 문제를 이미 두 건 고쳤는데, 이번 것도 본질적으로 같은 유형(상태를 덮어쓰기 전 스냅샷을 안 남긴다)이다.
- **제안 내용**: `position_state.json`을 덮어쓰기 전에 `position_state_prev.json`(1세대) 또는 타임스탬프가 붙은 회전 백업(예: 최근 3개)을 남긴다.
- **기대 효과**: 다음에 유사한 "출처 불명 포지션" 사건이 생기면, 상태 파일의 이전 세대를 바로 열어 진입 시점·손절가·수량을 즉시 확인할 수 있다.
- **비용·위험**: 낮음(파일 I/O 소량 추가). 디스크 용량 영향 미미(단일 JSON 파일).
- **선행 조건**: 없음.
- **우선순위 제안**: 이번 주.

### G-2. `[ExternalEntry]`류 감지 로직을 "엔진 기동 전 이미 존재하던 포지션"까지 확장

- **관측 근거**: 기존 536-1의 외부 진입 감지(`[체결동기화] 외부진입`)는 엔진이 살아있는 동안 실시간 체결을 관찰해 감지하는 방식이라, 오늘처럼 엔진 기동 **이전**에 이미 존재하던 포지션은 감지 경로를 타지 않고 "복원"으로만 처리된다. 이 사각지대가 오늘 1-1의 원인 규명을 어렵게 만든 핵심 요인이다.
- **제안 내용**: 포지션 복원 시점에 `entry_source`가 없거나 확인 불가능하면, 실시간 체결 중 감지되는 외부 진입과 동일한 심각도(현재 ERROR + Health CRITICAL, 536-2 참고)로 경보를 올린다.
- **기대 효과**: "기동 전 원인불명 포지션"과 "기동 중 외부 진입"을 같은 심각도로 다뤄, 오늘 같은 사례가 조용히 INFO/WARNING으로만 지나가지 않게 한다.
- **비용·위험**: 오탐 가능성 — 정상적으로 시스템이 만든 포지션인데 `entry_source` 필드가 어떤 이유로든 비어있는 경우(구버전 상태 파일 등)까지 과도하게 경보를 울릴 수 있다. 도입 전 최근 상태 파일 포맷과의 하위 호환성 확인 필요.
- **선행 조건**: F-2(로그 가시화)가 먼저 적용돼 있어야 이 경보의 기준 데이터가 쌓인다.
- **우선순위 제안**: 536-2(기존 P2 고도화 제안)와 통합해 주간회의에서 논의.

## 2. Fix 작업 구현계획 (장후 갱신)

### F-1 (갱신). ProfitGuard Tier4 래치를 "당일 영구"가 아니라 "정정 가능한 재평가"로 바꿀지 여부 — P1 · 대응 이상점 1-8

- **원인 가설**: 현재 `_TierGate._halted`는 한번 True가 되면 그 날은 절대 재평가되지 않는 순수 래치다. 오늘처럼 애초에 `current_pnl` 계산 자체가 오염됐던 경우, 오염이 걷힌 뒤에도 래치는 그대로 남는다.
- **변경 파일**: `strategy/profit_guard.py` — `_TierGate.check()` 및 `_halted` 필드. 예: 래치 트리거 당시의 `current_pnl` 스냅샷을 함께 저장해두고, 이후 그 스냅샷을 구성한 거래 중 `artifact`/`manual`로 사후 재분류된 것이 있으면 **1회 재평가 기회**를 주는 경로 추가.
- **회귀 위험**: **크다.** ProfitGuard의 존재 이유는 "하루 이익을 지키기 위해 매매를 멈추는 것"인데, 재평가를 허용하면 반대로 "멈춰야 할 때 다시 여는" 방향의 오작동이 생길 수 있다. 신중한 설계가 필요하며, **먼저 섀도(로그만)로 "재평가했다면 오늘 몇 시에 풀렸을 것"을 계산해보고 사용자 검토를 거칠 것**을 강하게 권고한다.
- **절대원칙 저촉 여부**: 없음.
- **런타임 주의**: `py37_32`.
- **검증 방법**: 오늘 사례를 회귀 테스트 픽스처로 등록 — `entry_source`가 나중에 `artifact`/`manual`로 재분류된 거래가 래치 판정에 쓰였을 때의 처리 동작을 단위 테스트.
- **섀도 계측 필요 여부**: 필요(위 참조).
- **적용 시점**: 사용자 검토 후.
- **결정 필요 사항**: 래치를 "재평가 가능"으로 바꾸는 것 자체가 리스크 정책 변경 성격이 있어 **사용자 판단이 필요하다** — 이번 사고처럼 드문 오염 사례 하나 때문에 안전장치의 "일단 멈추면 그날은 안 푼다"는 보수적 설계 철학을 바꿀 가치가 있는지부터 사용자가 결정할 사안.
