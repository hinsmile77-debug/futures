### 2-1. `.git/index.lock` 해소 — 이상점 1-2 처분

**증상(장전)**: 장전 점검이 `.git/index.lock`(0바이트, 저장소 저장을 막는 잠금 파일)을 스테일(오래돼 무효)로 확정했지만, 회수 명령(`--reclaim`)이 "권한 없음"(`Operation not permitted`)으로 실패해 지우지 못했다.

**이번 장중 재확인**: 같은 락이 그대로 남아 있었다(나이 약 3.5시간, `python scripts/git_lock_guard.py --check` → `STALE 스테일 확정 - 0바이트 · 3.5시간 · git 프로세스 0개`). `--reclaim`을 다시 시도해도 똑같이 `[Errno 1] Operation not permitted`로 실패했다.

**조치**: 스킬 정본이 지정한 우회 절차(`references/invariants.md` §0-B — 잠금 파일을 "지우는 것" 대신 같은 폴더 안에서 "다른 이름으로 옮기는 것")를 그대로 실행했다.

```
mv .git/index.lock .git/index.lock.stale.5
```

이 코웍(리눅스 샌드박스) 마운트는 파일을 지우는 동작(`unlink`)은 막지만 이름을 바꾸는 동작(`rename`)은 허용하기 때문에, 이 명령은 오류 없이 성공했다. 직후 `python scripts/git_lock_guard.py --check`가 `OK index.lock 없음`으로 판정을 바꿨다. **이번 장중 세션에서 실제 `git commit`은 실행하지 않았다** — 장중 규정(코드·저장소 변경 금지)에 따라 잠금 정리만 하고 커밋 자체는 시도하지 않았다.

**영향**: 지금부터 이 저장소는 다시 저장(커밋)이 가능한 상태입니다. 장전 리포트의 "사용자 조치 1번"(탐색기에서 직접 지워달라는 요청)은 더 이상 필요하지 않습니다.

**영향(기술)**: `.git/index.lock`이 `index.lock.stale.5`로 이름이 바뀌어 git이 더 이상 이를 잠금으로 인식하지 않는다. 원본 0바이트 파일 자체는 저장소 폴더 안에 이름만 바뀐 채 남아 있으나(무해한 잔여물), 다음 커밋 시 신경 쓰지 않아도 된다.

**처분**: ✅ 해소(이상점 1-2). 근거: `git_lock_guard.py --check` 재확인 결과("OK index.lock 없음").

## 고도화 방안 (장중 갱신)

### 방안 3. `git_lock_guard.py --reclaim`이 회수 실패 시 자동으로 `mv` 우회를 시도하게

**근거**: 오늘 장전·장중 두 세션 모두 같은 순서(① `--reclaim` 실패 확인 → ② 사람(또는 점검 세션)이 `mv`로 우회)를 반복했다. `references/invariants.md` §0-B에 이미 문서화된 절차이므로 스크립트 안에 자동화하지 못할 이유가 없다.
