## §2 이상점

### 1-1 🆕 [P1] 부팅 직후 DB 초기화가 수 분간 끝나지 않는다 — 정상 18–20초 대비 10배 이상

- **증상**: 10:28 세션 ≥150초, 10:35 세션 ≥210초 동안 같은 줄에서 멈춘 채, 둘 다 완료 로그 없이 종료.
- **근거**: `crash_fault.log` 행 감지 덤프 12회 전부 동일 스택
  ```
  utils/db_utils.py, line 401 in _migrate_predictions_db
  utils/db_utils.py, line 200 in init_predictions_db
  utils/db_utils.py, line 4877 in init_all_dbs
  main.py, line 20809 in main
  ```
  401행은 `predictions` 전 행에 거는 역채움 `UPDATE … WHERE up_prob IS NULL OR down_prob IS NULL OR flat_prob IS NULL` 문(인덱스 없음 → 전수 스캔)이다.
- **기준선(실측)**: `20260922–24_SYSTEM.log`에서 `[FaultHandler] 활성화` → `[System] DB 초기화 완료` 간격은 **17–21초**(20회 중 18회), 1초가 2회. 이 기간 행 감지 덤프는 **0건**이었다.
- **재현 시도(오늘 10:5x, 장외)**: 같은 DB의 복사본에 py37_32(SQLite 3.38.2)로 같은 UPDATE → **0.59초, 대상 0행**.
  `predictions` 133,572행, `features` 열 합계 **454MB**(DB 전체 1.29GB). 대상 행이 0이라 이 UPDATE는 매 기동마다 **아무것도 안 고치면서 454MB를 훑는 작업**이다.
- **원인: 미확정 — 유력 가설 3개(정합성 미확인)**
  1. **부팅 직후 콜드 캐시 + 보안 모듈 I/O 경합** — 두 세션 모두 부팅 3–4분 안이었고, 같은 시각 Cybos 보안 모듈 `TEFWP.exe`/`TEFWP64.exe`가 **반복 크래시**(10:23:45–10:35:44, 0xc0000005/0xc000041d 8건)했다. 다만 C:는 MX500 SSD라 454MB 콜드 읽기만으로 3분 반은 설명이 약하다.
  2. **비정상 종료 뒤 WAL 복구** — 10:31 전원 끄기가 10:28 세션을 UPDATE 도중 죽였다. 그러나 10:35 시점 `-wal`은 0바이트였고, **10:28 세션은 비정상 종료 이전 부팅에서 이미 멈춰 있었다** → 이것만으로 두 번 다 설명되지 않는다.
  3. 잠금 대기 — **반증됨**: `get_conn` busy_timeout이 10초라 잠금이면 10초 뒤 예외로 끝났어야 한다. 3분 넘게 같은 줄에 있을 수 없다.
- **10:35 세션의 종료 원인도 미확정**: 크래시 이벤트·faulthandler 치명 트레이스·`[CLEAN EXIT]` 모두 없다 → 외부에서 강제 종료(창 닫기·작업관리자)된 형태. 사용자가 멈춘 줄 알고 닫았을 가능성이 가장 높으나 확인하지 못했다.
- **기준 대응**: 계측 4원칙 ④(폴백·지연 가시화) — 기동 단계별 소요시간이 로그에 없어 「DB 초기화가 몇 초 걸렸는지」를 매번 두 줄의 시각 차로 역산해야 한다. 절대원칙 §1·§2와 직접 저촉은 없음(오늘 휴장).
- **영향**: 평일 아침에 PC를 재부팅한 직후 미륵이를 켜면, 화면이 뜨기까지 몇 분이 걸리거나 멈춘 것처럼 보여 사람이 꺼 버릴 수 있다. 08:40 기동이면 개장까지 여유가 있지만, **장중 재기동(동결 감시 → 강제종료 → 런처 재기동)** 경로라면 그만큼 매분 판단·청산 감시가 빈다.
- **영향(기술)**: FZ-1/FZ-2 동결 감시 → 하드 종료 → RESTART_LOOP 왕복(실전 전환 기준 ②ⓑ)의 복구 시간에 이 초기화 시간이 그대로 더해진다. 정상 18–20초도 이미 행 감지 주기(30초)의 2/3다. 성장하는 `predictions.features`(454MB)가 매 기동 풀스캔 대상이다.
