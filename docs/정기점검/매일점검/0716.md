## 1. 딥다이브 결과 — 비대칭의 두 가지 코드적 원인

### 원인 ① TP/Stop 배수 설계 자체가 비대칭 (`config/settings.py:671-698`)

```python
ATR_STOP_MULT = 1.5                                   # 손절: ATR × 1.5
ATR_HORIZON_TP1_MULT = {"1m":0.3, "3m":0.5, "5m":0.7}  # 1차 목표(호라이즌별)
ATR_TP2_MULT = 1.5                                     # 2차 목표: 손절과 정확히 1:1
ATR_TP3_MULT = 2.5                                     # 3차 목표: 1.67:1
PARTIAL_EXIT_RATIOS = [0.33, 0.33, 0.34]
```
5m 기준 첫 이익실현선(TP1)이 손절폭의 절반도 안 되는 0.47R 지점에서 끊긴다.

### 원인 ② (더 결정적) 사이징이 항상 1계약으로 바닥나 분할청산 자체가 무력화

`Sizer` 로그 기준: 기본리스크 300,000원 × 신뢰도배수(0.6) × 레짐배수(0.8) = 유효리스크
144,000원. 손절폭(4~6pt) × pt_value(50,000원) ≈ 계약당 리스크 200,000~300,000원 →
144,000 ÷ ~250,000 < 1 → **최소 1계약 강제**. 7/15 8건 전부 1계약.

`main.py:10233`(당시 라인) `if total_qty == 1 and stage == 1:` — 1계약 포지션이 TP1에
닿으면 "33% 부분청산"이 아니라 `arm_tp1_single_contract_with_mode()`로 대체되는데,
기본 모드가 `"breakeven"`(실현이익 0)이었다. 그 결과 실전에서 벌어지는 경로는 3가지뿐:

| 경로 | 결과 | 7/15 사례 |
|---|---|---|
| TP1도 못 찍고 반전 | 풀 손절 (-1.5R) | 4건 전부 (-4~5pt대) |
| TP1 찍고 반전 | 본전+α (+0.1~0.2R) | 2건 |
| TP2까지 논스톱 | 전량 익절 (+1.5R) | 1건 |

→ 손실은 항상 최대 리스크 단위, 이익은 대부분 0.1~0.2R로 캡. PF 0.36은 이 회로의
필연적 산출물.

### 부가 발견 — 신호소멸청산이 몽키패치에 가려 나흘도 못 살고 삭제됨

   죽은 코드.

## 2. 개선 완료 (2026-07-16, 339차)

### ✅ TP1 1계약 보호모드 기본값 `breakeven` → `atr_profit`

8개 지점 통일: `main.py:496`(초기값), `main.py:_restore_tp1_protect_mode_setting()`,
`main.py:_on_tp1_protect_mode_changed()`, `main.py:_ts_execute_partial_exit()`(실행시점
fallback), `dashboard/main_dashboard.py`(ExitPanel 기본값·fallback 2곳),
`strategy/runtime/session_recovery_service.py`(세션 복구 fallback 2곳),
`data/session_state.json`(실제 저장값 — 코드 기본값만 바꾸면 이미 저장된 값을 그대로
로드하므로 함께 갱신 필요).

`atr_profit` 모드는 TP1 도달 시 손절가를 진입가가 아니라 `진입가 + ATR×0.25`로
이동 — 반전해도 스크래치(0)가 아니라 소액 확정이익으로 마감되도록 함.
**라이브 미검증** — 다음 TP1 히트 케이스에서 `[SingleContractTP1] ... mode=atr_profit`
로그 확인 필요.

### ✅ 신호소멸청산 — shadow-only 기록으로 복구 (실거래 청산 액션 아님)

`main.py:_ts_check_exit_triggers()` TP3 체크 직후(3.5순위)에 반대신호 감지 블록
추가 — `signal_decay_exits`에 counterfactual만 INSERT하고 `_send_broker_exit_order`/
`close_position`은 호출하지 않음. 같은 포지션(entry_time)당 1회만 기록.

복구 방향을 "즉시 실청산"(290차 원안)이 아니라 shadow로 정한 이유: `signal_decay_exits`
테이블 자체 주석("리포트 전용 계측 테이블 — 실거래 의사결정에 관여하지 않는다",
`utils/db_utils.py`)과 `VALIDATION_CAMPAIGN["signal_decay"]`(§3-5,
`config/settings.py`, 이미 `min_samples=10` 사전등록)가 애초부터 shadow-first 설계였음.

**주간 검토 체계는 새로 안 만들고 기존 걸 연결**: `scripts/generate_validation_
campaign_report.py`의 `resolve_and_eval_signal_decay()`가 이미 매주 금요일 EOD
체인에서 자동 판정하고 `data/validation_campaign_report.md` [4]번 항목에
PASS(누적 saved_pts≥0)/FAIL(음수 → conf 임계 강화 권고)/INSUFFICIENT(n<10)를
출력하는 구조가 완성돼 있었음 — 기록(write)만 복구하면 됐음.

**라이브 미검증** — 반대신호 발생 시 `[SignalDecayShadow]` DEBUG 로그 + 테이블
신규 행 적재 확인 필요. `min_samples=10` 도달 전까지 리포트는 "표본 부족" 보류가 정상.

dev_memory 등록: `DECISION_LOG.md`/`NEXT_TODO.md` 2026-07-16(339차) 항목.

## 3. 개선 예정 (미착수 — 우선순위순)

### 🥈 신호소멸청산 채택 여부 — 매주 금요일 주간회의 안건 (진행 중, 자동)
`resolve_and_eval_signal_decay()` 판정 결과를 보고 실거래 청산 액션으로 전환할지
수동 결정. 4주 누적("아낀 pt − 놓친 pt") 기준이므로 최소 4주는 shadow 관찰 필요.
NEXT_TODO에 "DONE 처리 전 삭제 금지"로 등록해 CB②/FP-CRITICAL처럼 방치되지 않도록
안전장치를 걸어둠.

### 🥈 TP1을 물리적 부분청산 대신 "회계적 분할청산(synthetic partial)"으로 전환
Cybos 최소 체결단위가 1계약이라 실제로 못 쪼개더라도, 손익 기록/DB 레벨에서는
"포지션의 1/3에 해당하는 pt를 TP1에서 확정"하고 나머지 2/3만 트레일링을 계속
태우는 회계 처리가 가능함. 계약을 못 쪼갠다는 물리적 제약이 "이익을 못 챙긴다"는
결과로 이어질 필요는 없음.

### 🥈 TP1 배수를 Stop과 최소 1:1 근처로 재조정
5m TP1을 0.7R → 1.0R대로 올리거나, 1계약 상황에선 TP1 개념을 없애고 곧장
TP2(1:1) + 트레일링만 쓰는 단순화 검토.

### 🥉 사이징 파라미터 vs 분할청산 설계의 정합성 결정
늘 1계약으로 바닥나는 현재 리스크 파라미터(기본리스크 300,000원)로는 "33/33/34%
3단 분할"이라는 설계 자체가 무의미. ⓐ 기본리스크를 올려 실제 2~3계약이 나오게
하거나, ⓑ 1계약 전용 경로(atr_profit 등)를 정식 노선으로 확정 — 둘 중 하나를
명시적으로 택해야 함. CLAUDE.md §8 `SIZING_TARGET_CAPITAL_ENABLED` 실전전환
재검토 항목과 같은 시점에 함께 정리하는 게 효율적.
