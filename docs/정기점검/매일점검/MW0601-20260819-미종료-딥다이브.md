## 2. 원인 분석 — 증거 체인

### 2-1. 스핀 지점: 파이썬 코드가 아니라 Qt 이벤트 루프의 네이티브 내부

`logs/crash_fault.log`(faulthandler 30초 주기 전 스레드 덤프, 230차)가 결정적 증거다.
동결 구간(13:41~16:05)의 **모든** 덤프에서 메인 스레드는:

```
Thread 0x00006180 (most recent call first):
  File "main.py", line 12666 in run        ← _qt_app.exec_()
```

**파이썬 콜백 프레임이 하나도 없다.** 즉 어떤 파이썬 핸들러 안에서 도는 게 아니라,
`exec_()` 아래 **네이티브(C) 코드 안에서** 스핀한다. `Responding=False`이므로
GetMessage/PeekMessage 호출 자체가 끊긴 상태 — 어떤 메시지 핸들러(네이티브) 안에
들어간 채 영원히 반환하지 않으며 내부에서 CPU를 태우고 있다. GIL은 주기적으로 풀리므로
다른 파이썬 스레드(워커의 완료 로그, slack_queue, db_writer 등)는 살아서 움직였다 —
이것이 "13:51:22에 워커 로그가 남은" 이유다.

### 2-2. 워커는 가해자가 아니라 1차 피해자에 가깝다 — 단 기동 시점이 방아쇠와 <1초 일치

같은 fault 덤프에서 워커 스레드(0x62b4)는 10분 내내:


병리 상황의 산물이다. **다행히 이 값은 저장되지 않았다** — `result_ready`는 Qt 큐드
시그널이라 죽은 메인 루프에 영영 배달되지 못했다.

**시점 상관**: 동결 개시(13:41:21±1s)와 워커 기동(13:41:20.99)이 1초 이내로 일치하고,
그 초에 시작된 신규 활동은 워커가 유일하다. 게다가 매분 :21은 수급 폴링
(`_fetch_investor_data` — BlockRequest 백그라운드 스레드 2회 생성/소멸)·지수 폴링과
**위상이 겹치는 초**다(타이머들이 기동 시 같은 위상으로 시작). 워커 기동(CoInitialize +
`Dispatch("Dscbo1.OptionMst")` 크로스 아파트먼트 마샬링)이 메인 STA의 다른 COM 활동과

## 3. "종료되지 않은" 메커니즘 — 전부 한 스레드에 있었다

정상 종료 경로: `_scheduler_tick`(30초 QTimer) → 15:40 `daily_close()` →
`_schedule_shutdown()` → `QTimer.singleShot(15s, _auto_shutdown)` → `_qt_app.quit()`.
**이 사슬 전체가 동결된 메인 스레드의 QTimer 위에 있다.** 그래서 종료가 영영 오지 않았다.
`session_state.json`의 `auto_shutdown_done_date`가 빈 값인 것과 정합한다.

같은 이유로 아래 안전장치들도 **전부 동시에 무력화**됐다:

| 안전장치 | 위치 | 상태 |
|---|---|---|
| 15:10 강제청산 (STEP 8, 절대원칙 §1) | 매분 파이프라인 (메인) | 죽음 |
| 453차 D2 `_ts_scheduler_force_exit_net` — "분봉·틱이 전부 죽어도 이 타이머는 돈다" | `_scheduler_tick` 30초 QTimer (메인) | **죽음 — 전제 불성립** |
