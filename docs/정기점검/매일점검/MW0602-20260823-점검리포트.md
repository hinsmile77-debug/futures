# 부록 C. ↩️ 정정 — 커밋 실패 원인은 "잔존 lock"이 아니다 (부록 A 정정)

> 대원칙 B-①에 따라 **부록 A 본문은 고치지 않았고**, 그 절 머리에 포인터 한 줄만 달았다.
> *왜 그때 그렇게 판단했는가*가 남아야 정정의 가치가 있기 때문이다.

## C-1. 무엇이 틀렸나

부록 A는 원인을 **"다른 git 프로세스가 남긴 잔존 lock"** 으로 적고, 처방으로
`Remove-Item …\.git\index.lock -Force` 를 사용자 조치 1-1번에 올렸다.

**사용자가 그것을 실행했고, lock은 실제로 사라졌다. 그런데 커밋은 여전히 실패했다.**
`git status` 를 한 번 돌리자마자 같은 lock이 다시 생겼다.

## C-2. 진짜 원인 — 이 마운트는 `unlink` 를 금지한다

```
$ ls -ld .git                      drwx------ … (내 소유)
$ touch .git/__probe               → 생성 OK
$ rm -f  .git/__probe              → rm: cannot remove: Operation not permitted
$ mv .git/a .git/b                 → rename OK
$ touch <워크트리>/__wt_probe && rm → 삭제 실패 (워크트리도 동일)
```

즉 **파일 생성과 rename은 되는데 삭제만 안 된다.** `.git/` 만이 아니라 **작업 폴더
전체**가 그렇고, **내가 방금 만든 내 소유 파일조차** 못 지운다.

**그래서 이런 고리가 생긴다.**

1. 사용자가 `index.lock` 삭제 → 정상
2. 내가 `git status` 실행 → git이 **optional lock** 으로 `index.lock` 생성
3. status 종료하며 그 lock을 **unlink 시도 → 실패**
4. stale lock 잔존 → 다음 `git add` 가 `File exists` 로 거부

⇒ **내가 상태를 확인하는 행위 자체가 lock을 다시 만들고 있었다.** 사용자가 몇 번을
지워도 같은 일이 반복된다. **부록 A의 처방은 구조적으로 성립하지 않는다.**

## C-3. 해결 — rename 이 허용된다는 점을 쓴다

```
# ① lock 이름을 옆으로 비켜준다 (삭제가 아니라 rename)
mv .git/index.lock .git/index.lock.stale.N
# ② 읽기 작업은 optional lock 자체를 만들지 않게
git --no-optional-locks status --porcelain
# ③ add / commit — 정상 경로가 rename(index.lock → index) 이라 통과한다
git --no-optional-locks add …
git --no-optional-locks commit -F -
```

`commit` 의 성공 경로는 `rename` 이므로 문제가 없다. 실패하는 것은 **정리(unlink)**
단계뿐이고, 그건 `warning:` 으로만 남고 종료코드에 영향을 주지 않는다.

**실측 결과** — 본 세션 커밋 2건 모두 이 방식으로 성공했다.
```
6ec5a13 [MW0602] 486차: 캠페인 채널 [55] 신설 … (4 files, +826)
7e6a775 [MW0602] 486차: 08-23 휴장일 점검 … (3 files, +879)
git fsck → 이상 없음
```

## C-4. 이건 오늘 처음이 아니다 — 상시 조건이다

정리하다 보니 `.git/` 에 **내가 만들지 않은 잔여 lock이 20여 개** 있다:
`index.lock.s7` · `index.lock.s8` · `index.lock.s9` · `index.lock.sB` · `index.lock.y1` ·
`index.lock.stale2`~`stale5` · `HEAD.lock.s2` · `HEAD.lock.y2` · `HEAD.lock.z2` …

이름 규칙(`.stale`, `.sN`, `.yN`, `.zN`)이 제각각인 것으로 보아 **이전 세션들이 각자
같은 벽에 부딪혀 각자의 방식으로 우회한 흔적**이다. 즉 이것은 사고가 아니라
**이 실행 환경의 상시 조건**이고, 매번 다시 발견되고 있었다.

→ 그래서 이번에는 **`references/invariants.md` 에 §0-B 로 못박았다**(F-2/486차).
다음 세션이 `git status` 부터 돌리다가 같은 자리에서 멈추지 않도록.
