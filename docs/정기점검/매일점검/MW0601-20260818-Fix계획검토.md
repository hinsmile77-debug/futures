## F-4. daily_broker_pnl 단위 명시 — 승인 + 동반 필수 3건 (신규 결함)

**전제 검증.** 스키마 `date PRIMARY KEY, pnl_krw`(`db_utils.py:2655`), gross 확정은
476차 원단위 대사로 이미 완료. 쓰기 경로 `main.py:15563~15578` 실측에서 **결함 3건 신규 발견**:

**동반 ① — 휴장일 유령 행 (이번 검토 최대 발견).**
`_yesterday = 달력 어제`(`:15567`)라 주말·휴장일에도 upsert된다. 실물(8월):
```
08-08(토) 723,000 · 08-09(일) 723,000   ← 08-07(금) 값 복제
08-16(토)  32,000 · 08-17(일)  32,000   ← 08-14(금) 값 복제
```
현재 대시보드 일별 탭은 trades 날짜로 그룹화해(`main_dashboard.py:6808`) 유령 날짜가
행으로 안 뜨므로 **실해는 잠복 상태**다. 그러나 **실전 전환 기준 ①("모의투자 4주
통산 수익률 양수")을 이 테이블 SUM으로 판정하는 순간 주말마다 직전 금요일 값이
2회씩 이중가산**된다 — 8월 실측으로 +151만원 과대(723,000×2 + 32,000×2).
F-4가 "①은 net 기준 명문화"를 목표로 하는 만큼 **이 가드 없이는 목표가 성립하지
않는다.** 조치: ⓐ upsert에 거래일 가드(해당 날짜에 predictions/trades 행 존재 여부
또는 KRX 캘린더), ⓑ 기존 유령 행 정리 — **삭제는 사용자 승인 후**(대안: `is_phantom`
플래그 후 판정 쿼리에서 제외).

**동반 ② — `pnl==0` 스킵(`:2665`).** 0원으로 마감한 거래일이 기록 불가 — "거래일인데
0원"과 "휴장"이 구분 안 된다(계측 4원칙 ②). net/commission 컬럼이 생기면 gross=0
행도 정보가 있으므로 스킵 조건을 "거래일 가드 통과 시 0도 기록"으로 재검토.

**동반 ③ — `"추정자산"` 키의 이름≠의미.** `_prev_pnl = summary.get("추정자산")`
(`:15570`)인데 실제 담기는 값은 4.9억대 자산이 아니라 **직전 거래일 실현손익**이다
(08-14 32,000 = 그날 gross와 일치, 723,000 = 08-07 값). 동작은 맞고 이름이 함정이다
— 주석 필수(브로커 TR summary 매핑 단계에서 키 이름이 어긋난 것으로 보이며, 매핑
원점 수정은 별도 확인 후).

**원안 3컬럼 설계 보완.** `commission_krw`·`pnl_net_krw`의 원천은 upsert 시점이 아니라
**EOD `daily_close()`에서 trades 합산으로 채우는 별도 UPDATE**가 맞다 — 장중 13:19
balance push 시점에는 이후 거래가 남아 있을 수 있다(오늘은 우연히 최종값). gross는
현행대로 브로커 TR, net/commission은 EOD 확정 — 두 시점을 컬럼 주석에 명기.

**구현이득 (상향).** 원안 추정(단위 격차 23,332원/일 설명)에 더해, 전환기준 ① 판정
