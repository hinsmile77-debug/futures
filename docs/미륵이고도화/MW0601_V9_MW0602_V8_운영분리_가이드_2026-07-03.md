## 왜 이렇게 하는가 (이득 요약)

미륵이에는 이미 챔피언-챌린저 패턴(15차, `challenger.db`)이 프로세스 내부에 존재한다. 이 분리는 그 패턴을 **머신 단위로 확장**하는 것이다.

- **개발 리스크 완전 격리**: MW0601의 v9 코드가 크래시·DB 오염을 일으켜도 MW0602(V8, 로컬 DB·모델 완전 별개)는 물리적으로 무관.
- **페어드 비교 데이터**: 같은 날 같은 장세를 두 머신이 각자 보므로 나중에 v9 대 v8 실측 비교가 가능(쉐도우 A/B를 한 프로세스에서 복잡하게 구현할 필요 없음).
- **롤백 단순함**: 실패 시 MW0601에서 `git checkout dev` 한 번.
- 현재는 둘 다 모의투자 단계라 "자본 리스크 분산" 이득은 아직 발생하지 않음 — 지금 이득은 **개발 안전성 + 비교 데이터 품질**. 실전 전환 후에는 여기에 진짜 챔피언-챌린저(소액 실거래 병행) 이득이 얹어진다.

### 2. `v9-dev` 브랜치 생성 (dev에서 분기)


### 4. MW0601 자동 기동 — 계속 유지 (정정)

`start_mireuk.bat`/`LAUNCH_API.bat`의 08:40/15:40 자동 기동 스케줄은 **끄지 않는다.**
MW0601은 매일 `v9-dev` HEAD를 그대로 자동 기동/청산한다 — 지금은 v9-dev가 dev와 동일하므로
그냥 V8과 동일하게 돌고, v9 변경이 하나씩 들어갈 때마다 자연스럽게 그 상태로 매일
운영/데이터 축적이 이어진다. MW0602(dev)와 처음부터 끊김 없는 페어드 비교 데이터가
쌓이는 것이 이 분리의 핵심 이득이므로, 굳이 정지시킬 이유가 없다.

**단, 딱 하나의 규칙**: main.py나 실시간 파이프라인(진입/청산 게이트, 앙상블 결정)에
영향을 주는 커밋은 **장 마감(15:40) 이후에만** `v9-dev`에 반영한다. 장중에 이런 코드를
고치는 세션은 그날 자동 기동과 겹치지 않도록 별도 임시 브랜치(예: `v9-wip`)에서 작업하고,
검증 후 장 마감 뒤 `v9-dev`로 병합해 다음날 08:40 기동이 검증된 상태를 받게 한다
(MW0602/dev에도 이미 적용 중인 "장중 코드 미변경" 원칙을 v9-dev에도 동일 적용하는 것뿐).

⚠️ **`retrain_eod.py`(15:45 자동)·`retrain_intraday.py`(장중 DriftRetrain)는 "오프라인
스크립트처럼 보이지만 실제로는 매일 스케줄대로 자동 실행되는 라이브 경로**다. W2~3에서
트리플 배리어 라벨을 `batch_retrainer.py`에 실제로 통합할 때는 "main.py를 안 건드리니
안전"이 아니라 "라이브 스케줄에 걸리는 코드"로 취급하고, 위와 동일하게 장 마감 이후
반영 + 다음날 기동 전 최소 스모크 테스트(`python -m py_compile`, 수동 1회 실행)를 거친다.

### 5. dev_memory 관리 규칙 (브랜치 분리 기간 동안)

**문제**: `dev_memory/*.md`는 git 추적 파일이라 브랜치마다 독립적으로 진화한다. `dev`(MW0602)는 계속 291차, 292차...로 V8 운영 로그를 이어가는데, `v9-dev`(MW0601)에서 같은 차수 번호를 쓰면 나중에 병합할 때 "같은 번호, 다른 내용" 충돌이 생긴다.

**규칙**:
- `dev` 브랜치의 차수 카운터(`CURRENT_STATE.md`/`SESSION_LOG.md`/`NEXT_TODO.md`/`DECISION_LOG.md`)는 **V8 운영 로그 전용**으로 MW0602가 그대로 이어간다.
- `v9-dev` 브랜치에서는 이 4개 파일을 **원칙적으로 건드리지 않는다** — 병합 시 충돌을 최소화하기 위함.
- v9 작업 로그는 지금까지 해온 방식대로 `docs/미륵이고도화/*.md`(날짜 접미사 파일)에 계속 쌓는다 — 이 폴더는 브랜치 무관하게 v9 전용 세션 로그 역할.
- 병합(`v9-dev → dev`) 시점에만 `CURRENT_STATE.md` 맨 위에 "v9 통합" 항목 하나를, **그 시점의 실제 차수**로 새로 추가한다(지금 미리 번호를 정하지 않는다).

### 6. 커밋 범위 (기존 원칙 + 확장)

기존 규칙([[feedback_git_commit_scope]]) 그대로 유지, `docs/**/*.md`를 커밋 대상(O)에 명시적으로 추가:

- **커밋 O**: `*.py`, `config/*.py`, `dev_memory/*.md`, `docs/**/*.md`
- **커밋 X**: `model/**/*.pkl`, `data/db/*.db(-shm/-wal)`, `data/*.json`, 스크립트 진단 산출물(`*_report.md`/`*_metrics.json` 등 재실행 시마다 바뀌는 것), `machine.cfg`

`v9-dev` 브랜치에서도 동일 — 재학습으로 나온 신규 pkl 등은 각 머신이 자체 생성하므로 커밋 금지.

### 7. 주기적 동기화 (V8 안전 패치를 v9-dev로 흡수)

MW0602가 `dev`에서 계속 V8 버그를 고치는 동안(291차, 292차...), 그 패치가 `v9-dev`에도 반영돼야 이미 고친 버그를 나중에 병합 시 다시 들여오지 않는다.

```
# MW0601, v9-dev 브랜치에서 — 매주 1회 또는 dev에 P0 픽스 랜딩 시
git fetch origin
git merge origin/dev
```

`rebase`가 아니라 `merge` 사용 — 공유 브랜치 히스토리 재작성 금지 원칙 준수.
