## 0. 왜 v2를 다시 고치는가

v2(2026-07-04)는 "v1의 3계층 아키텍처(L1/L2/L3) + 감사 문서(260704)가 지목한 항목"을 병합해
우선순위를 재배열한 문서였다. 그런데 v2 작성 다음날(2026-07-05), **origin/dev(MW0602)가
290차·291차 커밋으로 감사 로드맵 §8의 P0~P3 전항목을 구현**했다(순EV 리포트, Triple-Barrier·
Meta-Labeling·분위회귀 섀도우, 신호소멸청산, 지정가집행, 챌린저 부트스트랩+heartbeat, 신규
피처 4종, 대시보드 상태 스트립 등 — `docs/260704_SYSTEM_AUDIT_UPGRADE_PROPOSAL.md` §8 최신
상태 컬럼 참고). 나아가 4주 검증 캠페인 체계(섀도우 채널 합격선 사전등록·ON 정책 롤백기준·
금요일 EOD 자동 판정·**신호경로 동결령**)까지 구축했다(`260705_OFFENSE_READINESS...` §9 금지사항).

이 저장소는 이 문서 작성 시점(2026-07-05)에 `git merge origin/dev`로 위 변경사항을 v9-dev에
전부 흡수했다. 따라서 v2가 다루던 "감사 항목 구현"이라는 작업의 대부분은 **완료된 과거**이고,
v9-dev가 앞으로 해야 할 일은 이제 **감사가 다루지 않은, v1 고유의 3계층 아키텍처**로 좁혀진다.

## 2. Track L3 — 소프트게이트 점수화 (qty_ok/mode_filter_ok 병목의 실제 해법)

### 문제

`gate_blocking_report.md`(290차): 18개 게이트 중 최저 통과율이 qty_ok(9.6%)·mode_filter_ok
(11.4%). 30일 등급 분포 `{X: 5848건, C: 1912건}` — **A/B등급 0건**. 원인은 9항목 체크리스트 +
Degraded Mode(`main.py` `_classify_health_level`)·ExecutionGovernor(`tradability` 스코어)·
MetaGate(`blended_conf`)·ToxicityGate(score) 4종이 **각자 독립적으로 grade를 X로 되돌릴 수
있는 직렬 AND 구조**라는 것. dev의 `generate_gate_ablation_report.py`는 qty_ok를
`_SAFETY_OPERATIONAL_GATES`(제거 검토 제외 대상)로 이미 분류해뒀다 — 즉 dev도 "이건 안전
게이트지 손볼 대상 지표가 아니다"까지는 도달했지만, 그 뒤에 있는 **직렬 AND 자체의 재설계**는
손대지 않았다.

### 방향 — 섀도우 우선(이번 세션 범위)

기존 직렬 AND(하나라도 실패 시 X)를 **가중 점수 합산**으로 대체한 버전을 새 모듈
`strategy/entry/soft_gate_scorer.py`(`SoftGateScorer`)로 구현하되, **실거래 판정
(`_final_grade`/`_qty_display`)에는 영향을 주지 않고 병렬로 로그만 남긴다** — dev가 TB/
meta-gate/분위회귀 3채널에 적용한 것과 동일한 섀도우 우선 원칙. 재사용: `meta_gate.py`의
등급별 가중치 블렌딩(`_GRADE_CFG`, blended_conf 연속값 계산) 패턴.

### 승격 조건 (아직 미확정 — 사전등록 대상)

dev의 `VALIDATION_CAMPAIGN` 사전등록 패턴을 그대로 따른다. 이번 세션에서는 집계 스크립트
(`generate_soft_gate_shadow_report.py`)만 만들고, "점수합산 방식이 실제로 A/B 통과를 늘리면서
EV가 악화되지 않는가"의 합격선은 **표본이 쌓인 뒤 별도 세션에서 확정**한다(데이터를 보기 전에
기준을 정한다는 원칙 유지).

## 3. Track L1/L2 — 3계층 아키텍처의 잔여 부분

### 기존 인프라 재확인 (중복 구현 방지)

레짐 분류기가 이미 3개 존재한다:

| 기존 모듈 | 역할 | 한계 |
|---|---|---|
| `collection/macro/regime_classifier.py` `RegimeClassifier` | 일 1회 매크로 레짐(RISK_ON/NEUTRAL/RISK_OFF) | VIX/SP500 기반, 방향성 없음 |
| `collection/macro/micro_regime.py` `MicroRegimeClassifier` | 1분 ADX/ATR 기반 5분류(추세/횡보/급변/혼합/탈진) | 방향(UP/DN) 없음, Hurst/gap/GEX 미반영 |
| `collection/macro/intraday_tactical_regime.py` `IntradayTacticalRegime` | 장중 방어 레짐(NORMAL/DAY_RISK_OFF/CRASH) | 방향성 트렌드 판정이 아니라 리스크 오프 판정 전용 |

v1이 말하는 "L1 데이 레짐 엔진(신규)"은 이 셋을 **재구현하는 게 아니라 통합하는 애그리게이터**
여야 한다 — 위 3개 출력 + Hurst(`features["hurst"]`, 이미 계산됨) + 시가이격(`_session_open_price`
기반, 이미 계산됨) + GEX/PCR(`opt_gex_bn`/`opt_chain_pcr`, 이미 옵션체인에서 병합됨) + 첫 30분
모멘텀을 합쳐 `TREND_UP`/`TREND_DN`/`RANGE`/`CHAOS` + confidence + 히스테리시스를 출력한다.

### Track L1 (섀도우, 이번 세션 범위)

`strategy/regime/day_regime_engine.py`(`DayRegimeEngine`) 신규 — 위 통합 로직. main.py의
Layer2(IntradayTacticalRegime) 갱신 직후(약 4555행)에 매분 호출, 결과는 로그·`entry_gate_json`
저장만(정책 분기 없음). 검증 스크립트 `generate_day_regime_backtest_report.py`
(`generate_regime_postmortem_report.py` 패턴)로 최근 N일 재분류 후 방향 적중률/PnL 교차 집계 —
"이 레짐 분류가 실제로 방향 신호와 상관 있는가"가 L2 착수의 선행 증거가 된다.

### Track L2 (이번 세션 범위 밖 — L1 검증 완료 후)

레짐별 앙상블 프로파일 분기(TREND면 10·15m 호라이즌 주축+홀딩편향, RANGE면 1·3·5m 축소사이즈,
CHAOS면 전면 관망) + 청산 재설계. L1의 백테스트 리포트로 레짐 분류가 실제로 유의미하다는 근거가
나온 뒤 별도 세션에서 착수한다 — 근거 없는 레짐에 정책을 조건부로 거는 것은 v1 자신의 설계
원칙(데이터 기반 의사결정)에 위배된다.
