## 1. 발견 및 수정 — WarmupRetrain 거래일 미체크 + cybos 서버라벨 하드코딩

**증상**: 13:02 재시동(2026-07-19, 실제로는 일요일)이 "장중 재시작"으로 오판정되어
불필요한 GBM 경량 재학습 서브프로세스가 기동됨. 동시에 `[DBG CK-2b]`/`[DBG CK-3]` 디버그
로그가 `Cybos 실서버`로 찍혔는데, 몇 줄 뒤 `[Notify]`/`[Capability]`는 정확한 로직으로
`Cybos 모의투자`를 출력해 로그 자체가 모순.

**원인**:
- `main.py:2793` WarmupRetrain "장중 재시작" 판정이 `datetime.time(9,0) <= t < time(15,10)`
  시각만 확인하고 `utils/time_utils.is_trading_day()`를 호출하지 않음.
- `strategy/runtime/broker_runtime_service.py:50-51`가 cybos 브로커일 때 `GetServerGubun`
  실제 조회 없이 `server_label = "Cybos 실서버"`로 무조건 고정.

**수정**: `main.py`의 WarmupRetrain 조건에 `is_trading_day(_rst_now)` 추가.
`broker_runtime_service.py`도 cybos 분기에서 `GetServerGubun`을 실제 조회해
`"Cybos 모의투자"`/`"Cybos 실서버"`를 판정하도록 변경. 커밋 `f415c07`(v9-dev).

**검증**: 16:43 재시동 로그로 서버라벨 수정을 실측 확인(`[DBG CK-2b] ... 서버종류=Cybos
모의투자` — 이하 전 구간 일관). WarmupRetrain 거래일 체크는 16:43이 이미 `_late_restart`
(14:30 이후) 조건에 걸려 시각 조건만으로도 배제되는 케이스라 이 재시동으로는 직접
검증되지 않음 — 코드 리뷰로만 확인됨. 다음에 주말·공휴일 중 09:00~15:10 사이 재시동이
있으면 그때 실측 가능.

## 2. 딥다이브 — 남은 콘솔 mojibake 2건

같은 재시동 로그에 서로 다른 원인의 콘솔 인코딩 이상점 2건이 남아있어 원인을 분리
특정했다.

### 2-A. `'?' is not recognized as an internal or external command` (RECHECK 직후)

**딥다이브**: `start_mireuk.bat`은 BOM 없는 UTF-8 파일이고 2행에 `CHCP 65001`. 이 PC에서
`cmd.exe`로 380~411행을 원본 그대로(바이트 단위로) 잘라 재현 테스트한 결과, **매번 재현되나
매번 다른 지점에서** `'X' is not recognized as an internal or external command`가 발생함을
확인 — Windows `cmd.exe`가 `CHCP 65001` 상태에서 멀티바이트(한글) UTF-8이 밀집된 배치
파일을 파싱할 때 내부 버퍼 경계에서 줄을 잘못 끊어 읽어 그 조각을 별도 명령으로 오인
실행하는, 잘 알려진 결함. `CALL :L`(라벨 점프)을 제거하고 직접 `ECHO`로 바꿔도 동일하게
재현되어 원인이 라벨/GOTO 메커니즘이 아니라 CHCP 65001 자체의 배치 파서 결함임을 확인.

**기각된 가설 — CP949 재인코딩**: "파일을 CP949로 저장 + `CHCP 949`"로 바꾸는 흔히 알려진
해법을 동일한 바이트 단위 재현으로 실측했으나 **오히려 깨짐이 더 심해짐**(phantom 명령
개수 증가 + `占쏙옙` 형태의 이중 인코딩 깨짐 추가 발생). 이 "해법"은 검증되지 않았고
악화 위험이 실측으로 확인됨 — **적용하지 않기로 결정**.

**결정 — 방치**: 실제 운영 로그 2회(13:02, 16:43) 모두 이 에러 이후 스크립트가 정상적으로
`[OK] cybos 준비 완료` 배너와 `main.py` 실행으로 이어졌고, 재현 테스트에서도 매번 phantom
에러 이후 스크립트가 끝까지 정상 진행함을 확인 — **기능 영향 없는 순수 콘솔/로그 잡음**.
원인이 애플리케이션 코드가 아니라 Windows `cmd.exe` 자체의 결함이라 결정적으로 고칠
방법이 없고, 유일하게 검증한 "해법 후보"가 악화시킴을 확인했으므로 코드 변경 없이
known-benign으로 문서화만 하고 넘어간다. `LAUNCH_API.bat`도 동일 패턴(UTF-8, BOM 없음,
`CHCP 65001`)을 갖고 있어 같은 결함이 잠재해 있을 수 있음 — 실제 발생 시 이 문서를 참조.

### 2-B. `9 媛?李?理쒖냼???꾨즺.` (=" 9개 창 최소화 완료." 텍스트 깨짐) — 수정함

**딥다이브**: `start_mireuk.bat:74`가 `powershell -File scripts\close_other_windows.ps1`를
호출하고, 그 스크립트 47행 `Write-Host "[INFO] $minimized 개 창 최소화 완료."`가 원인.
이 PC에서 실측한 결과 Windows PowerShell 5.1은 부모 cmd의 `CHCP 65001`을 상속하지 않고
`Write-Host` 출력을 시스템 기본 codepage(CP949)로 인코딩하는 반면, 부모 콘솔은 UTF-8로
해석해 mojibake 발생. `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`을
스크립트 최상단에 추가하는 수정을 바이트 단위로 검증 — 정확한 UTF-8 바이트가 출력됨을
확인(고신뢰 픽스).

**수정**: `scripts/close_other_windows.ps1` 최상단(param 블록 다음)에
`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` 추가. 창 최소화 로직 자체는
변경 없음.

**검증**: 로컬 재현 테스트로 수정 전/후 바이트 시퀀스 직접 비교 — 수정 전 CP949 바이트,
수정 후 올바른 UTF-8 바이트(`개` = `0xEA 0xB0 0x9C`) 출력 확인. 실제 재시동 로그로는
아직 미검증(다음 실행 시 콘솔에서 육안 확인 필요).
