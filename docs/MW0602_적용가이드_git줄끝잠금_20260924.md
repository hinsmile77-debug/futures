두 git 이 다른 자로 재고 있었을 뿐이다. 진짜 위험은 오히려 **Windows 에서 깨끗하게 보이던**
LF `.bat` 이었다(MW0601: 스케줄러가 매일 돌리는 것만 14개).

`.gitattributes` 규칙(정본: futures 루트):

```gitattributes
* text=auto eol=lf          # 파이썬·에이전트가 쓰는 것에 맞춘다
*.bat text eol=crlf         # cmd.exe·PowerShell 은 우리가 안 짜는 파서 — CRLF 로 못 박는다
*.cmd text eol=crlf
*.ps1 text eol=crlf
*.xlsx binary               # 외 바이너리 명시
```

🔴 **pull 만으로는 디스크가 안 바뀐다.** `.gitattributes` 는 인덱스 규칙이다. 이미 디스크에 있는
LF `.bat` 은 다시 쓰기 전까지 LF 그대로다 → §3-4 의 `--fix` 가 필요한 이유.

### 3-3. 전수 진단 (아무것도 안 바꾼다)

```

```

출력 예(MW0601 의 06-30 사본으로 실측):

```
futures - 260630_MW0602 WARN gattr=- bat_lf=4 mixed=1 ps1_nobom=0 mount_noise=58
```

| 칸 | 뜻 | 위험 |
|---|---|---|
| `gattr` | `.gitattributes` 유무 | `-` 면 그 저장소는 규칙이 아직 없다 → pull 또는 §3-6 |
| `bat_lf` | LF 줄이 있는 `.bat`/`.cmd`/`.ps1` | 🔴 스케줄러 배치면 높음(`goto` 레이블 탐색 실패) |
| `mixed` | 한 파일에 CRLF·LF 혼재 | `.gitattributes` 가 있으면 git 에는 무해. 정리 대상 |
| `ps1_nobom` | 한글 든 UTF-8 `.ps1` 에 BOM 없음 | PowerShell 5.1 에서 한글 깨짐 |
| `mount_noise` | 마운트 git 이 줄끝만으로 「수정됨」이라 할 수 | 규칙이 들어가면 0 이 된다 |

### 3-4. 나머지 저장소 pull → 교정

저장소마다(§1 표의 브랜치):

```
cd C:\Users\<유저명>\PycharmProjects\<저장소>
git pull
python ..\futures\scripts\eol_audit.py --repo . --fix
```

`--fix` 가 하는 일:
- `.bat`/`.cmd`/`.ps1` 의 LF → CRLF, MIXED → LF. **줄끝만** 바꾸고 내용은 그대로.
- 줄끝만 바뀐 파일은 `git diff` 는 비었는데 `status` 에 M 으로 남는다 → 인덱스 stat 만 갱신
  (`git add`). 내용 변경은 스테이징하지 않는다.
- `.gitattributes` 가 없는 저장소는 건너뛴다.

확인: `git diff --cached --name-only` 가 **비어 있어야** 한다. `git status` 의 수정 개수는
교정 전과 같아야 한다(진짜 미커밋 작업만 남는다).

### 3-5. `.ps1` BOM

진단에 `ps1_nobom` 이 있으면:

```
python ..\futures\scripts\eol_audit.py --repo . --fix-bom
git add <그 파일> && git commit -m "<파일>: UTF-8 BOM 추가 — PowerShell 5.1 은 BOM 없는 파일을 CP949 로 읽는다"
```

BOM 은 내용 변경이라 **커밋이 필요하다.** MW0601 이 이미 푸시한 3개는 pull 로 받는다.

### 3-6. 원격에 규칙이 없는 저장소 (fuoption, MW0602 전용 저장소 등)

```
copy ..\futures\.gitattributes .
git add .gitattributes
git commit -m "줄끝 규칙을 저장소 안으로 (.gitattributes)" -- .gitattributes
python ..\futures\scripts\eol_audit.py --repo . --fix
```

먼저 `git ls-files --eol | findstr i/crlf` 가 **비어 있는지** 볼 것. 인덱스에 CRLF 가 있으면
`git add --renormalize .` 가 필요하고, 그건 미커밋 작업까지 스테이징하니 **작업 트리가 깨끗한 날** 한다.

## 5. pull 이 거부·충돌할 때

MW0601 에서 실제로 난 두 경우:

- **원격에 이 PC 가 안 받은 커밋이 있어 push 거부** → `git pull --rebase --autostash` 후 push.
- **autostash 복원 충돌**(backtest_hanryangi): 원격이 `docs/dev_memory/` → `dev_memory/` 로 파일을
  옮겼고, 로컬은 옛 위치 파일을 지운 채였다. git 이 「옮겨진 파일도 지워라」로 읽어 `UD` 충돌.
  해결: 옮겨진 파일은 원격 버전 유지(`git checkout HEAD -- <파일>`), stash 의 내용이 새 HEAD 에
  **이미 반영됐는지 확인한 뒤에만** `git stash drop`.

## 6. 앞으로의 규칙 (두 PC 공통)

1. **새 저장소는 `.gitattributes` 부터.** 정본은 futures 루트.
2. **스케줄러가 돌리는 `.bat`/`.ps1` 을 파이썬·에이전트로 고쳤으면 CRLF 로 저장**하거나 곧바로
   `eol_audit.py --repo . --fix`. git 은 커밋할 때 정규화하지만 **디스크는 LF 로 남는다.**
3. **CRLF 파일에 덧붙이기(append) 주의.** MIXED 의 주 경로다 — MW0601 에서 규칙을 넣은 **당일
   저녁에도** fuoption 장후 자동조치가 `dev_memory/DECISION_LOG.md`·`NEXT_TODO.md` 에 LF 줄을
   덧붙여 MIXED 를 만들었다. `.gitattributes` 가 있으면 git 에는 무해하지만, `.bat` 이면 위험하다.
4. **한글이 든 `.ps1` 은 UTF-8 BOM.**
5. **코웍 마운트에서는 읽기 git 만, `--no-optional-locks` 로.** 쓰기(`add`·`commit`·`gc`)·푸시는
   Windows 에서. 예외는 `peter_feed_push.py` 하나이며 사후 `--reclaim` 을 유지한다.
6. **코웍이 도는 동안 PycharmProjects 아래 폴더 이동·이름 변경은 막힌다.**
7. 가드를 고치면 **fuoption 사본에도 복사**(`test_sibling_copy_matches_canonical` 이 감시).
