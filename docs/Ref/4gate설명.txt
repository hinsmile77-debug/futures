4가지 메커니즘 상세 설명

1. FP-CRITICAL (main.py:5359-5371)
역할: RegimeFingerprint가 감시하는 3개 CORE 피처(cvd_divergence, vwap_position, ofi_norm)의 실시간 분포가 학습 당시 분포에서 심각하게 벗어났다고 판단될 때 그 분(minute)의 진입을 통째로 차단하는 최종 안전장치.

동작 방식:
strategy/regime_fingerprint.py가 매분 PSI(Population Stability Index)를 계산해 _PSI_WATCH=0.10 / _PSI_ALARM=0.20 / _PSI_CRIT=0.30 3단계로 레벨을 매김.
get_level() >= 3(=CRITICAL)이면 STEP6에서 direction=0, grade="X"로 강제 override, checklist_reason="FP-CRITICAL" 기록.
conf 수치 자체를 건드리는 게 아니라 conf가 아무리 좋아도 무조건 진입을 막는 킬스위치라는 점이 핵심 — 앞서 딥다이브에서 확인했듯 7/7엔 학습 기준선이 "개장 후 50분 스냅샷"으로 잘못 고착되어 PSI가 오탐 폭주(176건, 51.8%)한 게 원인.
목적 자체는 정당함(피처 분포가 실제로 깨졌을 때 모델이 학습 안 된 영역에서 잘못된 예측을 내는 걸 막는 것) — 문제는 기준선 산출 로직의 버그였음.


2. RegimeOverride (main.py:5334-5357, config/strategy_params.py:735-737)
역할: 매크로 레짐(RISK_ON/NEUTRAL/RISK_OFF) × 마이크로 레짐(추세장/횡보장/급변장/혼합/탈진) 조합별로 사전 정의된 파라미터 세트(PARAM_CURRENT)를 적용하고, 그 조합이 "진입 자체를 금지"하도록 정의된 경우 차단하는 게이트.

동작 방식:
apply_regime_overrides(PARAM_CURRENT, current_regime, micro_en)이 현재 레짐 조합에 맞는 파라미터(임계값 조정 등)를 반환.
그 결과에서 entry_conf_neutral >= 9999.0이면 (관례적으로 "이 조합은 진입 불허"를 의미하는 센티널 값) is_entry_blocked()가 True → direction=0, grade="X".
특히 "탈진" 마이크로 레짐은 "EXHAUSTION"으로 매핑되는데, 주석에 "레짐 챔피언 게이트가 실제 차단 담당"이라고 되어 있어 탈진 레짐 자체는 이 단계보단 바로 다음의 ChampGate(5377행 이하)가 통상 담당.
즉 레짐 조합 자체가 통계적으로 진입하기에 부적합하다고 사전에 판정된 경우를 걸러내는 정적 규칙 기반 게이트로, FP-CRITICAL(실시간 분포 이상 감지)과는 성격이 다름 — 이쪽은 "미리 정의된 나쁜 조합"을 막는 것.


3. CB3_P4_GRADE_BLOCK_ENABLED (config/settings.py:766, main.py:5734-5746)
역할: Circuit Breaker ③(30분 정확도 기반)의 세부 단계 "P4 RESTRICTED"에서 C등급 진입만 차단하는 스위치. 현재 False로 비활성화되어 있음.

동작 방식 (원래 의도):
circuit_breaker.is_grade_restricted()가 True(즉 최근 30분 정확도 acc30m이 30% 미만)이고 _final_grade == "C"일 때, CB3_P4_GRADE_BLOCK_ENABLED가 True면 강제로 _final_grade = "X"로 강등.
왜 꺼져 있나 (296차/297차 배경): 30m 호라이즌이 구조적으로 랜덤 수준 성능(acc=0.3052)으로 확인되어 앙상블/CoherenceGate에서 완전히 퇴역했는데, CB③-P4는 여전히 그 퇴역된 30m 정확도만으로 RESTRICTED를 판정함. 임계값(CB_ACC_RESTRICTED_MIN=0.30)이 30m의 확정 성능(0.3052)과 거의 같아 정상적인 표본 변동만으로도 상시 RESTRICTED에 고착 → 무관한 다른 호라이즌의 정상 C등급 진입까지 상시 차단하는 부작용이 실측됨(292차 딥다이브).
그래서 "차단 로직만" 끄고 accuracy_buf 누적·acc30m_stage 추적·대시보드 표시는 유지 중 — 즉 감시는 계속하되 실제 진입 차단은 잠시 멈춘 상태. CLAUDE.md에 명시된 대로 실투 전환 전 반드시 재검토(30m 재도입 또는 CB③ 기준 호라이즌 교체) 필요.
7/7 사례에선 이 플래그가 False라서 C등급이 이 경로로는 안 막혔지만, 결과적으로는 FP-CRITICAL이 더 크게 작용해 전체 진입은 여전히 막혔음.


4. coherence_blocked (model/ensemble_decision.py:760-829, 863)
역할: 멀티 호라이즌(1m/3m/5m/10m/15m, 30m은 296차 퇴역으로 영구 제외) 예측들이 **서로 방향에 동의하는 정도(합의도)**를 측정해, 합의가 낮으면 "여러 호라이즌이 서로 다른 얘기를 하는 노이즈성 신호"로 판단하고 차단하는 게이트. 두 단계로 구성:

① CoherenceGate (비율 기반, 760-816행):

FLAT이 아닌(방향 있는) 호라이즌들 중 앙상블 최종 방향과 일치하는 비율(_coherence_score = n_coherent / n_active)을 계산.
시간대별 임계값(_coherence_min): 개장 직후(GAP_OPEN)나 TrendGate 활성 구간은 0.50로 완화, 그 외는 기본 COHERENCE_GATE_MIN.
TrendGate(10분 이상 연속 추세 신호)가 외부 근거를 제공하면 예외 면제(_tp_coherence_exempt) — 추세 초기엔 단기 호라이즌만 방향을 잡고 장기 호라이즌이 FLAT에 고착되는 정상적인 상황을 오탐하지 않기 위함.
미달 시 _coherence_blocked = True.

② CascadeCoherence (820-829행):
CoherenceGate를 통과해도 추가로 compute_cascade_coherence()(장기→단기 방향 정렬 순서 검증, "하위만 방향 있고 상위는 FLAT"인 노이즈성 스파이크 탐지)가 0.25 미만이면 역시 _coherence_blocked = True.
최종 반영 (863행, main.py 5754행):

_coherence_blocked=True면 최우선으로 grade="X" (다른 어떤 조건보다 먼저 체크).
추가로 main.py:5748-5759 (285차-P5): 앙상블 coherence_blocked=True + 체크리스트 등급이 C로 동시 발생하면 진입 차단. 백테스트 근거(5/8~7/3)로 A/B등급은 이 조합에서도 승률 92.9%(13승1패)로 견조했지만 C등급 유일 표본은 손실(-26만원)이었기 때문에, A/B등급은 영향 없이 C등급만 추가 차단하도록 좁혀 설계됨.
7/7 맥락: coherence_blocked=23건은 FP-CRITICAL(176건)에 비해 규모는 작지만, 별도의 독립적인 필터로 계속 작동 중이며 이번 진입 실패에 부차적으로 기여함.

정리 — 4개 게이트의 계층 관계
순서	게이트	판단 기준	성격
1	coherence_blocked	호라이즌 간 방향 합의도 (실시간 통계)	신호 자체의 내적 일관성 검증
2	RegimeOverride	매크로×마이크로 레짐 조합 (사전 정의 규칙)	정적 화이트/블랙리스트
3	FP-CRITICAL	피처 분포 드리프트 PSI (실시간 vs 학습기준선)	모델 유효성 자체에 대한 안전장치
4	CB3_P4_GRADE_BLOCK_ENABLED	최근 30분 실측 정확도 (현재 비활성)	실적 기반 서킷브레이커
4개 모두 최종적으로 grade="X" 또는 direction=0으로 수렴시키는 독립적인 안전판들이며, 여러 개가 동시에 걸릴 수 있습니다(7/7처럼). 이 구조 자체는 의도된 다중 방어선이지만, 각 게이트의 판정 로직(특히 FP-CRITICAL의 기준선 산출)에 버그가 있으면 정상 신호까지 과도하게 막는 부작용이 발생한다는 게 이번 딥다이브의 핵심입니다.



1. PSI는 호라이즌별로 산출되는가
아니요, 호라이즌별로 분리되어 있지 않습니다. 단일 전역(global) 값입니다.

main.py:4363에서 features = self.feature_builder.build(...)로 만든 1분봉 기준 단일 피처 dict를 main.py:4422에서 그대로 _fp.update_live(features)에 넘깁니다. 이건 호라이즌별 피처(build_for_horizon(), 1m/3m/5m/10m/15m/30m 각각 다른 산출물)와는 다른, 호라이즌 구분 없는 base 피처 스냅샷입니다.
_CORE_FEATURES = ("cvd_divergence", "vwap_position", "ofi_norm")(regime_fingerprint.py:33) 3개 피처 각각 PSI를 구하고, psi_max = max(...)로 3개 중 최댓값 하나만 남깁니다(regime_fingerprint.py:124-132).
get_level()로 판정된 CRITICAL 여부는 main.py:5362에서 **앙상블 전체(모든 호라이즌 통합 후 최종 direction/grade)**에 일괄 적용됩니다. 즉 "10m만 피처가 이상해졌다"든 "1m만 이상해졌다"든 구분 없이, 3피처 중 아무거나 하나라도 PSI가 튀면 모든 호라이즌·모든 방향의 진입이 한 번에 차단됩니다.
이건 설계상 단순화된 선택으로 보이며, 장단점이 있습니다: 구현이 단순하고 "시장 미시구조 자체가 깨졌다"는 신호는 호라이즌 무관하게 위험하다고 볼 수도 있지만, 반대로 특정 호라이즌에만 영향을 주는 국소적 드리프트도 전체를 차단하는 과잉 차단 위험이 있습니다(오늘 딥다이브에서 실측된 51.8% 차단 사례가 바로 이 전역 차단 구조 때문에 영향 범위가 컸던 것과 무관하지 않습니다).

2. 개장 후 50분 워밍업 구간의 리스크 노출 — 의견
방향성은 맞지만, 실제 노출 폭은 "50분 전체"보다 좁고, 노출되는 리스크의 종류를 구분해서 볼 필요가 있습니다.

이미 겹치는 다른 안전장치가 있어 실제 무방비 구간은 더 짧습니다.
main.py:5399-5420에 별도의 sigma 게이트가 있습니다:

09:00~09:19: sigma_20봉 미수집 → 전면 진입 금지
09:20~09:29: A등급만 허용(B/C 차단)
09:30부터 정상 운영 재개
즉 09:0009:29(약 29분)은 이미 다른 이유로 보수적으로 운영됩니다. PSI 워밍업(라이브 버퍼 50개 채워지는 약 09:50까지)과 겹치는 실제 "무방비" 구간은 **대략 09:3009:50(약 20분)** 정도로 좁혀집니다.

변동성 자체는 별도 게이트(CB④)가 이미 커버합니다.
safety/circuit_breaker.py:372-384의 CB④(ATR 급등 서킷브레이커)는 RegimeFingerprint와 완전히 독립적이며, 순간 ATR이 임계 배수를 넘으면 단 1개 샘플만으로도 즉시 5분 정지를 겁니다(중앙값 기준은 3개 샘플). PSI처럼 50개 샘플을 기다릴 필요가 없어 개장 직후부터 바로 작동합니다. 따라서 "변동성이 크다"는 문제 자체는 이미 이 다른 메커니즘이 담당하고 있습니다.

PSI가 실제로 메꾸는 공백은 "변동성"이 아니라 "분포 이상"입니다.
PSI/RegimeFingerprint가 잡으려는 건 ATR처럼 눈에 보이는 변동성 급등이 아니라, CVD/VWAP/OFI 값의 분포 자체가 학습 당시와 미묘하게 달라진 구조적 변화(ATR은 정상 범위인데 수급 패턴만 깨진 경우 등)입니다. 이건 CB④가 못 잡는 영역이라, 09:30~09:50 사이에 이런 유형의 이상이 발생하면 정말로 무방비입니다.

종합 의견: "50분간 리스크에 노출된다"는 우려는 방향은 맞지만 다소 과대평가된 프레이밍입니다 — 실제 순수 노출 구간은 ~20분이고, 순수 변동성 스파이크는 CB④가 이미 방어합니다. 다만 그 20분 동안 "ATR은 정상인데 미시구조 분포만 깨지는" 특정 유형의 리스크는 실제로 탐지 불가 상태이며, 이건 라이브 버퍼가 매 프로세스 재시작마다 리셋되는 구조(regime_fingerprint.py:62-64, 파일로 영속화 안 됨) 때문에 생기는 근본적인 콜드스타트 문제입니다. 개선하려면 라이브 버퍼를 _FP_FILE처럼 디스크에 영속화해서 재시작 시에도 최근 N분 데이터를 복원하거나, min_live 임계값(현재 50)을 낮추는 방향을 검토할 수 있습니다 — 다만 이건 별도 개선 작업이라 지금 제안만 드리고 실제 코드 변경은 원하시면 별도로 진행하겠습니다.
