1. 추천 적용 시 어떤 호라이즌에 쓰이는가
"추천 적용" 클릭 → main.py:986 _on_apply_shap_candidate_requested() 실행:

이 함수는 특정 호라이즌을 지정하지 않는다. data/shap_feature_registry.json의 active_features — 6개 호라이즌(1m/3m/5m/10m/15m/30m)이 공유하는 전체 피처 풀 — 안에서 기존 약한 피처(old_feat)를 새 후보(new_feat)로 교체할 뿐이다.
실제로 어느 호라이즌 모델이 그 피처를 학습에 반영할지는 재학습 시점에 별도로 결정된다. learning/batch_retrainer.py(약 990행)가 features/horizon_feature_registry.py를 통해 featureset by horizon/horizon_feature_sets.json의 호라이즌별 include 목록과 교집합을 취해 최종 슬라이싱한다. 즉 active_features 풀에 들어가도 해당 호라이즌 JSON의 include 목록에 없으면 그 호라이즌 모델엔 반영 안 됨.
화면의 후보 3개를 그 JSON 기준으로 실제 확인하면:

후보	반영되는 호라이즌
poc_distance	1m·3m·5m·10m·15m (30m 제외)
micro_regime_code	1m·10m·30m
toxicity_score	1m만
즉 "동적 피처" 탭 상단이 "1m" 탭 기준 화면이었으므로, 지금 나열된 SHAP TOP3는 1m 모델 관점의 후보이고, 어차피 세 피처 모두 1m에는 반영됩니다. 다만 poc_distance/micro_regime_code는 다른 호라이즌에도 동시에 걸쳐 있고, toxicity_score는 1m 전용이라는 점이 다릅니다.

2. 추천 적용 후 "세트 재학습"을 따로 눌러야 하는가
아닙니다. main.py:1019를 보면 _on_apply_shap_candidate_requested() 내부에서 레지스트리 저장 직후 self._start_manual_retrain(True, ...)를 자동 호출합니다 — 즉 "추천 적용" 버튼 자체가 이미 즉시 강제 재학습(py310_64 GBM 서브프로세스)을 트리거합니다.

가운데 "세트 재학습"(btn_force_retrain → _on_force_feature_retrain_requested)은 별개 용도로, 스왑 없이 현재 active_features 세트를 그대로 다시 학습시키고 싶을 때(예: 이전 재학습 실패 복구, 강제 리프레시) 쓰는 수동 버튼입니다. 추천 적용 직후에 또 누르면 중복 재학습 요청일 뿐이라 불필요합니다.
