## 0. 결론

**가능하다. 그리고 날짜를 넣는 일 자체는 거의 공짜다 — 진짜 작업은 실시간 유입을 막는 쪽이다.**

세 문장으로 요약하면:

1. `reload_today()`는 이미 `self._session_date` **한 변수로 전부 파라미터화**되어 있고, 하위 조회 함수 4개가 모두 날짜 인자를 받는다. 하드코딩은 **두 줄뿐**이다.
2. 그런데 실시간 진입점 **6개**가 날짜를 묻지 않고 차트에 밀어 넣는다. 과거 날짜를 켜 둔 채 장이 돌면 **오늘 봉이 과거 봉 뒤에 이어붙고**, `maybe_roll_session()`이 **1분 안에 오늘로 강제 복귀**시킨다.
3. 봉은 262 거래일치가 있지만 **오버레이 레이어는 층마다 시작일이 다르다.** 이걸 「0건」으로 그리면 계측 4원칙 ② 위반이다 — 「미측정」과 갈라야 한다.

## 1. 이미 되어 있는 것 — 날짜 파라미터화

`reload_today()`(10170~)의 본문은 처음 한 줄을 빼면 전부 `self._session_date`로 돌아간다.

| 호출 | 날짜 인자 | 상태 |
|---|---|---|
| `raw_candles WHERE ts LIKE ?` | `f"{self._session_date}%"` | **이미 변수** |
| `fetch_today_trades(today_str=None)` | `utils/db_utils.py:2400` | **이미 인자 지원** |
| `fetch_regime_today(today_str=None)` | `:4159` | **이미 인자 지원** |
| `fetch_direction_today(today_str=None)` | `:4168` | **이미 인자 지원** |
| `_load_gp_trades(session_date)` | `:10104` | **이미 인자 필수** |

즉 **시그니처 변경 0건.** 고칠 하드코딩은 딱 두 곳이다.

```
10171   self._session_date = datetime.now().date().isoformat()   # reload_today
10255   self._session_date = datetime.now().date().isoformat()   # _reload_today_bg
```

배경 스레드 로딩(`_start_reload_thread` 10232 → `_sig_reload_done` → `_apply_reload_result` 10311)도
이미 있다. **날짜를 바꿔 다시 부르기만 하면 되는 구조가 이미 깔려 있다.**

비유하자면 이미 지어진 집에 방이 하나 더 필요한 게 아니라, **문에 손잡이만 없는 상태**다.

## 2. 진짜 작업 — 실시간 유입 차단

과거 날짜를 보는 중에도 아래 6개는 **무조건** 차트를 건드린다.

| 진입점 | 줄 | 과거 날짜에서 벌어지는 일 |
|---|---|---|
| `update_tick` | 10337 → 8857 | 마지막 봉 ts(과거 15:08)와 오늘 분이 안 맞으니 `_live_candle`을 새로 만든다 → **차트 오른쪽 끝에 오늘 틱이 유령 봉으로 붙는다** |
| `on_candle_closed` | 10341 → 8889 | `_closed_candles.append()` → **과거 봉 뒤에 오늘 봉이 이어붙는다**. 게다가 첫 줄 `maybe_roll_session()`이 `today != _session_date`를 보고 **매 봉마다 오늘로 강제 리로드** |
| `record_entry` / `record_exit` | 10353 / 10357 | 오늘 체결 마커가 과거 차트에 찍힌다 |
| `set_regime_at` / `set_direction_at` | 10345 / 10349 | 오늘 레짐·방향이 과거 봉 색으로 칠해진다 |
| `sync_active_trade` | 8912 | 오늘 보유 포지션 밴드가 과거 차트에 뜬다 |

가장 고약한 건 `maybe_roll_session()`(10245)이다. 이건 **버그가 아니라 자정 넘김 처리**로 설계된
정상 동작인데, 날짜 선택이 생기는 순간 정반대로 작동한다.

### 처방 — 모드 플래그 하나

```python
self._live_mode = (self._session_date == datetime.now().date().isoformat())
```

- 6개 진입점 앞머리에 `if not self._live_mode: return` 한 줄.
- `maybe_roll_session()`은 `if not self._live_mode: return`을 **맨 앞에** 둔다.
- **오늘로 되돌아오면 반드시 `reload_today()`로 전량 재적재**한다. 과거를 보는 동안
  흘려보낸 틱은 복구되지 않으므로, 증분 재개는 조용한 구멍을 만든다.

> 🔴 이 플래그는 **화면 상태가 아니라 데이터 무결성 장치**다.
> 빠뜨리면 과거 차트가 "조용히 그럴듯하게" 오염된다 — 계측 4원칙 ④.

## 4. 함정 둘 — 스키마에서 오는 것

### ① 계약 롤오버 — `raw_candles`에 종목코드가 없다

```sql
CREATE TABLE raw_candles (
    ts TEXT PRIMARY KEY,        -- ← 종목 구분 없음
    open, high, low, close, volume, bid1, ask1, oi, ...
)
```

`on_candle_closed`는 `candle.get("code")`를 **읽지만 저장하지 않는다.**
그래서 `_trim_to_last_price_group()`(10070)이 close→open **4% 점프 휴리스틱**으로
종목 전환을 *추측*한다. 오늘 하루 안에서는 잘 맞지만 날짜를 넘나들면 세 가지가 깨진다.

1. **만기일 PK 충돌** — 근월·차월이 같은 ts를 가질 수 없다. 둘 중 하나만 남는다.
2. **날짜 간 가격 비교 금지** — 날짜마다 계약이 다르다. 실측 오프셋(미륵이 − 정규):
   9/14 −4.00 · 9/11 −4.47 · 9/4 −0.01 · 8/4 −2.04. **일정하지 않다.**
3. **날짜 선택 UI에 계약월을 띄울 수 없다** — DB에 그 정보 자체가 없다.

> 이건 차트 작업으로 고칠 수 없다. **스키마 결함이고 별도 티켓이다.**
> 당장은 화면에 "계약월 미기록 — 날짜 간 가격 수준 비교 금지" 경고를 띄우는 게 최선이다.
> `book_*_tot` 컬럼 폐기 티켓과 같은 성격이다.

### ② 15:08 절단

최근 60 거래일 중 **56일이 15:08 또는 15:09에 끝난다.** 정규장 마감은 15:45다.
과거 날짜 차트는 **마지막 37분이 통째로 없다.**

`session_bars`가 그 구간을 갖고 있다 — `POST_FORCE_EXIT` 15:10~15:34(659봉/29일),
`CLOSE_FILL` 15:45(2봉). 하지만 **다른 테이블이고 29일치뿐**이라 전체 해결은 못 된다.

근본 처방은 수집 쪽이다: `COLLECT_REGULAR_EOD.bat`에 15:10~15:45 구간을 추가하거나
`collect_peter_levels.py --today`를 EOD 배치에 넣는다. **이건 이 검토의 범위 밖이고
이미 별도로 올려둔 최우선 차단 항목이다.**

## 6. 금지 목록

1. **실시간 진입점을 그대로 둔 채 날짜만 바꾸지 않는다** — 과거 차트가 조용히 오염된다.
2. **없는 레이어를 「0건」으로 그리지 않는다** — 「미측정」과 가른다(계측 4원칙 ②).
3. **날짜 간 가격 수준을 비교하지 않는다** — 계약이 다르고 오프셋이 일정하지 않다.
4. **과거→오늘 복귀 시 증분 재개하지 않는다** — 반드시 전량 재적재한다.
5. **`raw_candles` 스키마를 이 작업에서 건드리지 않는다** — 별도 티켓이다.
6. **15:08 이후가 없는 것을 "거래가 없었다"로 읽지 않는다** — 수집 절단이다.

# 부록2 — 콤보 → 달력 전환 (2026-09-14)

## 왜 바꿨나

§5에서 "달력보다 콤보박스"라고 썼는데 **실물에서 틀렸다.**
262행 드롭다운이 화면 세로 전체를 덮어 차트를 가렸다.
달력은 한 달씩만 보여주므로 크기가 일정하다.

콤보를 권한 원래 이유 — "데이터 없는 날을 고르면 오독된다" — 는 버리지 않고
달력 안에서 두 장치로 해결했다.

1. **표식**: 봉이 있는 날은 밝게·굵게(`#E6EDF3` Bold), 없는 날은 흐리게(`#30363D`).
   **숨기지 않는다** — 휴장일인지 수집 실패인지 달력에서 직접 보여야 한다(계측 4원칙 ②).
2. **거부**: 없는 날을 고르면 재적재하지 않고 위젯을 되돌린 뒤
   「✕ YYYY-MM-DD — 봉 데이터 없음(휴장 또는 미수집)」을 띄운다.
   **조용히 빈 차트를 그리지 않는다.**

# 부록4 — 달력이 안 열리던 결함 (2026-09-14)

## 증상

실행 화면에서 날짜칸은 떴는데 **누를 곳이 없었다.** 달력 팝업이 열리지 않는다.

## 원인

`setCalendarPopup(True)` 로 내장 팝업을 쓰면서 QDateEdit 을 다크 스타일시트로 칠했다.

```python
f"QDateEdit::drop-down{{border:none;width:18px;}}"   # ← 이 한 줄
```

Qt 에서 `::drop-down` 서브컨트롤을 스타일시트로 덮으면 **기본 화살표 렌더링이
꺼진다.** `image:` 로 대체 아이콘을 주지 않으면 아무것도 그려지지 않고,
그 자리는 누를 수 있는 것처럼 보이지도 않는다.

오프스크린 검증에서 못 잡은 이유: `calendarPopup()` 은 `True` 를 반환하고
`calendarWidget()` 도 정상 객체를 돌려준다. **API 는 전부 정상이었고
픽셀만 비어 있었다.** 위젯 속성 검사로는 걸리지 않는 종류의 결함이다.

## 처방 — 내장 팝업을 버리고 자체 팝업

이미지 리소스 없이 Qt 화살표를 스타일링하는 건 취약하다. 통제 가능한 쪽으로 옮겼다.

| 대상 | 내용 |
|---|---|
| `setCalendarPopup` | `True` → **`False`** · `::drop-down` 규칙 삭제 |
| `_cal` **신규 필드** | 자체 `QCalendarWidget`(`clicked` → `_pick_date`) |
| `_cal_popup` **신규 필드** | 그것을 담는 `QDialog(self, Qt.Popup)` — 바깥 클릭 시 닫힘 |
| `_btn_cal` **신규** | 「달력 ▾」 버튼 — **명시적이고 항상 보이는 누를 곳** |
| `_open_calendar` **신규** | 날짜칸 아래에 팝업 배치 · 현재 월로 이동 |
| `_pick_date` **신규** | 고른 날 → 날짜칸 반영. 유효성 검사는 기존 `_on_date_changed` 가 그대로 한다 |
| `_style_calendar` · `_mark_calendar` | `_date_edit.calendarWidget()` → `self._cal` |

# 부록6 — 실행 화면에서 잡은 배지 결함 2건 (2026-09-14)

C단계 확인 화면(2026-09-11 복기)에서 두 가지가 틀린 채로 떠 있었다.
**둘 다 오프스크린 검증은 통과했는데 실데이터에서 틀렸다.**

## 결함 ① GP 커버리지가 통째로 죽었다 — 「GP 미조회」

```python
_ids = VALIDATION_CAMPAIGN["gp_rule_challenger_ids"]
cov["gp"] = _dset(..., (_ids[0], _ids[1]))     # ← KeyError(0)
```

`gp_rule_challenger_ids` 는 **dict** 다 — `{"long": "GP_LONG_GB90", "short": "GP_SHORT_SQZ60"}`.
인덱스로 읽어 KeyError 가 났고, 5개 층을 **공용 try 하나**로 묶어둔 탓에
GP 만 죽은 게 아니라 그 뒤가 전부 날아갈 수 있는 구조였다.

`_load_gp_trades` 는 바로 옆에서 `ids["long"], ids["short"]` 로 올바르게 읽고 있었다.
**같은 파일 안의 선례를 안 보고 새로 썼다.**

처방: dict 접근으로 고치고 **레이어마다 try 를 따로** 걸었다. 한 층이 터져도
나머지는 산다.

## 결함 ② 무포지션일을 「미수집」으로 오판 — 「거래 미수집」

2026-09-11 은 `trades` 0행이 맞다. 그런데 그날 미륵이는 돌았다(레짐 370 · 방향 370).
즉 **무포지션일**이지 미수집이 아니다.

날짜 집합만으로는 "행이 없다"까지만 알 수 있고 **왜 없는지**는 모른다.

처방 — 증인 레이어:

```
그날이 direction(ensemble_decisions) 집합에 있는가?
  있다  → 파이프라인이 돌았다 → 거래 0행은 「0건」
  없다  → 안 돌았다 → 「미수집」
  못 읽음 → 판정 불가 → 「0건?」
```

방향 이력은 파이프라인이 **매분** 쓰므로 "그날 시스템이 살아 있었다"의 가장
촘촘한 증거다. 방향을 못 읽으면 레짐으로 넘어가되, 레짐은 purge 로 과거가
잘려 있어 **"없음"이 증거가 못 되므로** 그 구간은 증인에서 제외한다.

### 세 번째 상태가 왜 필요한가

증인을 **못 읽은 것**을 "안 돌았다"로 접으면 거래 0행이 전부 「미수집」으로
둔갑한다 — 미측정을 측정값으로 바꾸는 짓이고, 이 배지가 막으려던 바로 그
오류다(계측 4원칙 ②). 그래서 `_pipeline_ran()` 은 **True / False / None** 을 낸다.

## 검증

| 증인 | 날짜 | 상황 | 거래 배지 |
|---|---|---|---|
| True | 2026-09-11 | 가동·거래 0행 | **0건** |
| True | 2026-09-14 | 거래 1행 | 1건 |
| True | 2026-06-01 | 가동·거래 0행 | **0건** |
| False | 2025-10-14 | 운영 이전 | **미수집** |
| None | 2026-09-11 | 증인 못 읽음 | **0건?** |
| None | 2026-06-01 | 증인 못 읽음 | **0건?** |

GP 도 `5건 · 4건 · 0건` 으로 정상 복귀했다(이전 「미조회」).

## 배지 툴팁 추가

문구가 아홉 가지로 늘어 화면만 봐서는 못 읽는다. 배지에 마우스를 올리면
전체 판정표가 뜬다 — `n건 · 384+27 · 0건 · 0건? · 미수집 · 보관밖 ·
기록없음 · 원천없음 · 미배선/미조회`.

## 교훈
