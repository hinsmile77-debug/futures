# cancel_ratio — Cybos Plus 데이터 가용성 재조사 보고서

> 작성: 2026-07-14 (320차 후속 — DYNAMIC_FEATURES_POOL 전수 audit에서 파생)
> 성격: **문서 실측 기반 조사** — 코드 변경 없음, 라이브 무영향
> 근거 자료: `docs/CyBos ref/CYBOS_FUTURES_ORDER_TR_MAP.md`(xls 실측 캡처 기반),
> `docs/CyBos ref/CYBOS_선물옵션_API_목록.md`, `docs/CyBos ref/Excel_Example/*.xls`(xlrd 직접 파싱)
>
> **한 줄 요약**: `cancel_ratio.py`(`CancelRatioCalculator`)가 요구하는 "시장 전체 매수/매도측
> 개별 주문 취소 이벤트"는 Cybos Plus 어디에도 없다는 기존 추정이 실측 문서로 **재확인**됐다.
> 다만 조사 중 `Dscbo1.FutOptRest`(선물옵션 잔량추이)라는 **미사용 TR**에서 "건수"·"건수증감"
> 필드를 발견했고, 이걸로 취소 활동을 **근사**할 여지는 있으나 실측 검증이 전혀 안 돼 있어
> 이번 조사만으로는 구현 착수 근거가 부족하다.

## 0. 배경

- 319차: `DYNAMIC_FEATURES_POOL`(`config/constants.py`) 전수 audit에서 `"cancel_ratio"`가
  계산 모듈(`features/supply_demand/cancel_ratio.py`)은 존재하나 `feature_builder.py`가
  애초에 import하지 않아 raw_features에 한 번도 쓰인 적 없는 "죽은 풀 항목"으로 확인됨.
- 320차: 같은 패턴이던 `"vpin"`은 실제 배선 완료(`VPINCalculator` → `feature_builder.py`,
  `main.py:_on_tick_price_update`의 틱 델타 역산 활용).
- `cancel_ratio`는 배선 전 "필요 입력 데이터가 Cybos Plus에 실제로 존재하는가"부터 재조사
  필요하다는 판단에 따라 본 보고서 작성.

## 1. `CancelRatioCalculator`가 요구하는 입력

`features/supply_demand/cancel_ratio.py`:

```python
def on_cancel(self, side: str):   # 'bid' 또는 'ask' — 개별 주문 취소 이벤트
def on_fill(self, side: str):     # 'bid' 또는 'ask' — 개별 주문 체결 이벤트
```

즉 **시장 전체 참여자**의 개별 주문이 취소됐는지 체결됐는지, 그리고 그게 매수호가측인지
매도호가측인지를 실시간으로 분류해서 알려주는 이벤트 스트림이 필요하다. 이는 흔히
"Level-3 주문흐름 데이터"라고 부르는 등급으로, 거래소 회원사(증권사)나 기관용 direct feed에서나
제공되는 데이터이며 리테일 API에는 보통 없다.

## 2. 실측 확인 — 취소/정정 TR은 전부 "내 계좌" 전용

`docs/CyBos ref/CYBOS_FUTURES_ORDER_TR_MAP.md`(xls 공식 TR 테스트 예제를 xlrd로 직접 파싱해
작성된 문서, 실제 계좌번호·주문번호·서버 응답메시지 포함)의 취소/정정 관련 TR 전체:

| ProgID | 용도 | 비고 |
|---|---|---|
| `CpTrade.CpTd6832` | **내 계좌**의 정정주문 실행 | 입력: 원주문번호+계좌번호 필요 |
| `CpTrade.CpTd6833` | **내 계좌**의 취소주문 실행 | 입력: 원주문번호+계좌번호 필요 |
| `CpTrade.CpTd6842`/`6843` | 선물스프레드 정정/취소 | 위와 동일 성격(내 계좌) |
| `CpTrade.CpTd9082`/`9084` | 예약주문 취소 | 위와 동일 성격(내 계좌) |
| `Dscbo1.CpFConclusion` | 체결통보(실시간) | **내 계좌**의 체결/정정/취소 상태만 통지 |

전부 입력 파라미터에 "계좌번호"·"원주문번호"가 필수라는 점에서 명확하다 — **내가 낸 주문을
취소/정정하는 액션 TR**이지, 시장의 다른 참여자가 주문을 취소하는 것을 구독하는 서비스가
아니다. `Dscbo1.CpFConclusion`(체결통보) 역시 계좌 단위 실시간 이벤트로, 문서 자체가
"이 파일 전체에 시장 전체 취소 이벤트에 해당하는 TR은 등장하지 않는다"는 취지로 정리돼 있다.

**결론**: `cancel_ratio.py`가 요구하는 형태(시장 전체 매수/매도측 취소 이벤트)의 데이터는
Cybos Plus에 존재하지 않는다는 기존 추정이 재확인됨 — 이 설계 그대로는 **영구 구현 불가**.

## 3. 예상외 발견 — `Dscbo1.FutOptRest`(선물옵션 잔량추이)

`docs/CyBos ref/CYBOS_선물옵션_API_목록.md`에서 현재 코드베이스가 전혀 쓰지 않는 TR을
확인하던 중 발견. `docs/CyBos ref/Excel_Example/FutOptRest.xls`를 xlrd로 직접 파싱한 필드
구조(반복정보):

```
시각 | 현재가 | 대비 | 거래량 |
1~5차 매도호가 | 1~5차 매수호가 |
1~5차 매도잔량 | 1~5차 매수잔량 |
1~5차 매도건수 | 1~5차 매수건수 |
총 매도잔량 | 총 매수잔량 | 총 매도건수 | 총 매수건수 |
매도잔량증감 | 매수잔량증감 | 매도건수증감 | 매수건수증감 |
주기별누적체결매도수량 | 주기별누적체결매수수량 |
누적체결매도수량 | 누적체결매수수량
```

핵심은 **"건수"**(그 호가에 걸린 개별 주문 수, 잔량과 별개 필드)와 **"건수증감"**(건수의
변화량)이 매도/매수 측 각각 존재한다는 점이다. 여기에 누적 체결량(매도/매수 별도)까지
있으므로, 이론적으로는:

```
건수 감소분 중 "누적체결수량 증가로 설명되는 부분" = 체결로 인한 소멸
건수 감소분 중 그 나머지 = 취소로 추정 가능한 부분
```

이라는 근사 계산으로 `cancel_ratio.py`의 스푸핑 감지 의도(매수/매도측 취소 쏠림 탐지)를
개별 취소 이벤트 없이도 **다른 수식으로 재현**할 여지가 있다.

### 3-1. 검증되지 않은 부분 (구현 착수를 보류하는 이유)

| 항목 | 상태 |
|---|---|
| **조회/실시간 분류** | API 목록 표에 **"조회"**(request-response)로 분류돼 있음. 실시간 구독(subscription) 이벤트가 아니라 폴링 방식으로 추정 |
| **실측 응답 데이터** | xls 예제의 캡처 응답이 `DibMsg1 = "해당자료가 없습니다(futopt.rest.rq)"` — **실제 데이터가 찍힌 적 없음**. 필드명만 확인됐을 뿐 값의 형태·갱신 빈도는 미검증 |
| **폴링 주기/요청 제한** | 입력 필드에 "조회주기(분:초단위, 틱:0)"가 있어 한 번 호출로 여러 시점의 이력을 반환하는 차트형 조회일 가능성 있음(비교: 같은 방식으로 확인한 `Dscbo1.FutureBid1`은 실제로 한 번 호출에 70개 시점을 반환하는 구조였음 — §4 참조). 다만 Cybos Plus 초당 요청 제한과 충돌 여부는 실측 필요. 이 코드베이스엔 아직 Cybos용 요청 제한 가드가 없음(`collection/kiwoom/api_connector.py`에만 존재) |
| **계좌 권한** | 이 TR이 현재 사용 중인 계좌/서비스 등급으로 조회 가능한지 미확인 |

### 3-2. 참고로 확인한 인접 TR — `Dscbo1.FutureBid1`

`docs/CyBos ref/Excel_Example/FutureBid.xls`(5,272행, 실제 캡처 데이터 포함)를 같은 방식으로
파싱해보니, 이 TR은 한 번 호출로 시각별 매도우선호가/매수우선호가/체결거래량 등을 다수 시점
반환하는 **차트형 조회**였다(예: 요청개수=70 → 70개 시점 반환). `FutOptRest`도 "조회주기" 입력
필드 구조가 유사해 같은 성격일 가능성이 있으나, 5호가 잔량·건수까지 포함하는지는 `FutureBid1`
캡처에는 없어(단일 최우선호가만 존재) 별개로 확인이 필요하다.

## 4. 종합 판단

1. `cancel_ratio.py` 원래 설계(개별 취소 이벤트 기반)는 **영구 구현 불가로 확정**.
2. `Dscbo1.FutOptRest` 기반의 대체 지표는 "기존 모듈을 배선"하는 문제가 아니라 **처음부터
   새로 설계**해야 하는 별도 스코프의 작업이며, 다음 선결 조건 없이는 착수 근거가 부족하다:
   - 실제 Cybos Plus 계정으로 `FutOptRest` 호출 → 실데이터 응답 캡처
   - 조회/실시간 여부, 폴링 주기, 요청 제한 확인
   - 건수/건수증감 필드가 실제로 유의미하게 움직이는지(상수·결측이 아닌지) 확인
   - 위 확인 후에야 "건수 감소분 - 체결 기여분 = 추정 취소"라는 근사 공식의 타당성 검토 가능

## 5. 권고

- `config/constants.py:DYNAMIC_FEATURES_POOL`의 `"cancel_ratio"`는 미배선 상태 유지(현재
  주석: "매수/매도측 취소 이벤트 데이터 자체가 브로커 피드에 없는 것으로 추정 — 재조사 전까지
  죽은 후보"를 "재조사 완료 — 원설계는 불가 확정, FutOptRest 대체안은 실측 선행 필요"로 갱신).
- 다음 실거래 세션(Cybos Plus 로그인 상태)에서 `FutOptRest` 실측 캡처를 별도 태스크로 진행할
  것을 제안. 이번 조사만으로는 코드 구현에 들어갈 근거가 부족함.
