## §0. 왜 예약작업인가 — 코드만 넣으면 안 도는 장치다

`scripts/freeze_sentinel.py`는 **별도 프로세스**여야 의미가 있다. 미륵이 본체가 얼어붙은
상태를 보는 장치이므로, 본체 안에서 돌면 같이 멈춘다.

⚠ **예약작업은 git으로 공유되지 않는다.** 코드를 커밋해도 이 PC에 작업을 등록하지 않으면
센티넬은 **한 번도 돌지 않는다** — FP-CRITICAL(2개월간 PSI=0.0)·TOX 죽은 섀도(한 달 무배선)와
같은 상태가 된다. 그것을 막으려고 이 문서가 있다.

## §2. 설치 ✅ **완료 (2026-09-02 525차)** — 아래는 재설치·다른 PC용 절차

> 🔴 **이 PC에는 이미 등록돼 있다.** `\Mireuk\Mireuk_FreezeSentinel_0855`
> (Next Run 2026-09-03 08:55). 다시 실행할 필요 없다.

### §2-1. 등록 (관리자 권한 불필요)

⚠ **폴더 규약**: 이 PC의 미륵이 예약작업은 `\Mireuk\` 폴더에
`Mireuk_<용도>_<시각>` 으로 들어간다(기존 `Mireuk_ClaudeWake_0847` 확인).
초판 지침의 루트 등록(`mireuk-freeze-sentinel`)은 그 규약을 몰랐던 것이라 **폐기**한다.

```powershell
$tn = '\Mireuk\Mireuk_FreezeSentinel_0855'
$tr = '"C:\Users\pc1\anaconda3\envs\py37_32\python.exe" "C:\Users\pc1\PycharmProjects\futures\scripts\freeze_sentinel.py"'
schtasks /Create /TN $tn /SC DAILY /ST 08:55 /TR $tr /RL LIMITED /F
```

- **08:55 시작** — 감시 창(09:00)보다 5분 먼저.
- **종료는 스스로** — 창이 끝나면(16:30) `감시 창 종료 — 정상 종료` 후 빠진다.
  하루 1회 사이드카이며 상주하지 않는다.
- 작업 디렉터리 설정 불필요 — 스크립트가 `_ROOT` 를 **자기 파일 위치**에서 잡는다.
- ⚠ 경로는 자기 PC 값을 쓸 것([[feedback_pc_path_hardcoding]]).

### §2-2. 🔴 기본값 3개를 반드시 고칠 것 — 안 고치면 **조용한 부재**가 된다

`schtasks /Create` 의 기본값은 이 용도에 맞지 않는다. 2026-09-02 실측:

| 설정 | 기본값 | 왜 위험한가 | 바꾼 값 |
|---|---|---|---|
| `StartWhenAvailable` | `False` | PC가 08:55에 꺼져 있거나 절전이면 **그날 감시가 통째로 없다**. 아무 로그도 안 남는다 | **True** |
| `DisallowStartIfOnBatteries` | `True` | UPS 배터리 전환 중엔 **시작조차 안 한다** — 정전은 감시가 가장 필요한 순간이다 | **False** |
| `StopIfGoingOnBatteries` | `True` | 장중 배터리 전환 시 감시자가 **도중에 멈춘다** | **False** |

```powershell
$set = New-ScheduledTaskSettingsSet -StartWhenAvailable -AllowStartIfOnBatteries `
       -DontStopIfGoingOnBatteries -ExecutionTimeLimit (New-TimeSpan -Hours 10) `
       -MultipleInstances IgnoreNew
Set-ScheduledTask -TaskPath "\Mireuk\" -TaskName "Mireuk_FreezeSentinel_0855" -Settings $set
```

- `ExecutionTimeLimit 10h` — 08:55~16:30 은 약 7.6시간. 기본 72시간은 너무 느슨해
  이상 시 다음날까지 남는다.
- `MultipleInstances IgnoreNew` — 이미 돌고 있으면 중복 기동하지 않는다.

⚠ `Set-ScheduledTask -Settings` 후 **트리거·명령이 살아 있는지 반드시 재확인**할 것
(§3). 2026-09-02 확인 결과 둘 다 보존됐다.

### 비거래일·비활성 처리

스크립트가 스스로 판정한다 — 비거래일이면 종료코드 **6**으로 즉시 빠진다.
스케줄러에 요일 조건을 넣지 않는 이유는 휴장일 판정이 `utils/time_utils.is_trading_day`
한 곳에만 있어야 하기 때문이다(진실원천 단일화).

## §3. 확인 (설치 직후 1회)

```powershell
schtasks /Query /TN "\Mireuk\Mireuk_FreezeSentinel_0855" /V /FO LIST |
  Select-String "Task To Run|Next Run Time|Last Result|Status"
$t = Get-ScheduledTask -TaskPath "\Mireuk\" -TaskName "Mireuk_FreezeSentinel_0855"
$t.Settings.StartWhenAvailable; $t.Settings.DisallowStartIfOnBatteries; $t.Triggers[0].Enabled
```

**스케줄러 경유 실행까지 확인할 것** — 내 셸에서 되는 것과 스케줄러가 띄우는 것은 다르다:

```powershell
schtasks /Run /TN "\Mireuk\Mireuk_FreezeSentinel_0855"
# 10초 뒤 Last Result 확인: 창 밖이면 6, 장중이면 0
```

그리고 **수동 1회 판정**으로 동작을 눈으로 본다(마커를 남기지 않으므로 안전):

```cmd
"C:\Users\pc1\anaconda3\envs\py37_32\python.exe" scripts\freeze_sentinel.py --once
```

- 장중에 돌리면 `OK — 정상 · 신선한 신호 3종 (heartbeat, crash_fault[TS], SYSTEM.log)`
- 장 마감 후에 돌리면 `CRITICAL`이 나오는 것이 **정상**이다 — `--once`는 감시 창을
  무시하는 진단 모드다. 실제 예약작업은 창 밖에서 판정하지 않는다.

## §5. 매일 볼 것

- `logs/freeze_sentinel_<날짜>.log`의 `ARMED` 줄 — **센티넬 자신의 생존 증거**다.
  이 줄이 없으면 예약작업이 조용히 죽은 것이다(감시자가 「조용한 부재」에 빠지는 것이
  가장 나쁘다).
- `CRITICAL`이 뜨면 **먼저 크래시 지문을 볼 것** — `logs/crash_fault.log`의
  `Windows fatal exception`·`access violation`과 런처 `[AUTO-RESTART]`.
  있으면 크래시(런처가 회수)이지 동결이 아니다(522차 T-A와 같은 판별).
