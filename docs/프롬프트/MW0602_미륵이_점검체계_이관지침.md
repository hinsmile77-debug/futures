## 2. 반영할 두 대원칙 (스킬 본문이 정본 — 아래는 요약)

`mireuk-daily-check` 스킬 SKILL.md 맨 앞의 「대원칙 A·B」가 정본이다. 먼저 그것을 읽어라.

### 대원칙 A — 리포트는 알기 쉽게 쓴다

> **줄이라는 뜻이 아니다 — 쉽게 만드는 대상은 순서와 표현이지 내용이 아니다.**
> 근거·로그 인용·파일과 함수 이름·절대원칙 번호·STEP 번호는 하나도 빼지 않는다.
> 증거를 덜어내서 읽기 쉬워진 리포트는 이 원칙의 **위반이지 이행이 아니다.**

실행 규칙 5개:

1. **§0은 전문용어 없이** — 약어·태그명·파일경로·절대원칙 번호·STEP 번호를 하나도 쓰지 않는다.
   답할 것은 셋: 지금 위험한가 / 무엇이 잘못됐나 / 사람이 뭘 해야 하나.
2. **약어는 첫 등장에서 한 번 풀어쓴다** — `CB②(Circuit Breaker 2단계 — 연속 손실 시 자동 정지)` ·
   `STEP5(매분 9단계 중 5번째 — 진입 체크리스트)` · `p65(하위 65% 지점 — DynMC 산출 진입 임계)`.
3. **숫자에 단위와 비교 기준을 병기** — `342.15pt(코스피200 선물 지수 포인트)` ·
   `-480,000원(자본 대비 -0.96%)` · `2계약(선물 포지션)` · `MDD 3.2%(peak 대비 · 자본 대비 1.8%)`.
   **미륵이 고유 함정: 집계가 포지션 단위인지 청산 레그(이벤트) 단위인지 반드시 구분해 병기한다**
   (계측 4원칙 ① · 417차 실측 이벤트 단위 p=5.07e-07 → 포지션 단위 p=0.93).
4. **「영향」은 평문 한 문장** + 그 아래 `**영향(기술)**` 을 따로. **둘 다 쓴다.**
5. **사용자 조치는 맨 끝 `## 사용자 조치` 한 절에 집결** — 각 항목에 걸리는 시간·안 하면 생기는 일.

### 대원칙 B — 하루 한 파일 · append 전용

**리포트는 `docs/정기점검/매일점검/<PC명>-<YYYYMMDD>-점검리포트.md` 하나뿐이다.**
장전이 만들고, 장중이 이어 붙이고, 장후가 이어 붙여 종합 완성본으로 닫는다.
**`-pre` / `-intra` / `-post` 접미사 파일은 금지** — 종전 허용을 철회했다.

- **앞 국면 절의 본문을 고치거나 지우지 않는다.** 정정은 뒤 국면 절에서 하고 앞 절에는
  `> ↩️ {시각} 정정 — {번호} 참조` 한 줄만 단다. *왜 그때 그렇게 판단했는가*가 남아야 한다.
  **미륵이에는 특히 중요하다** — 함정 ①(판정 ≠ 결정) 때문에 그때의 판정 근거가 없으면
  같은 권고를 몇 주째 다시 올리게 된다(2026-07-15 Hurst 완화 권고가 3주 반복된 사례).
- 뒤 국면은 앞 국면 항목을 **전부** ✅해소 / 🔄지속 / ⬆️격상·⬇️완화 / ↩️정정 / 🆕신규 로 처분한 뒤 시작한다.
- 이상점 번호는 하루 안에서 이어진다. **지속 항목에 새 번호를 붙이지 않는다.**
- 장후 완성 판정 한 문장: **"이 파일 하나만 읽고 그날이 전부 재구성되도록 구성한다."**
- 파일명에 PC명이 들어가므로 MW0601·MW0602가 서로 덮지 않는다.
  **한 PC의 리포트가 다른 PC의 국면 절을 이어 붙이지 않는다** — 서로 다른 브랜치의 관찰이다.

### 국면별로 다르게 넣을 것

**장전** — `## 산출` 절을 이렇게 바꾼다:

```markdown
- **리포트: `docs/정기점검/매일점검/<PC명>-<YYYYMMDD>-점검리포트.md` — 장전이 이 파일을 새로 만든다.**
  헤더 + `## 0. 오늘 한눈에`(평문) + `## 제1부. 장전` 까지 쓴다. 장중·장후가 뒤에 이어 붙일 것이다.
  **`-pre` 접미사 파일을 만들지 않는다.** 같은 날 파일이 이미 있으면 덮지 말고 이어 붙인다.
  형식은 `references/report_template.md`를 따르되 **위 대원칙 A·B가 템플릿보다 우선한다.**
- 채팅 본문은 **평문 3~5줄** — 위험 여부, 이상점 건수(P0/P1/P2), 가장 시급한 것, 사용자가 할 일.
  약어·태그명을 쓰지 않는다(대원칙 A).
```

**장중** — `## 산출` 절:

```markdown
- **리포트: 장전이 만든 파일 끝에 `append` 한다.**
  붙이는 것: `## 0-B. {HH:MM} 갱신`(평문 갱신 블록) → `## 제2부. 장중`
  (이월 처리 표 → 신규 이상점 → Fix → 고도화).
  **장전 절의 본문은 한 글자도 고치지 않는다.** 정정할 것이 있으면 제2부에 쓰고 장전 절에는 포인터 한 줄만.
  파일이 없으면 장전 점검이 안 돈 것이다 — 그 사실을 이상점(관측 공백)으로 적고 파일을 새로 만든다.
```

절차 요약에도 한 줄 추가:

```markdown
- **오늘 리포트 파일을 먼저 읽는다.** 장전이 남긴 이상점·확인 필요·관측 항목을 전부 처분
  (✅🔄⬆️⬇️↩️)한 뒤에 장중 이야기를 시작한다.
```

**장후** — `## 산출` 절을 「여기서 하루가 닫힌다」로 바꾸고 순서를 고정한다:

```markdown
- **리포트: 오늘 파일 끝에 `append` 하여 그날의 종합 완성본으로 만든다.**
  **앞 두 국면 절의 본문은 한 글자도 고치지 않는다.** 붙이는 것은 순서대로:
  1. `## 0-C. {HH:MM} 갱신 — 오늘 한눈에 (최종)` — 평문. 오늘 하루 한 문장 / 돈은 어떻게 됐나 / 지금 할 일
  2. `## 제3부. 장후` — 이월 처리 표(장전·장중 전 항목) → 신규 이상점 → Fix → 고도화
  3. `## 종합 — 오늘` — ① **종합 판정표**(3줄) ② **당일 이상점 통합 대장**
     (번호순 · 발견 국면 · 최초/최종 심각도 · 최종 처분) ③ **종가 기준 최종 손익**
     (실현/평가 손익 원 + 자본 대비 %, MDD는 peak 대비·자본 대비 병기, **진입·청산 건수는
```

## 4. ⚠ 파일명 전환의 유일한 위험 — **옛 이름을 지우지 마라**

마흐디가 같은 전환을 먼저 했고, **오보 0건**으로 끝났다. 이유는 하나다:

> **파일명을 바꾸면서 옛 이름을 버리지 않고 「legacy 패턴」으로 남겼다.**
> 감시 코드는 신·구를 **둘 다** 찾고, 수집기는 **날짜로 분기**한다.

이름을 바꾸는 쪽만 하고 읽는 쪽을 안 고치면 **전환 당일부터 매일 허위 경보가 뜬다.**
그러므로 §1-②·⑤에서 찾은 「리포트 파일명을 기대하는 코드」를 **전환 전에** 아래 두 방식으로 고친다.

### 방식 ① 존재를 감시하는 쪽 — 신·구를 둘 다 찾는다

```python
_REPORT_PATTERN = "{pc}-{date}-점검리포트.md"
# 전환 전 산출물. 「한 거래일도 없음」을 확인한 뒤에 이 튜플을 비운다 — 그 전엔 지우지 않는다.
_REPORT_LEGACY_PATTERNS = (
    "{pc}-{date}-점검리포트-pre.md",
    "{pc}-{date}-점검리포트-intra.md",
    "{pc}-{date}-점검리포트-post.md",
)
_REPORT_PATTERNS = (_REPORT_PATTERN, *_REPORT_LEGACY_PATTERNS)
```

### 방식 ② 산출물 목록을 점검하는 쪽 — 날짜로 분기한다

```python
from datetime import date as _date

# 점검 리포트가 「하루 한 파일」로 바뀐 첫 영업일. 그 이전 날짜를 재집계할 때
# 새 이름을 기대하면 과거 전부가 거짓 누락으로 뜬다.
ONE_FILE_SINCE = _date(2026, 9, 1)   # ← 이 세션이 정한 실제 전환일로 바꿀 것

if day >= ONE_FILE_SINCE:
    targets.append((f"docs/정기점검/매일점검/{PC}-{D}-점검리포트.md", "post"))
else:
    targets += [
        (f"docs/정기점검/매일점검/{PC}-{D}-점검리포트-pre.md", "post"),
        (f"docs/정기점검/매일점검/{PC}-{D}-점검리포트-intra.md", "post"),
        (f"docs/정기점검/매일점검/{PC}-{D}-점검리포트-post.md", "post"),
    ]
```

### 직전 리포트를 찾는 glob이 있으면 — 둘 다 훑고 새 이름을 우선한다

```python
_REPORT_GLOBS = ("*-점검리포트.md", "*-점검리포트-post.md")   # rank 0 = 새 이름 = 우선
```

**옛 이름만 버리면 「전일 리포트 대조」가 전환일 이후 영구히 눈이 먼다.**

### 전환일을 정하는 법

- **전환일은 「코드 커밋 + 예약 프롬프트 갱신」이 **둘 다** 끝난 다음 영업일**로 잡는다.
- 코드보다 프롬프트가 먼저 바뀌면 그날 산출물과 코드 기대가 어긋난다(반대도 마찬가지).
- **전환일 하루는 옛 파일과 새 파일이 공존해도 된다.** 과거 리포트를 새 이름으로 옮기지 않는다 —
  그날의 판단은 그날의 형태로 남는다.

### 적용 시점 — 장중 금지

**코드 변경·커밋·배포·재기동은 장후(15:10 이후)에만 한다.** 라이브 프로세스가 돈다.
장전·장중에 이 지침을 읽었다면 **계획만 확정하고 착수는 장후로 미룬다.**

### dev_memory

- `dev_memory/DECISION_LOG.md`에 **append**. 세션 헤더에 **PC명(MW0602)과 차수**를 병기한다.
  차수는 **원격(git) 기준**으로 맞춘다(392차 관행) — 같은 날 두 PC가 같은 차수를 붙인 충돌이 실제로 있었다.
- 항목 구성: 증상 → 원인 → 결정 → Why → How to apply → 검증.
- **반드시 남길 것**: 전환일(`ONE_FILE_SINCE`)의 실제 값과 **그렇게 정한 이유**,
  legacy 패턴을 남긴 이유, 그리고 **"옛 이름을 지우는 시점은 「한 거래일도 안 나온 것을 확인한 뒤」"** 라는 조건.
- 새 항목은 `dev_memory/NEXT_TODO.md`에 체크박스로.
- **dev_memory에는 대원칙 A(평문화)를 적용하지 않는다** — 개발자용 기록이라 정밀함이 우선이다.
