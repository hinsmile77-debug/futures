## 2. 로그 읽는 법

```
09:00:10 RATE SearchTimeline st=200 rem=49/50 reset=09:15:00 phase=load n=1
           │              │       │     │         │              │      └ 그 페이지에서 본 응답 순번
           │              │       │     │         │              └ load=새로고침이 부른 요청(로드 8초 안) / poll=X 자체 폴링
           │              │       │     │         └ 한도가 풀리는 시각(KST)
           │              │       │     └ 창당 한도
           │              │       └ 남은 호출
           │              └ HTTP 상태(429 = 소진)
           └ 대상 엔드포인트
```

**다른 소비자 판정**: 같은 `reset` 창 안에서 `rem` 감소폭 > 우리 관측 수(load+poll)이면 그 차이만큼
**다른 누군가가 같은 계정 예산을 썼다**(MW0602 수집기·사람의 X 열람). `latency_report.py` 의 「X 한도 실측」
표에서 `관측` 열과 `rem 최대→최소` 를 비교하면 된다.

## 5. 첫날 RATE 가 안 찍힐 때

1. `collector.json` 의 `rl` 이 `null` 인가 → 훅이 응답을 못 봤다.
2. Chrome DevTools(X 탭) Network 에서 `SearchTimeline` 요청의 응답 헤더에 `x-rate-limit-*` 가 있는가.
   - 없으면: X 가 헤더를 주지 않는다 → F-1 은 불가, F-3 은 자동으로 종전 120초로 돈다(폴백 내장). 예산은
     PAGE_ERROR 군집 주기로만 추정한다.
   - 있는데 안 찍히면: 요청 경로가 `OPS` 정규식(`/graphql/<id>/SearchTimeline`)과 다른지 확인.
3. 어느 경우든 F-2(80초)는 헤더와 무관하게 동작한다 — `latency_report.py` 의 PAGE_ERROR·오류분으로 효과를 본다.
