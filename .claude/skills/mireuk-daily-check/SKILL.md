# 미륵이 일일 운영 점검

## 이 스킬이 하는 일

한 문장으로: **"오늘 미륵이가 절대원칙을 지키며 설계대로 살았는가"를 로그로 심문하고, 안 그런 부분에 대해 고칠 계획과 더 나아갈 계획을 내놓는다.**

산출은 항상 세 부분이다. 순서도 고정이다.

1. **이상점 정리보고** — 국면(장전/장중/장후)별 작업흐름 이상점
2. **Fix 작업 구현계획** — 우선순위(P0/P1/P2)와 함께
3. **고도화 방안** — 당일 작동 점검결과를 근거로

---

## 0. 시작 전 — 이 프로젝트의 세 가지 함정

미륵이는 메시아와 다르다. 이 셋을 모르면 보고서가 틀린다.

### 함정 ① 판정(verdict)과 결정(decision)은 별개다

검증 캠페인 리포트의 판정·권고는 **조치 여부와 무관하게 매주 재계산·재출력**된다.
따라서 **"FAIL이 계속 뜬다 = 미조치"가 아니다.** 양방향으로 실제 사고가 있었다.

- 이미 배포된 권고(2026-07-15 Hurst 완화)를 3주째 리포트가 다시 찍었고, 0801 결산 초안이 그걸 "승인 1순위"로 잘못 올렸다 → 코드 확인 후 철회
- 일부러 적용하지 않기로 한 FAIL이 기록되지 않아, 다음 세션이 적용을 재시도할 뻔했다

→ **어떤 권고든 "이미 코드에 있는가"를 먼저 확인하라.**
`config/settings.py:VALIDATION_CAMPAIGN_DECISIONS`(확정 결정 레지스트리)와
`dev_memory/DECISION_LOG.md`가 진실원천이다.

### 함정 ② 재인용 금지 수치가 있다

CLAUDE.md에 **"무효다 — 재인용 금지"** 로 못박힌 수치들이 있다. 이것들을 근거로 쓰면
보고서 전체의 신뢰가 무너진다. 목록은 `references/invariants.md` §3에 있다. 대표적으로:

- 2026-06-25 SHAP=0 판정 (이름↔값 정렬 오염 구간 한복판)
- 2026-08-01 §9-3의 이벤트(청산 레그) 단위 사이징 통계 4종

### 함정 ③ 멀티PC다

MW0601·MW0602가 같은 repo를 공유한다. **PC별 Claude 개인 메모리는 다른 PC 세션에 보이지 않는다.**
- 커밋 제목 첫 단어: `[MW0601]` 또는 `[MW0602]`
- `dev_memory/DECISION_LOG.md`·`NEXT_TODO.md` 세션 헤더에도 PC명 병기
- **PC간 공유가 필요한 내용은 반드시 git에 커밋되는 문서에 적는다**

수집기가 호스트명에서 PC를 뽑아 다이제스트 첫 줄에 찍는다. `UNKNOWN`이면 수동 확인하라.

## 1. 국면과 날짜를 확정한다

인자로 국면이 넘어왔으면 그것을 쓴다. 없으면 KST 현재시각으로 추론하되 **추론값을 첫 줄에 명시**한다.

| 국면 | 인자 | 시간대(KST) | 무엇을 묻는가 |
|---|---|---|---|
| 장전 | `pre` | ~09:00 | 오늘 거래할 자격이 되는가 |
| 장중 | `intra` | 09:00~15:10 | 매분 9단계가 설계대로 돌고 있는가 |
| 장후 | `post` | 15:10~ | 오늘 하루가 절대원칙을 지켰는가 |

**리포 루트**: `CLAUDE.md`와 `dev_memory/`를 함께 가진 디렉터리.

## 1-B. 멀티PC 설치 — MW0601·MW0602 양쪽에서 동작한다

스킬은 **PC를 가리지 않는다.** 절대경로가 하나도 없고, 리포 루트는 `CLAUDE.md`+`dev_memory/`로
자동 탐지하며, PC명은 호스트명에서 뽑는다. 따라서 **한 PC에서 커밋하면 다른 PC는 pull만 하면 된다.**

```bash
# 설치한 PC에서
git add .claude/ scripts/collect_evidence.py config/dailycheck_targets.json
git commit -m "[MW060X] NNN차: 일일 점검 스킬"
git push

# 다른 PC에서
git pull
python scripts/collect_evidence.py --discover      # ← 이 검증은 PC마다 한 번씩 하라
```

**`--discover`를 PC마다 돌리는 이유**: 코드는 같아도 로그 적재량·보관 정책·경로가 PC마다 다를 수
있다. 인벤토리가 다르면 `config/dailycheck_targets.json`을 공유값으로 두기 어렵다 —
그때는 두 PC의 합집합으로 `scan_dirs`를 넓히되 `priority_logs`는 그대로 둔다.

산출물은 파일명에 PC명이 들어가 서로 덮지 않는다.

| 산출물 | 이름 |
|---|---|
| 증거 다이제스트 | `docs/정기점검/매일점검/evidence_<PC명>-<YYYYMMDD>_<국면>.md` |
| 점검 리포트 | `docs/정기점검/매일점검/<PC명>-<YYYYMMDD>-점검리포트.md` |

> 호스트명에서 `MW####`를 못 뽑으면 다이제스트 첫 줄이 `UNKNOWN`이 되고 경고가 뜬다.
> 그 상태로 커밋하면 어느 PC의 관찰인지 영영 모르게 된다 — 반드시 확인하라.

**예약작업은 PC별로 따로 등록해야 한다.** 코드는 git으로 공유되지만 예약작업은 그렇지 않다.
각 PC의 데스크톱 앱에서 시작한 세션에서 등록하라.

## 2. 증거를 먼저 모은다

```bash
python scripts/collect_evidence.py --phase post --out-auto
```

`--out-auto`는 `docs/정기점검/매일점검/evidence_<PC명>-<날짜>_<국면>.md`로 저장한다.
셸 날짜 확장(`$(date ...)`)에 기대지 않아 PowerShell·bash 어디서든 같게 동작한다.

**처음 쓰는 PC라면 `--discover`를 먼저 돌려라.** 로그 폴더 구조를 확인하고
필요하면 `config/dailycheck_targets.json`에 `scan_dirs`를 고정한다.

```bash
python scripts/collect_evidence.py --discover
```

수집기가 내는 것: 당일 파일 인벤토리(날짜 토큰 자동탐색) · 커밋 상태와 **PC명 태그 규약 점검** ·
**설정 불변식 검사(절대원칙·한시예외)** · 로그 다이제스트 · 안전장치/크래시 패턴 인용 ·
타임라인 앵커와 **매분 루프 커버리지** · dev_memory · JSON 산출물 · 정기점검 리포트 현황 · 자동 적신호.

- 출력이 크면 `--out docs/정기점검/매일점검/evidence_<PC>-<날짜>_<국면>.md`로 파일에 받는다
- 파이썬은 `py37_32`든 `py310_64`든 상관없다 (수집기는 표준 라이브러리만 쓴다)

> §10 자동 적신호는 **출발점이지 결론이 아니다.** 기계가 못 잡는 것 — 설계와 다른 순서,
> 있어야 할 로그가 아예 없는 것, INFO로 조용히 지나간 폴백 — 이 진짜 수확이다.

## 4. 설계와 대조한다 — 이 스킬의 핵심

증거를 **기준**에 대야 이상점이 된다. 기준은 다섯 군데다.

1. **`CLAUDE.md`** — 절대원칙 6종(변경 불가), 매분 9단계, 확률 판단 기준, 실전 전환 기준 ①~⑧, 26주 재검증 항목. **충돌 시 최우선.**
2. **`CORE.md`** — 핵심 판단 규칙. 코딩 전 반드시 확인.
3. **`ROADMAP.md`** — Phase별 구현 계획과 마일스톤.
4. **`dev_memory/DECISION_LOG.md` · `NEXT_TODO.md`** — 이미 아는 문제인가, 새 문제인가. **이미 결정된 사안을 새 발견인 양 보고하지 않는다.**
5. **커밋 이력** — 당일/최근 커밋이 실제로 반영됐는가. PC명 태그가 붙었는가.

> `_archive/plans/PROJECT_DESIGN.md`는 2026-04 브레인스토밍이다. 30m 호라이즌 등
> **퇴역한 내용을 포함**하므로 사료적 참고용으로만 쓰고 근거로 인용하지 마라.

국면별 구체 점검항목은 **`references/phases.md`**, 절대원칙·한시예외·재인용금지 목록은
**`references/invariants.md`** 에 있다. 둘 다 읽고 빠짐없이 통과시킨다.

## 5. 보고서를 쓴다

형식은 **`references/report_template.md`** 를 따른다. 작성 시 지킬 것:

- **이상점 하나 = 증상 → 근거(로그 인용 + 시각) → 기준 위반(CLAUDE.md 절대원칙 번호 / 9단계 STEP) → 영향** 4단.
- 심각도는 **P0(오늘 거래에 직접 위험·절대원칙 위반) / P1(정확성·관측 훼손) / P2(운영 부담·기술부채)**.
- **불확실한 것은 불확실하다고 쓴다.** 표본 부족이면 "확정 결론 금지"(313차 원칙)를 명시하라.
- Fix 계획은 파일·함수 수준까지. "게이트를 개선한다"가 아니라
  "`strategy/entry/checklist.py`의 `_core_pass()`에서 entry_horizon 그룹 판정을 …".
- **장중에는 코드 변경을 제안만 하고 실행하지 않는다.** 라이브 프로세스가 돌고 있다.
- 고도화 방안은 **당일 관측에서 출발**해야 한다. 일반론 금지.

**산출 위치 — 기존 관행을 따른다:**

```
docs/정기점검/매일점검/<PC명>-<YYYYMMDD>-점검리포트.md
```

PC명은 수집기 첫 줄에 찍힌 값(`MW0601`/`MW0602`)을 쓴다. 국면을 여러 번 돌리면
같은 파일에 국면별 절을 append 하거나 `-pre`/`-intra`/`-post` 접미사를 붙인다.
**기존 날짜본을 덮어쓰지 않는다** — 주간점검이 지난주 리포트를 잃은 사고가 실제로 있었다.

## 6. dev_memory에 남긴다 (생략 금지)

- `dev_memory/DECISION_LOG.md`에 **append**. 세션 헤더 형식:
  `## 2026-08-12 (MW0601 46X차 — 일일 점검)`
- 항목 구성: **증상 → 원인 → 결정 → Why → How to apply → 검증**. "라이브 미검증"이면 검증 기한 명기.
- 새 fix/고도화는 `dev_memory/NEXT_TODO.md`에 체크박스로 추가.
- **기존 내용을 덮어쓰지 않는다.** 두 파일 다 280~315KB 누적 기록이다.
- 세션 차수는 **원격(git) 기준**으로 맞춘다(392차 관행). 같은 날 두 PC가 같은 차수를 붙인 충돌이 실제로 있었다(2026-07-02).

## 실행을 요청받았을 때

"fix 항목 구현해" / "고도화 방안 구현해" 로 이어지면:

1. 구현계획을 먼저 항목별로 — 변경 파일, 변경 내용, 회귀 위험, 검증 방법.
2. **장중이면 실행하지 않는다.** 라이브 프로세스가 돈다. 계획만 확정하고 장후 적용을 권고한다.
3. **절대원칙 6종은 변경 대상이 아니다.** 저촉되는 제안은 내지 마라.
4. **COM 콜백 안에는 `dynamicCall`·`emit`을 넣지 마라** — 0xC0000409 크래시(절대원칙 4).
5. 커밋 메시지 첫 단어는 `[MW0601]` / `[MW0602]`.
6. 재학습 코드를 건드리면 `py310_64` 전용임을 잊지 마라 — `py37_32`로 돌리면 OOM 재발(191차 결정).
7. 게이트·차단 로직 신설은 **섀도 계측을 거친 뒤** 승격한다.
