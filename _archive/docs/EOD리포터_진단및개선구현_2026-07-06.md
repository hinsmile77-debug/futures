## 0. 배경

`data/daily_reports/*.txt` EOD 리포트를 무작위 7건(2026-05-07~07-06) 샘플링해
이상점을 딥다이브했다. 6/7건이 `(1일차)` / `데이터 부족(1일)` / `누적 +0원`으로 고정돼
있었고, 이후 조사를 이어가며 리포트에 실제로 출력되는 거의 모든 지표(버전/등급/
호라이즌/CUSUM/PSI)에서 각각 독립된 원인의 문제를 추가로 발견했다. 아래는 발견 순서대로
정리한 진단 → 근본원인 → 구현 → 검증 전체 기록이다.

## 1. "1일차" 고정 — 활성 버전 이원화 (가장 심각)

### 증상
```
버전    : v1.2  (1일차)
판정    : INSUFFICIENT
롤링20일: 누적 +0원  Sh=0.00  MDD=0.0%
```
2026-05-07부터 07-06까지 두 달째 매일 모의투자가 돌고 있었는데도 위 3줄이 하루도 안
지난 것처럼 고정.

### 근본원인
"현재 버전" 포인터가 두 곳에 따로 존재:
```
strategy_versions.is_current = 'v1.2'      (scripts/qa_strategy_seeder.py가 2026-05-07
                                             18:37에 더미 3버전을 등록하며 남긴 QA 테스트값)
config/strategy_params.py PARAM_HISTORY[-1]["version"] = 'v1.0'  (05-07 이후 갱신 안 됨)
```
`main.py`(라이브 스냅샷 기록)는 `PARAM_HISTORY[-1]`을 읽어 매일 `v1.0` 태그로 저장했고,
`daily_exporter.py`(리포트 조회)는 `strategy_versions.is_current`(`v1.2`)를 기준으로
조회 — 실거래 데이터는 `v1.0`에 33일치 쌓였는데 리포트는 `v1.2`(QA 더미 1건)만 봄.

DB 실측:
```
strategy_live_snapshots:
  v1.0 → 33일치, 2026-05-07~07-06 (실제 손익 등락: 06-26 +562만, 07-01 -776만 등)
  v1.1/v1.2 → 각 1건 (QA 더미, 05-07)
```

### 구현
1. **DB 정정**(`data/db/strategy_registry.db`, 커밋 대상 아님): `is_current`를 `v1.2` →
   실제 운영 버전 `v1.0`으로 되돌림.
2. **`main.py:8425-8438`**: 라이브 스냅샷 기록 시 `PARAM_HISTORY[-1]` 대신
   `get_registry().get_current_version()`을 읽도록 변경 — registry를 유일한 소스로 통일.
3. **`strategy/ops/hotswap_gate.py:143-190`**: 다음 버전 넘버링도 registry 기준으로
   통일(향후 실제 Hot-Swap 발동 시 같은 드리프트 재발 방지) + `param_optimizer.apply_best()`와
   동일 패턴으로 `PARAM_HISTORY`에도 문서화용 항목 append.

### 검증
```
버전    : v1.0  (33일차)
판정    : UNDERPERFORM
Live    : Sh=-0.69  MDD=137.4%  WR=0.0%  PF=1.00
롤링20일: 누적 -2112475원  Sh=-0.69  MDD=137.4%
```
`(1일차)`/`누적 +0원` 고정 해소, 실제 33일치 반영 확인(`판정 UNDERPERFORM`은 버그가
아니라 진짜 실측 — WFA 대비 Live 성과 하회).

## 3. 등급 "?" 버킷 (5건, `-1,275,689원`) — 실제 코드 버그, 수정 완료

### 증상
```
등급별 순EV(30일): ?=-1,275,689원(5건,승60%)  A=+62,241원(102건,승73%) ...
```

### 근본원인
전량 `exit_reason='stuck_exit_flat'`(브로커 잔고에 포지션이 안 보여 합성 청산 기록을
만드는 경로, `main.py` `_ts_resolve_stuck_exit_pending`)에서 발생. 이 경로가 `grade`를
**청산(EXIT) 주문 dict**(`pending`)에서 읽었는데, EXIT 주문 dict엔 애초에 `grade` 키가
없어(`_set_pending_order`가 EXIT 생성 시 grade 인자 없이 기본값 `""`로 호출) 항상 빈값이
됐다. 같은 블록 바로 위에서는 `entry_price`/`entry_time`을 이미 **`self.position`**
(진입 시점 데이터를 들고 있는 포지션 객체)에서 올바르게 읽고 있었는데 `grade`만 잘못된
객체를 참조하고 있었다.

정상 청산 경로(`PositionTracker.apply_exit_fill → _build_exit_result`,
`strategy/position/position_tracker.py:875`)는 `"grade": self.grade`로 정확히 포지션
객체에서 읽는다 — stuck-exit 합성 경로만 이 패턴을 안 따르고 있었다.

이미 `dev_memory` 285차/286차에 "미조치"로 등록돼 있던 항목이 이번 리포트 딥다이브
숫자로 실측 확인된 것(신규 발견 아님).

**잠재 버그 추가 발견**: 같은 코드블록의 `_sq_result` dict에 `entry_horizon` 키
자체가 아예 없었음 — 정상 경로(`_build_exit_result`)는 `"entry_horizon": self.entry_horizon`도
포함하는데, stuck-exit 경로만 누락. 향후 거래 재개 후 stuck exit이 한 번이라도 발생하면
그 건도 등급 버그와 동일하게 `entry_horizon`이 "?"로 잡힐 상황이었다.

### 구현
`main.py:10727-10745`(`_ts_resolve_stuck_exit_pending`) — `grade`를
`getattr(self.position, "grade", "") or ""`로, `entry_horizon`을
`getattr(self.position, "entry_horizon", None)`으로 수정해 `_sq_result`에 반영.
`_record_trade_result`(main.py:2166, 2173)가 두 키를 그대로 받아 DB에 쓰므로 별도
수정 불필요.

### 남은 사항
DB에 이미 남은 과거 5건(06-22~07-01)은 소급 정정되지 않음 — 필요 시 해당
`entry_ts`로 `ensemble_decisions`를 대조해 grade 역추적/백필 가능하나 미실시(사용자
확인 대기).

## 5. CUSUM 상시 CRITICAL/CLEAR — ref 캘리브레이션 전무 (심각, 수정 완료)

### 증상
샘플 리포트 대부분이 실거래가 있던 날엔 무조건 `CUSUM: CRITICAL`, 무거래일엔
`CUSUM: CLEAR (0.00)` — 이분법적으로만 반응, 통계적 드리프트 감지로 보기 어려움.

### 근본원인
`strategy/param_drift_detector.py`의 `DriftDetector.__init__`은 `ref_mean=0.0`,
`ref_std=1.0` 기본값을 갖고, 이를 실측치로 세팅하는 `estimate_ref_from_trades()`가
정의는 있지만 **전체 저장소에서 호출하는 곳이 단 한 군데도 없었다**
(`reset_all()`도 `hotswap_gate.py`에서 실제 Hot-Swap 발동 시에만 호출되는데, 이 시스템은
여태 v1.0 그대로라 한 번도 발동한 적이 없음 — §1과 동일한 계열의 "배선은 있는데 실행된 적
없음" 문제).

`main.py:8375-8378`에서 `update(daily_pnl=forward_stats["pnl_krw"], ...)`로 **원화
손익 그대로**를 넘기면:
```
z = (daily_pnl - 0) / 1 ≈ daily_pnl (원화 숫자 그 자체)
```
표준화가 전혀 안 돼 `h_crit=6.0` 임계값과 비교되니, 손실이 6원만 넘어도(사실상 항상)
무조건 CRITICAL. 실제로 07-01 `CUSUM: CRITICAL (7764009.50)`이 그날
`daily_pnl=-7,764,010원`과 사실상 일치했던 게 그 증거.

### 구현
`strategy/param_drift_detector.py` — `get_drift_detector()` 싱글턴 생성 시
`_calibrate_from_live_history()`를 호출하도록 추가. registry의 실제 v1.0 라이브
히스토리(daily_pnl/win_rate/profit_factor, 최대 20거래일)에서 평균·표준편차를 추정해
`pnl`/`wr`/`pf` 세 `DriftDetector` 각각에 반영(QA 시더의 가상 WFA 수치는 사용하지 않고
순수 실측 라이브 데이터만 사용).

### 검증
```
캘리브레이션 결과: pnl ref_mean=-105,624원  ref_std=2,417,643원

BEFORE(기본값): PnL -1,000,000원 → Z=-1000000.00 → CUSUM=999999.50 → CRITICAL
AFTER (수정후): PnL -1,000,000원 → Z=-0.37       → CUSUM=0.00      → CLEAR
```
동일한 100만원 손실이 이제 실제 변동성(표준편차 241만원) 대비 정상 범위(-0.37σ)로
정확히 평가됨.

### 남은 한계
`_cusum_neg`(누적 CUSUM 값) 자체는 여전히 순수 인메모리 구조라 앱 재시작 시 0으로
리셋됨 — 캘리브레이션된 `ref_mean`/`ref_std`는 프로세스 생성 시마다 다시 계산되어 유지되지만,
"20거래일 누적" 추적은 프로세스가 재시작 없이 계속 살아있어야 의미가 있음. 영속화는
미착수(범위 밖, 필요 시 별도 작업).

## 6. PSI 상시 0.000 고정 — 학습 분포 전무 (심각, 수정 완료)

### 증상
```
PSI     : 0.000 (CLEAR)
PSI/feat: cvd=0.000  vwap_position=0.000  ofi=0.000
```
샘플 7건 전체에서 예외 없이 0.000 — 시장 상황과 무관하게 항상 동일.

### 근본원인
`strategy/regime_fingerprint.py`의 `update_live()`는 `if not self._training: return 0.0`
가드를 갖는다. `self._training`(WFA 학습 시점 피처 분포)을 채우는
`save_training_fingerprint()`가 **전체 저장소에서 호출되는 곳이 단 한 군데도 없었고**,
`data/regime_fingerprint.json` 파일 자체가 존재하지 않았다. Live 피처는 매분
`update_live()`를 통해 버퍼에 계속 쌓이고 있었지만(main.py:4430), 비교할 기준 분포가
없어 매번 0.0을 강제 반환 — 시장이 어떻게 바뀌든 영원히 CLEAR로 고정될 수밖에 없는
구조였다.

### 구현
`strategy/regime_fingerprint.py` — `update_live()`에서 `self._training`이 비어있으면
`_try_bootstrap_baseline()`을 호출하도록 추가. 피처당 50개(`_N_BINS×5`) 이상 라이브
표본이 쌓이면, 기존에 있던(HotSwap 전용 수동 호출) `reset_to_live_baseline()`을 자동으로
1회 실행해 그 시점 라이브 분포를 기준선으로 승격하고 `data/regime_fingerprint.json`에
저장(디스크 영속 — 재시작해도 유지).

### 검증 (격리된 테스트 파일로 검증, 실제 `data/regime_fingerprint.json`은 안 건드림)
```
부트스트랩 전 has_training_data: False
부트스트랩 후 has_training_data: True (50개 누적 시점)
같은 분포 유지 시 PSI: 0.01~0.13 (정상 — 자기 자신과 비교라 낮게 유지)
분포를 실제로 이동시켜 주입 후 PSI: 0.69 (CRITICAL) — cvd_divergence 등 개별 피처도
  WATCHLIST→ALARM→CRITICAL 단계 전환 정상 확인
```

### 남은 한계
`_training`(기준 분포)은 JSON에 영속되지만, `_live_buf`(원시 라이브 버퍼)는 여전히
인메모리라 재시작 시 재누적 필요(재부트스트랩 자체는 기준 분포가 이미 있으면 다시
일어나지 않으므로 문제 없음 — 매 재시작 시 몇 분간 PSI가 `min_live`(50개) 채워질 때까지
계산을 건너뛰는 정도의 영향).

## 7. 종합 — 발견된 문제의 공통 패턴

6개 이상점 중 5개(§1, §2, §3, §5, §6)가 전부 같은 계열: **"배선(코드 경로·함수)은
있는데 실제로 한 번도 실행/호출된 적이 없다."**
- §1: registry의 `is_current`를 갱신하는 함수는 있지만 QA 시더가 남긴 값이 실제 배포로
  착각돼 방치.
- §2: 마이그레이션 함수는 있지만 커밋 이후 앱 재시작 전이라 미실행.
- §3: 정상 청산 경로의 grade/entry_horizon 소싱 패턴이 stuck-exit 합성 경로에만 안 옮겨짐.
- §5: `estimate_ref_from_trades()` 정의만 있고 호출부 전무.
- §6: `save_training_fingerprint()` 정의만 있고 호출부 전무.

§4만 순수하게 "아직 데이터가 없어서 정상적으로 비어있는" 케이스였다.
